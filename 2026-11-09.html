01Simon Willison09.11

Саймон Уиллисон прячет длинные PR-описания от агентов под &lt;details&gt;, а сверху оставляет короткий абзац от человека

Почти все изменения в своих проектах Уиллисон получает как PR, которые открывают Claude Code или Codex. Описания у агентов точные, но длинные: несколько абзацев перед глазами у каждого, кто открыл PR. Его приём: сверху короткий текст, который он пишет сам или берёт у агента, а полное агентское описание лежит в свёрнутом блоке `<details><summary>`. В `<summary>` он пишет модель и часто уровень effort, например «Claude Opus 5.5 Medium». Иногда добавляет скриншот.

Пример опенера для PR #3042 в datasette: «`edit-tools.js` (~220KB) was loaded on every table, row and database page, even for users who couldn't edit anything.» GitHub Markdown такие блоки поддерживает в описаниях PR и комментариях, но кнопки для них в редакторе нет, на телефоне набирать неудобно. Приём не сокращает текст и не повышает качество ревью, он только прячет детали и задаёт первое впечатление.

Для вашей связки это полезно, если PR открывают агенты (feature-kickoff, MR в конце feature-build): читателю сразу видно, стоит ли открывать PR. Первый шаг: в шаблон описания PR добавить правило «первый абзац — до 2 предложений про суть и почему это важно, остальное в `<details><summary>модель + effort</summary>`».

Что взять себе
  • В скилл feature-kickoff добавить шаблон описания MR: короткий опенер на 1-2 предложения, затем полное описание в `<details><summary>модель + effort</summary>`.
  • Заставлять агента-автора PR самого писать опенер по правилу «самый короткий текст, который вводит в курс дела», чтобы его можно было брать без правки.
  • Указывать в `<summary>` модель и effort, с которыми сделан PR (у вас они закреплены в agent-файлах), чтобы при ревью видеть, кто что писал.

02GitHub09.11

Скилл tinker-ai-skill превращает ваши сессии Claude Code в датасет и дообучает на них локальную модель через Tinker

Репозиторий drost-ai/tinker-ai-skill (MIT, создан 7 ноября 2026) — скилл из 9 шагов, 11 скриптов. Он берёт транскрипты из ~/.claude/projects/, копирует их с чек-суммами (без сабагентов, мелких сессий и приватных проектов), приводит к OpenAI-формату, вычищает шум харнесса, заменяет креды и для каждой сессии подставляет случайную личность (постоянная фейковая личность запоминалась моделью). Дальше нарезка под контекст реальным рендерером без разрыва tool call и результата, блок сжатого контекста на продолжениях, отложенная выборка целыми сессиями, LoRA на Tinker, сравнение базы и чекпойнтов, слияние и BF16 GGUF для llama.cpp. Автор, Migel Tissera, так делал Tess-4-27B и Tess-4.5-27B. Цены на ноябрь 2026: 1000 строк (~45M токенов) — ~$55 на Qwen3.6-35B-A3B, ~$185 на Qwen3.8-27B. Уроки: system prompt и определения тулов нужны в каждой строке, иначе tool use деградирует; оценивать по поведению, а не по loss (два «коллапса» при падающем loss); запускать с теми же флагами, что при обучении.

Для вас это новая ветка: у вас много сессий и локальные модели на MLX, но дообучения на своих сессиях нет. По умолчанию Claude Code удаляет сессии через 30 дней. Первый шаг: поставить `cleanupPeriodDays: 3650` в ~/.claude/settings.json, затем клонировать репозиторий в ~/.claude/skills/tinker-ai-skill и прогнать пятиминутный сухой прогон на синтетике (`make_sample_transcript.py`, затем `train_tinker.py` без `--train` — это офлайн-проверка).

Что взять себе
  • Поставить `cleanupPeriodDays: 3650` в ~/.claude/settings.json, чтобы сессии не удалялись через 30 дней и копился материал для датасета.
  • Склонировать скилл в ~/.claude/skills/tinker-ai-skill и прогнать офлайн-сухой прогон на синтетике (без `--train`, бесплатно), чтобы увидеть формат строки и число токенов.
  • Взять у них схему очистки себе: подмена кредов и случайные личности на сессию, провал при утечке; полезно для любого экспорта наших транскриптов, например для скилла observability.
  • Перенять правило оценки: сравнивать чекпойнты и локальные модели по поведению на отложенных сессиях, а не по loss.

03GitHub09.11

Scott Hanselman выпустил sandbox-mcp: одноразовая Windows 11 из Windows Sandbox для агента через CLI sbx и MCP

sandbox-mcp (репозиторий создан 2026-11-06, релиз v1.2.0) запускает Windows-приложения в одноразовой гостевой Windows 11 через Windows Sandbox. Есть CLI `sbx` и опциональный MCP-сервер `windows-sandbox`, оба на одном движке. Каждый запуск поднимает чистый гость, ставит или запускает приложение, собирает артефакты (скриншоты, запись, ошибки) и уничтожает гостя. Результаты лежат в `%LOCALAPPDATA%\sandbox-mcp\runs\<timestamp>`.

Инструменты MCP: `sandbox_run`, `sandbox_exec`, `sandbox_deploy`, `sandbox_screenshot`, `sandbox_ui_tree`, `sandbox_ui_action` (клики и ввод через UI Automation), `sandbox_install_test`, `sandbox_detonate` (подозрительный файл, сеть `off|firewall|on`), `sandbox_snapshot` и `sandbox_diff`. В CLI везде есть `--json`. Ограничения: нужна Windows 11 24H2+ Pro/Enterprise/Education, одновременно работает только один Sandbox, нужна залогиненная сессия хоста, в госте нет Store, winget и Terminal, снапшот занимает 10–20 секунд. Автор предупреждает: выход считать недоверенным, от побега из Sandbox он не защищает. В README нет раздела про Claude Code, есть примеры для VS Code, Copilot CLI и Claude Desktop.

Для тебя это актуально только если тестируешь Windows-приложения: у тебя Mac, так что запуск возможен лишь на отдельной Windows-машине. Идея пригодна и шире: агент проверяет собранное в чистой среде и видит результат по скриншотам и дереву UI. Первый шаг на Windows: `git clone https://github.com/shanselman/sandbox-mcp`, `npm ci --omit=dev`, `npm link`, затем `sbx doctor` и `sbx run C:\Windows\System32\charmap.exe --open`.

Что взять себе
  • Если появится Windows-машина: подключить `windows-sandbox` MCP (`node ...\src\server.js`) в Claude Code и прогнать `sandbox_install_test` на своём установщике.
  • Взять паттерн «чистая среда на каждый запуск + `--json` + артефакты в папку по timestamp» для своих скриптов, где агент проверяет собранное.
  • Добавить в скилл quality-gates правило: вывод из песочницы (особенно `detonate`) считать недоверенным, как советует автор.

04GitHub09.11

cc-remote: Claude Code крутится на удалённом сервере, а Read/Edit/Bash выполняются на твоей машине

cc-remote (AkaraChen, 338 звёзд, создан 2026-11-01) — ACP-агент на базе claude-agent-acp. Процесс `claude` запускается на сервере через `ssh -T`, а его встроенные файловые и shell-инструменты отключены: вместо них cc-remote подставляет локальные аналоги с теми же именами и входами (Read, Write, Edit, NotebookEdit, Bash, Glob, Grep) и локальные MCP-серверы из ~/.claude.json и .mcp.json. На сервере остаются модель, логин/подписка, системный промпт, сессия, web search, сабагенты, скиллы и серверные настройки. Нужны ssh без пароля, Claude Code 2.1.248+ на сервере и Bun для сборки. Работает с acpc, Zed, paseo.

Права: Read/Glob/Grep без вопросов; Bash одобряется по префиксу (`npm test:*`), команды с `;`, `&`, `|`, редиректами, `$(…)` никогда не одобряются автоматически. Ограничения: `.claude/` проекта (команды, скиллы, агенты, настройки) на сервер не уходит, checkpoints/rewind не видят локальные правки, LSP, Monitor и worktree отключены, MCP-ресурсы и промпты недоступны. Для тебя это скорее нишевая вещь: полезна, если модель и подписка на одной машине, а код на другой. Но потеря проектных скиллов, хуков и worktree бьёт по твоему стеку. Первый шаг: `git clone https://github.com/AkaraChen/cc-remote && cd cc-remote && bun install && bun run compile && bun link`, затем `echo <server> > ~/.config/cc-remote/host && cc-remote doctor`.

Что взять себе
  • Правило Bash-аппрува по префиксу (`npm test:*`) и запрет автоодобрения для `;`, `&`, `|`, редиректов, `$(…)` — свериться с нашим PreToolUse-хуком и добавить недостающие случаи?
  • Проверка `cc-remote doctor` (ssh + версия удалённого claude) — сделать похожий preflight-скрипт для бота/RunPod-сессий?
  • Попробовать cc-remote на тестовом сервере, зная ограничения: проектный `.claude/` не едет на сервер, worktree отключены — сначала проверить, что нужные скиллы лежат в серверном ~/.claude?

Набор из четырёх скиллов для одного человека, который раздаёт задачи ИИ-ассистентам и принимает результат

solo-to-team-skills (автор 大冰, v0.9-draft, 350 звёзд, создан 7 ноября 2026) — это не софт, а набор методик в виде четырёх скиллов. dispatch-accept-verify: перед выдачей задачи пишется строка регистрации «待收» (кто делает, кто принимает, кто проверяет), дальше отдельно фиксируются «принято», «результат получен», «проверено». Задача уходит из открытого списка только после проверки или отмены с разрешения человека. evidence-before-done: нельзя сказать «готово» без доказательства, относящегося к текущей версии (открыть файл, перезапустить проверку, повторить шаги); адаптация из obra/superpowers. beginner-ops-writing: инструкции для новичка по одному шагу. ops-case-notes: обезличенные реальные случаи. Есть шаблон templates/task-register-line.md и пример examples/walkthrough-meeting-notes/.\n\nОграничения автор указывает сам: hooks пустые (`hooks: {}`), автодиспетчеризации и напоминаний нет, проверять задачи надо вручную или средствами хоста; контролируемого эксперимента нет, так что снижение ошибок не доказано. Установка описана для Codex и ещё нескольких китайских хостов; для Claude Code структура есть, но в первый релиз не вошла.\n\nУ тебя это в основном закрыто: task-context, feature-build, process («не говори готово без проверки») и субагенты. Новое только одно: журнал выданных задач с тремя раздельными статусами. Первый шаг: открыть templates/task-register-line.md и сравнить с context.md в task-context.

Что взять себе
  • Добавить в task-context таблицу выданных задач со статусами «принято / результат получен / проверено» и правилом: закрывать только после проверки
  • В строку задачи для субагента добавлять поле «кто и чем проверяет» до запуска, а не после
