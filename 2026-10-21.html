Harp: форк терминала Warp с боковой панелью для десятков агентов Claude Code и Codex

Harp — неофициальный форк open-source терминала Warp, только macOS. Боковая панель заменяет вкладки и показывает по каждой сессии Claude Code или Codex, что она делает: работает, ждёт тебя или закончила. Метка «непрочитано» висит, пока не посмотришь; точка значит, что идёт фоновая работа; луна — вкладка отложена. Вкладки можно собирать в именованные группы. При включённой интеграции с tmux группы и порядок хранятся в самих tmux-сессиях и переживают перезапуск, а агенты определяются опросом каждые 10 секунд. Сессия, запущенная по SSH с телефона, может запросить вкладку командой `tmux set-option @warp_adopt 1`. В подвале — два кольца на провайдера (окно 5 часов и недельный лимит); числа Harp сам не получает, а читает локальный JSON, формат описан в `docs/limit-rings.md`. Для Claude Code есть хук в `integrations/claude-code`, который сообщает о фоновых задачах. Лицензия в основном AGPL-3.0. Warp AI и облако по-прежнему ходят на серверы Warp; вход через Harp не проверен. Запускается рядом с Warp: свой bundle ID и папка `~/.harp`.

У тебя уже есть воркфлоу, субагенты и фоновые агенты внутри одной сессии, а Harp решает другое: обзор многих отдельных сессий в разных вкладках, где видно, какая ждёт ввода. Полезно, если держишь несколько параллельных Claude Code в worktree. Первый шаг: скачать `Harp-<version>.dmg` из Releases, в `~/.harp/settings.toml` включить `[integrations.tmux] enabled = true` и посмотреть хук из `integrations/claude-code`. Для отладки статусов: `WARPOSS_STATUS_TRACE=1`, лог в `~/Library/Logs/harp.log`.

Что взять себе
  • Посмотреть хук из `integrations/claude-code` в Harp и сравнить с нашими Stop/UserPromptSubmit-хуками: можно ли так же отдавать статус «жду тебя» во внешний индикатор?
  • Включить `integrations.tmux` в `~/.harp/settings.toml` и гонять параллельные worktree-сессии в tmux, чтобы группы и порядок переживали перезапуск.
  • Сделать JSON с остатком 5-часового и недельного лимитов по формату `docs/limit-rings.md` и подключить его как `integrations.limit_rings.file`.

FastAPI 0.154.0: параметры запроса получили опции валидации Pydantic

FastAPI уже есть, Pydantic тоже — новое здесь только одно: релиз 0.154.0 вышел 20 октября 2026. В нём единственное изменение, фича «Add Pydantic validation options to request parameters» (PR #16542, автор @tiangolo). Смысл по названию: параметры запроса (Query, Path и т. п.) теперь принимают опции валидации Pydantic прямо в объявлении.

Какие именно опции и для каких типов параметров, на странице релиза и в самом PR не сказано. Описание PR — только пометка про ИИ, список изменённых файлов не виден. Исправлений багов и примеров кода в релизе нет. Прогон CI прошёл (41 проверка), CodSpeed не показал изменения производительности. Ломающих изменений в заметках не заявлено, но и подробностей нет.

Для твоего стека: если сейчас валидацию тонко настраиваешь через отдельные Pydantic-модели или Depends, возможно, часть можно будет упростить. Но пока не открыть diff, это предположение. Первый шаг: открыть https://github.com/fastapi/fastapi/pull/16542, вкладку Files changed, посмотреть сигнатуры и тесты; потом на ветке выполнить pip install -U fastapi==0.154.0 и прогнать pytest.

Что взять себе
  • Прочитать Files changed в PR #16542 и выписать, какие опции Pydantic теперь принимают Query/Path/Header/Cookie, прежде чем использовать.
  • Поднять fastapi до 0.154.0 на отдельной ветке и прогнать pytest, чтобы убедиться, что текущая валидация параметров не изменилась.

03FastAPI releases20.10

FastAPI 0.155.0: из Path, Query, Header и др. убрали устаревшие **extra, неизвестные аргументы дают TypeError

FastAPI уже у тебя в стеке, так что про сам фреймворк не рассказываю, только про изменение. Релиз 0.155.0 вышел 20 октября 2026 и содержит один пункт, он ломающий (PR #16545, автор @tiangolo). Из Path, Query, Header, Cookie, Body, Form и File убрали устаревшие произвольные именованные аргументы (**extra). Раньше лишний kwarg принимался и попадал в схему с предупреждением об устаревании. Теперь неизвестный аргумент вызывает TypeError.

Что менять: все дополнительные свойства JSON Schema переносятся в json_schema_extra. Было Query(custom="value"), стало Query(json_schema_extra={"custom": "value"}). Для тебя это важно, потому что ошибка вылетит при импорте модуля, где объявлен эндпоинт, то есть сервис не стартует, а не упадёт на запросе. Если держишь незакреплённую версию fastapi в pyproject или lock-файле, обновление в CI или образе может сломать сборку. Первый шаг: перед апгрейдом сделать grep по коду на нестандартные kwargs в Query(, Path(, Header(, Cookie(, Body(, Form(, File( и заменить их на json_schema_extra. Потом поднять версию до 0.155.0 и прогнать pytest. Если после обновления получишь TypeError с неожиданным аргументом, ищи именно это место.

Что взять себе
  • Сделать grep по репозиториям на кастомные kwargs в Query/Path/Header/Cookie/Body/Form/File и перевести их в json_schema_extra до апгрейда
  • Закрепить версию fastapi в pyproject и uv.lock и обновлять до 0.155.0 отдельным PR с прогоном pytest
  • Добавить в CI тест, который импортирует приложение целиком, чтобы TypeError при объявлении эндпоинтов ловился до деплоя

FastAPI 0.151.0: JSON null в теле запроса больше не заменяется значением по умолчанию

FastAPI 0.151.0 (20 октября) — breaking change, PR #16536 от tiangolo. Теперь JSON-тело различает явный null и пропущенное поле. Для отдельных Body-параметров null валидируется как None: nullable-типы его принимают, non-nullable отклоняют, даже если задан default. Значения по умолчанию и default factory срабатывают только когда поле вообще не передано. Это касается и параметров внутри JSON-объекта, и параметра, который представляет всё тело целиком. Если ожидается JSON-объект (Body(embed=True) или несколько body-параметров), а клиент прислал null как всё тело, теперь будет ошибка валидации.

Раньше null у поля с дефолтом фактически мог давать значение по умолчанию. Если у вас есть клиенты, фронт или другие сервисы, которые шлют null, чтобы «сбросить к дефолту», после обновления они начнут получать 422. Pydantic и FastAPI вы уже используете, так что новое здесь только это поведение. Первый шаг: перед обновлением до 0.151.0 прогнать pytest-тесты эндпоинтов с body-параметрами, добавив кейсы с явным null и с отсутствующим полем. Клиентам, которые слали null ради дефолта, нужно вместо этого не передавать поле, как советуют в релизе.

Что взять себе
  • Добавить в pytest параметризованные кейсы для каждого эндпоинта с Body: поле отсутствует / явный null / null как всё тело — и проверить ожидаемые 200 или 422.
  • Найти в схемах поля с default или default_factory, не объявленные как Optional, и решить: разрешить None в типе или править клиентов, чтобы они не слали null.
  • Перед обновлением зафиксировать версию fastapi в lock-файле и выкатить сначала на staging, посмотрев рост 422 в логах и метриках.
