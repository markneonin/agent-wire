Шаблон репозитория запускает до 20 Claude Code агентов на эмуляторах Android и симуляторах iOS в GitHub Actions и собирает баг-репорты

mobile-agent-testers (pierridotite, MIT, создан 2026-11-16) — шаблон репозитория: workflow собирает приложение и поднимает по одному эмулятору/симулятору на персону, в каждом работает свой Claude Code агент. Тестов писать не надо: агент играет персону (модель телефона, ОС, размер шрифта, тёмная тема, язык, локаль), проходит приложение как новый пользователь или по вашему brief и пишет отчёт с пронумерованными скриншотами. Три инструмента: экран с координатами тапов, жесты, ввод текста; плюс accessibility-проверка на каждом экране (контролы без имени, цели меньше 48 dp / 44 pt). Готовых персон 20 (14 языков, RTL, планшеты). Поддерживаются Flutter, React Native, Expo, Kotlin, Swift, KMP, Capacitor. Отчёты шифруются вашим ключом, дубли склеивает Claude локально.

Цифры из README: LocalSend, 20 телефонов, 69 мин, $4.62 — 103 отчёта сжались в 46 багов, 29 нашёл один агент, 34 не про шрифты и доступность. AnkiDroid, 10 Android, меньше 10 мин, $4.69. Примерно $0.15–0.55 за телефон. Лимиты: на бесплатных раннерах около 20 джобов, 5 из них macOS; на подписке с 5-часовым лимитом 20 агентов выедают его за ~15 минут, советуют пачки по 6–10; агенты иногда неверно читают экран. У вас нет мобильных тестеров, а паттерн «персоны параллельно + дедуп отчётов» близок к вашим workflows. Если делаете мобильное приложение — первый шаг: `gh repo create my-testers --public --template pierridotite/mobile-agent-testers --clone && cd my-testers && ./setup.sh`, затем `gh workflow run agent-testers.yml` (демо, ~20 минут).

Что взять себе
  • Персоны (модель, язык, размер шрифта, тёмная тема) как матрица параллельных агентов — сделать такую матрицу в нашем synthetic-survey или для ревью UI через Workflow?
  • Агенты дают отчёт, а Claude склеивает дубли и показывает, сколько персон поймали каждый баг (103 отчёта → 46). Добавить такой шаг дедупа в наши мультиагентные ревью (vendor-review, council)?
  • Режим `bug_report=owner/repo#123`: агент воспроизводит баг из issue на устройстве. Сделать скилл, который берёт issue и просит агента воспроизвести его перед фиксом?
  • Правило из README про лимит подписки: 20 агентов сжигают 5-часовой лимит за ~15 минут, партии по 6–10. Записать потолок параллелизма в loop-design / subagents?

02GitHub23.11

fast-anything: профилирует приложение, портирует в Rust только горячие функции через агента и проверяет их на записанных вызовах

fast-anything (MIT, npm @el4cteo/fast-anything и crates.io, репозиторий создан 21.11.2026) ставит на место «переписать всё на Rust» другую схему: scan -- <cmd> профилирует приложение и ранжирует функции по времени и портируемости; port записывает до 500 реальных вызовов, создаёт крейт на одну функцию и TASK.md для агента; verify собирает релиз и прогоняет все записанные вызовы плюс краевые случаи (NaN, ±inf, -0.0, пустые и не-ASCII входы, входы в 16 раз больше, урезанные срезы). Порт включается только при полном совпадении: float в пределах 1e-9, ошибки там же, где у оригинала. Порт, который верен, но медленнее на вызов, тоже отклоняется. enable ставит Rust одним помеченным блоком, disable убирает побайтно, FAST_ANYTHING_DISABLE=1 запускает оригинал. Поддерживаются Python 3.10+ (PyO3), Node/Bun/Deno (napi-rs), Ruby, Java, Go, PHP, C/C++, C#, R. Замеры из README: Python fuzzy dedupe 4,91 с → 42 мс (116×), TS 20×, PHP 55×, Ruby 14×, Java 3×. Выгоднее портировать внешний цикл, чтобы граница в Rust пересекалась один раз. Подходят только детерминированные функции верхнего уровня на простых данных.

Для вас новое здесь не агент-оркестрация (она у вас есть), а готовый контур «профиль → порт → доказательство эквивалентности на записанном трафике» и MCP из 8 инструментов (fast_scan, fast_port, fast_verify, fast_enable, fast_disable, fast_bench, fast_report, fast_status). Пригодится для медленных Python-скриптов в bot/ и countries/. Первый шаг: npm i -g @el4cteo/fast-anything, затем fast-anything go --agent claude -- python app.py; либо claude mcp add fast-anything -- fast-anything mcp.

Что взять себе
  • Он принимает порт, только если все записанные вызовы и производные краевые случаи совпали, и отклоняет верный, но более медленный порт. Добавить такой «replay записанных вызовов + краевые входы» в наши скиллы рефакторинга и quality-gates?
  • Включение и откат одним помеченным блоком (disable возвращает файл побайтно, плюс переменная окружения для запуска оригинала). Перенять этот паттерн для наших автоматических правок скриптов бота?
  • Прогнать fast-anything scan -- python на самом медленном скрипте в bot/ (например watch.py) и посмотреть ранжирование горячих функций, прежде чем что-то портировать.
  • Подключить его MCP (claude mcp add fast-anything -- fast-anything mcp) и вызывать fast_scan и fast_bench из наших агентов на пробу.

Замер: возврат в чат после истечения кэша Claude Code стоит ~10x нового чата, лечится /compact до паузы или /clear плюс 3 строки

Репозиторий inevolin/claude-code-usage-analysis (MIT, 160 звёзд, создан 13.11.2026) измеряет, что происходит при истечении prompt-кэша Claude Code. Кэш живёт 1 час на Pro/Max/Ultra и 5 минут на API-ключе. Методика: 13 живых прогонов на API-ключе, Opus 5.5, medium effort, Claude Code 2.1.325. Единицы с учётом кэша: input 1, запись 5 мин 1.25, запись 1 ч 2, чтение 0.05, output 5. Цифры для 1 часа расчётные, не измеренные.

Результаты относительно нового сессии: возврат в окне кэша ≈1.51x; после истечения ≈9.83x (среднее по 5 прогонам; расчёт для 1 часа 11.0x); /compact до паузы ≈2.5x; /compact после паузы ≈9.7x, то есть не помогает; /clear плюс 3 строки (Goal, Done, Next) ≈1x. Отключение встроенного инструмента сломало кэш (22x, n=2), а смена effort, правка CLAUDE.md и добавление MCP-сервера почти не влияли (0.95–1.08x). Длинный вывод инструментов раздувает контекст: +64% для длинного лога за шесть ходов (n=2). Автор честно пишет, что много выводов на n=1–2, модель компакции валидацию не прошла, субагенты не измерялись.

Для вашей схемы: у вас много длинных сессий, в том числе в Telegram-боте, так что правило перед паузой применимо напрямую. Первый шаг: скопировать skills/claude-code-usage-check в ~/.claude/skills/ и запустить /claude-code-usage-check, либо python3 -m cc_usage_study.analyze ~/.claude/projects --summary --sessions --calls -o report.json (читает только метаданные).

Что взять себе
  • Прогнать анализатор по ~/.claude/projects и посмотреть, сколько реально уходит на возвраты после истечения кэша в наших сессиях, включая бот.
  • Добавить в CLAUDE.md правило: перед паузой дольше окна кэша делать /compact, после паузы /clear и три строки Goal, Done, Next (у нас уже есть task-context, можно сослаться на него).
  • Добавить в skill settings-cleanup или хук проверку: длинные логи в Bash пропускать через tail -50, не менять набор встроенных инструментов посреди сессии.
  • Для cron и headless-скриптов с claude -p: каждый запуск свежей сессией, состояние в файле заметок, а не через resume.

skill-distill: Claude Code превращает удачную сессию в скилл, по которому дешёвая open-weight модель повторяет задачу

skill-distill (sybil-solutions, репозиторий создан 21.11.2026, 470 звёзд) сам является скиллом для Claude Code или Codex. Учитель (сильная модель) читает удачную сессию и пишет скилл для ученика (open-weight модель в другом харнесе). Дальше цикл: ученик стартует в tmux на свежей копии исходного состояния с исходным промптом и скиллом; результат сравнивается с эталоном; учитель находит первую точку, где ученик ошибся, и правит скилл именно там; по три прогона на версию, пока результат не совпадёт. В конце человек смотрит эталон и лучшие результаты ученика рядом и принимает скилл вручную.

Защита от жульничества: у ученика отключён глобальный контекст и скиллы харнеса (где возможно); в скилл нельзя класть готовый результат или скрипт, который его выдаёт; проверки сначала валидируются на эталоне, и если проверка не проходит на эталоне, она считается сломанной. Скрипты: distill.py (init, trial, status, wait, evidence, verdict, ledger, report, accept), extract_session.py, capture_web.py (скриншоты веб-результата через Chromium). Адаптеры: omp протестирован, Codex как учитель протестирован, Claude Code как ученик написан, pi и opencode не тестировались. Бенчмарков и процентов успеха в README нет, только примеры в examples/. Claude Code как ученик требует ANTHROPIC_BASE_URL на совместимый сервер; парсера логов opencode пока нет.

Для тебя: у тебя уже есть скиллы, subagents, MLX и RunPod, но нет способа перенести рутинную задачу с Opus на дешёвую локальную модель с проверкой. Первый шаг: git clone https://github.com/sybil-solutions/skill-distill, затем ln -s "$PWD/skill-distill/skills/skill-distill" ~/.claude/skills/skill-distill (нужны tmux, git, Python 3.10+). В конце удачной сессии попросить: «distill this session into a skill for opencode with <модель> on my local server».

Что взять себе
  • Взять одну повторяющуюся задачу (например, скилл avito или market-pulse) и прогнать distill на локальной MLX-модели через opencode, чтобы понять, какие рутинные сессии можно снять с Opus.
  • Перенять правило «проверка сначала валидируется на эталоне, и если на эталоне она падает, она сломана» в наши скиллы quality-gates и testing.
  • Добавить в скиллы с subagents правило «правим инструкцию в первой точке, где исполнитель ошибся, и гоняем по 3 прогона на версию», вместо переписывания всего промпта целиком.
  • Запретить в brief для слабой модели класть готовый результат или скрипт, который его выдаёт, чтобы проверка шла по следованию инструкции, а не по копированию.

05ty releases22.11

ty 0.0.108: правило mismatched-type-name разбито на восемь, много ускорений

Вышел ty 0.0.108 (22.11.2026), тайп-чекер от Astral. Ломающее изменение: правило mismatched-type-name заменено восемью отдельными (#29957): mismatched-newtype-name, mismatched-typevar-name, mismatched-paramspec-name, mismatched-typevartuple-name, mismatched-typeddict-name, mismatched-type-alias-name дают предупреждение по умолчанию; mismatched-enum-name и mismatched-namedtuple-name выключены и проверяют имя, только если ty выводит одну строковую константу. Конфиг, флаги CLI и комментарии подавления нужно переписать под новые имена. Также ty теперь распознаёт TypeVar, ParamSpec, NewType и т.п., даже если имя известно только в рантайме: предупреждает, что имя не проверить, но тип использует. Диагностика uv-metadata переименована в project-manager (#30528).

Исправлены ошибки с ParamSpec (пересылка аргументов через распакованный tuple, ложные ошибки с lambda в вложенных вызовах), подавление invalid-paramspec на *args больше не «всплывает» на **kwargs. Огромный блок оптимизаций скорости и памяти: перегруженные вызовы (например boto3.client("s3")), проверки полей Pydantic-моделей и dataclass, enum, TypedDict, большие union литералов, LSP (автодополнение, подсказки, подсветка), вывод ty check --output-format gitlab.

Для вашего стека: если в pyproject.toml или в # ty: ignore[mismatched-type-name] есть старое имя правила, после обновления конфиг сломается. Первый шаг: выполнить grep -rn "mismatched-type-name" . и заменить на нужные из восьми правил, затем запустить ty check. Проекты на Pydantic/SQLAlchemy заметят прирост скорости.

Что взять себе
  • Найти grep-ом mismatched-type-name в pyproject.toml и # ty: ignore и заменить на новые правила — сделать это в наших репозиториях?
  • Включить mismatched-enum-name и mismatched-namedtuple-name (по умолчанию выключены), если хотим строже проверять имена в наших моделях?
  • Обновить ty до 0.0.108 и замерить время ty check на Pydantic-проектах до и после?
