01Hacker News18.11

Mastra открыла Factory: агентную канбан-доску в Slack, которой сама ведёт репозиторий Mastra

Mastra Factory — open-source «software factory», которую команда Mastra использует для разработки самого Mastra. Это настраиваемая агентная канбан-доска, которую можно @-тегать в Slack. Колонки: triage, plan, build, review, shipped. Под капотом durable-агенты, память разговоров, markdown-вики с цитированием источников, сигналы из комментариев к PR и облачная песочница с кодинг-харнессом. По умолчанию харнесс mastracode, поддержку Claude Code и Codex только планируют. За неделю Factory открыла и смержила 238 PR, люди — 630. Через три месяца команда в основном работает через Slack, сеньоры гоняют несколько сессий параллельно. Репозиторий закрыли для внешних контрибьюторов из-за потока PR низкого качества и просят подробные репро в issues. В обсуждении: фаза plan часто лишняя, её хотят заменить автоматикой triage→build; на каждую колонку можно делать скилл, выбирать модель, останавливать агента и ставить approval-гейты; рискованное надзирается сильнее. Скептик говорит, что Issues+PR уже это делают. По умолчанию агенты пишут от GitHub App «Mastra Platform», с PAT — от пользователя.

У тебя уже есть Workflow, сабагенты, worktree, feature-build и /schedule, так что оркестрация знакома. Нового здесь: триггер из Slack/PR-комментариев, постоянная доска со стадиями и вики с цитатами как память, плюс идея автоматизировать по риску. Первый шаг: `npm create factory` или шаблон https://github.com/mastra-ai/template-factory, смотреть как устроены скиллы на колонку.

Что взять себе
  • Автоматизация по риску: у них низкорисковое идёт без плана, рискованное под надзором и approval-гейтом. Добавить такое правило в feature-build, чтобы мелкие фиксы пропускали stage grilling/plan?
  • Скилл на каждую колонку (triage, plan, build, review) с выбором модели. Разделить наш feature-build на такие отдельные скиллы с пинами модели?
  • Вики с цитированием источников как память проекта. Попробовать markdown-вики со ссылками на код/PR рядом с CLAUDE.md и auto memory?
  • Сигналы из комментариев к PR как триггер сессии. Сделать хук или /schedule-рутину, которая подхватывает комментарии к PR и запускает агента?

02Codex CLI releases20.11

Codex CLI 0.171.0: модели GPT-6.2 Sol и Astra, TUI-workspace по умолчанию, codex exec --remote

В Codex CLI 0.171.0 (20 ноября 2026) добавили GPT-6.2 Sol и Astra в каталоги моделей, Sol теперь выбран по умолчанию. TUI-workspace включён по умолчанию: поиск по документам, превью изображений и транскрипты сабагентов рядом с основным диалогом. Появились настраиваемые undo/redo в композере (не-Vim), команды /rc и /remote для локального удалённого управления с кодом сопряжения устройства, и кастомная строка статуса для MCP через /statusline (под флагом tui_extensions_statusline).

Для автоматизации важнее всего `codex exec --remote <ADDR>`: неинтерактивная сессия запускается или возобновляется на уже работающем app server. Среди фиксов: сохранение черновиков и очереди при переключении сессий, права не сбрасываются при смене рабочей директории, поздние события завершения больше не отменяют approval нового хода, исправлен вход в корпоративные MCP, где IdP не отдаёт refresh-токен. В списке изменений ~200 PR: песочницы (seccomp, bubblewrap, Windows), Guardian, трейсы и бюджеты.

Для тебя: Codex у тебя второй мнение-инструмент через skill use-codex и vendor-review, а смена дефолтной модели на Sol меняет, чем именно ты ревьюишь. Проверь, какую модель получает `codex exec` без явного флага, и при необходимости закрепи её. Первый шаг: обновить Codex и попробовать `codex exec --remote <ADDR>`.

Что взять себе
  • Закрепить модель явным флагом в скиллах use-codex и vendor-review, раз дефолт сменился на GPT-6.2 Sol
  • Попробовать `codex exec --remote <ADDR>` в use-codex, чтобы запускать ревью на постоянно живом app server вместо холодного старта
  • Включить кастомную строку статуса MCP через /statusline (флаг tui_extensions_statusline) и посмотреть, полезна ли она

03Hacker News18.11

Google выпустил Gemini 4 Neon: средний уровень семейства, $3/$15 за млн токенов, #1 в Coding Agent Index

18 ноября 2026 Google представил Gemini 4 Neon, модель для сложной разработки и knowledge work. В семействе Gemini 4 она между Carbon (самые тяжёлые долгие проекты) и Hydrogen (быстрое повседневное). Цена: $3 за млн входных токенов, $0.15 за кэшированные, $15 за выходные, контекст 1M. Четыре уровня thinking, по умолчанию high, для сложного есть xhigh. ID модели: `gemini-4-neon`.

Цифры Google: #1 в Artificial Analysis Coding Agent Index (58.6), Terminal-Bench 4.1 — 65.2%, FrontierCode 2.0 — 46.2%, SWE-sweep 12.8% на mini-SWE и 39.0% в Antigravity. На high стоимость задачи на 32% ниже, чем у Carbon, и на 50–80% ниже, чем у конкурентов (по заявлению Google). Neon может работать как оркестратор параллельных субагентов Hydrogen в Antigravity; в демо упоминается команда `/swarm`. Заявлено меньше лишних чтений файлов и аккуратная компакция контекста. Доступна в платном API AI Studio и в Antigravity для Pro и Ultra; про CLI и лимиты в статье ничего нет. Все цифры — собственные бенчмарки Google. В обсуждении на HN (768 комментариев) Opus 5.5 хвалят за долгие проекты и связность, а Gemini — за более естественный текст (коммиты, PR). Жалуются на урезание квот и лимиты Antigravity.

Для тебя это ещё один кандидат во вторые мнения рядом с Codex и Gemini CLI, а не замена Opus 5.5. Первый шаг: прогнать `gemini-4-neon` на одном реальном ревью через скилл vendor-review и сравнить с Opus.

Что взять себе
  • Добавить `gemini-4-neon` в скилл vendor-review как отдельного ревьюера и сравнить находки с Opus 5.5 на одном реальном diff.
  • В HN хвалят Gemini за живой текст без «Claudese» и отдают ему коммиты и PR-описания. Проверить это на нашем human-writing/human-english через `slop_check.py`: сравнить вывод Neon и Sonnet.
  • Neon на high заявлена на 32% дешевле Carbon за задачу. Через use-antigravity попробовать отдать Neon объёмные задачи (саммари, извлечение) и замерить расход квоты.

04GitHub20.11

diego3g/craft: набор дизайн-скиллов для агентов, который рисует экраны со всеми состояниями и сам их проверяет

craft (MIT, 280 звёзд, создан 15 ноября 2026) — набор скиллов для Claude Code, Codex, OpenCode, Cursor и других агентов. Работает с Paper, pen.dev, Figma (через MCP) или с обычным HTML как запасным вариантом. Адаптер Figma, по словам README, ещё не проверен в реальных запусках.

/craft-setup по одному вопросу интервьюирует и пишет DESIGN.md из восьми разделов: Product, Audience and voice, Mood, Brand, References, Constraints, датированный Decisions log и Open questions; плюс токены и базовые компоненты. /craft берёт страницу, экран, флоу или элемент, подтверждает объём, перечисляет состояния (empty, loading, error, длинный контент, права, offline) на реалистичных «грязных» данных, рисует и проверяет. Остальные скиллы: craft-critique (ревью по важности, в режиме ревью ничего не меняет), craft-states, craft-explore (три структурно разных направления), craft-system (токены, индекс компонентов, аудит), craft-sync (связывает дизайн-систему в коде с дизайн-инструментом, правки возвращает диффом на ревью). Есть скрытый роутер using-craft. Правило «проект главнее»: если дизайн-система проекта отличается, она побеждает дефолты.

Для твоего сетапа: у тебя уже есть скилл frontend-роутер, skills и плагины, так что новизна — готовый дизайн-процесс с обязательным перечнем состояний и DESIGN.md как памятью решений. Первый шаг: `/plugin marketplace add diego3g/craft`, затем `/plugin install craft@craft` и `/craft-setup` в небольшом UI-проекте; сравнить с твоим frontend-скиллом.

Что взять себе
  • DESIGN.md с датированным Decisions log и Open questions — добавить такой файл-память в UI-проекты и ссылку на него в CLAUDE.md?
  • Обязательный перечень состояний (empty, loading, error, длинный контент, права, offline) перед отрисовкой — добавить как чек-лист в наш скилл frontend?
  • craft-critique: ревью, ранжированное по важности и ничего не меняющее — завести похожий режим «только ревью» для UI в frontend-скилле?

05Postgres Weekly19.11

Вышел Postgres 19: REPACK без блокировок, управление планами запросов, репликация последовательностей

Postgres 19 вышел 19 ноября 2026. Главное: REPACK убирает bloat и может переупорядочить таблицу по индексу; REPACK (CONCURRENTLY) не блокирует чтение и запись до финальной подмены. Он заменяет VACUUM FULL и CLUSTER (те остаются для совместимости). Для разработчика: INSERT ... ON CONFLICT DO SELECT (get-or-create за один запрос), COPY с выводом в JSON, IGNORE NULLS в оконных функциях. Для планов: расширение pg_plan_advice позволяет подсказывать планировщику, а pg_stash_advice применяет подсказки автоматически по query ID — медленный план чинится без правки приложения. Репликация: логическую можно включить без рестарта, реплицируются sequences, WAIT FOR LSN даёт read-your-writes на standby.

Для твоего стека: ON CONFLICT DO SELECT заменит в SQLAlchemy/asyncpg связку «insert on conflict do nothing + select» одним запросом, а WAIT FOR LSN полезен, если читаешь с реплик после записи. Перед апгрейдом: JIT теперь выключен по умолчанию; индексы full text search, pg_trgm и fuzzystrmatch могут потребовать reindex после pg_upgrade; pg_upgrade --check может пройти, а апгрейд упасть, если где-то standard_conforming_strings = off или есть свой каст uuid→bytea (теперь встроенный). После pg_restore делай VACUUM ANALYZE. Также вышли минорные 18.7, 17.12, 16.16, 15.20, 14.25 (52 security-исправления), Postgres 14 больше не поддерживается. Первый шаг: на стенде выполнить REPACK (CONCURRENTLY) на раздутой таблице и pg_upgrade --check.

Что взять себе
  • Заменить в наших SQLAlchemy-репозиториях паттерн «INSERT ON CONFLICT DO NOTHING + SELECT» на ON CONFLICT DO SELECT после перехода на 19
  • Добавить в чек-лист апгрейда: reindex FTS/pg_trgm, проверку standard_conforming_strings и своих кастов uuid→bytea, VACUUM ANALYZE после pg_restore, решение по JIT
  • Попробовать pg_stash_advice на одном медленном запросе по query ID вместо правки кода
  • Проверить, не стоит ли на Postgres 14 какой-то сервис — он больше не поддерживается
