Claude Code 2.1.332: скиллы из MCP-серверов (бета) и хук PreSkillShellCommand

В релизе от 25 ноября MCP-серверы теперь могут отдавать скиллы (бета). В меню `/` они показываются как `server:skill`, а остальные скиллы называются по-старому. Ещё появился хук `PreSkillShellCommand`: он может отклонить inline-шелл-команды скилла или команды, пока они загружаются. На 2.1.331 и старше настройки с этим именем при старте открывают диалог, так что обновляйте все машины сразу.

Остальное по большей части исправления. Починены зависания при бесконечном выводе хука и при заваленном stdout локального MCP-сервера: Ctrl+C раньше не срабатывал. Вывод хука длиннее ~50 000 символов теперь обрезается, а чтение именованного канала (например, `.env` от залоченного менеджера секретов) падает через 20 секунд. CLAUDE.md и rules больше не отправляются повторно при входе в worktree в `.claude/worktrees`. PreToolUse-хук теперь показывает причину запроса подтверждения на Read, Grep, Glob, Edit и Write. `/permissions` отвергает правила, которые не сработают при следующем старте, например `rm -rf` без имени инструмента. Для OpenTelemetry добавлено событие `assistant_response` (включается `OTEL_LOG_ASSISTANT_RESPONSES=1`). Ещё `computer-use` стал зарезервированным именем скилла на Mac с включённым computer use.

Для вас важно, что у вас много своих скиллов и хуков, а worktree вы используете на каждого писателя. Первый шаг: обновиться и проверить, что нет скилла с именем `computer-use`. Затем посмотреть, как ваш MCP-сервер (например, codebase-memory) мог бы отдавать скиллы, и попробовать хук `PreSkillShellCommand` на скиллах с inline-шеллом.

Что взять себе
  • Добавить хук `PreSkillShellCommand` в settings.shared.json, который режет опасные inline-шелл-команды в чужих скиллах и плагинах (plannotator, superpowers), но сначала обновить все машины до 2.1.332, иначе на 2.1.331 откроется диалог.
  • Проверить, нет ли у нас скилла или команды `computer-use`: на Mac с computer use он перестанет грузиться, переименовать.
  • Попробовать отдавать скиллы прямо из собственных MCP-серверов (codebase-memory, runpod) как `server:skill`, вместо копирования в ~/.claude/skills.
  • Если свои хуки пишут длинные логи, учесть обрезку вывода хука на ~50 000 символов, а в OpenTelemetry-фильтрах проверить `service.name` у desktop-сессий (теперь `claude-code-desktop`).

shrink-anything: CLI удаляет мёртвый код, файлы и зависимости, оставляя только те срезы, после которых тесты проходят

shrink-anything (MIT, npm @el4cteo/shrink-anything и crates.io, репозиторий создан 23.11.2026, 218 звёзд) чистит кодовую базу от мёртвого кода, неиспользуемых файлов, зависимостей и ассетов. Команда `scan` только показывает кандидатов, `cut -- <проверка>` удаляет их и запускает вашу проверку. Если она падает, пачка делится пополам, пока не найдётся ломающий срез, и его возвращают. Срез остаётся, только если проверка вернула 0 и прогнано не меньше тестов, чем раньше. Изменённые файлы сначала разбираются парсером языка, тесты не трогаются, `undo` восстанавливает файлы побайтно. Мёртвый код ищется подсчётом упоминаний имени, а не графом вызовов: режут, только если все упоминания внутри самого определения. Может пропустить мёртвое, но не должен выдумать. Публичные методы, экспорты библиотек и ассеты из public/ идут агенту или под `--aggressive`. Заявлено: демо на TypeScript −45% строк, статический сайт 913→398 КБ, −46% токенов для чтения. Без тестов доверять срезам нельзя.

У вас уже есть ast-grep, code-review, quality-gates и MCP с графом кода, но автоматической чистки «срез и откат по тестам» нет. Агенты накапливают код, и это закрывает именно такой случай. Первый шаг: `npm i -g @el4cteo/shrink-anything`, затем `shrink-anything doctor` и `shrink-anything scan` в проекте с хорошими тестами (например, invest/ или bot/). Потом `shrink-anything go --agent claude -- <ваша команда тестов>`. Есть и плагин: `/plugin marketplace add EL4CTEO/shrink-anything`.

Что взять себе
  • Прогнать `shrink-anything scan` и `cut` на invest/ или bot/ (там есть тесты) и посмотреть, сколько мёртвого кода найдёт.
  • Взять их правило приёмки среза: код выхода 0 и не меньше тестов, чем было. Добавить его в скилл quality-gates, чтобы упавший или опустевший набор тестов не считался зелёным.
  • Подключить MCP `claude mcp add shrink-anything -- shrink-anything mcp` или плагин и вызывать чистку после больших агентских фич как отдельный шаг feature-build.
  • Использовать `shrink-anything report` (Markdown и SVG для PR) как вложение в ревью после чистки.

gridlines: скилл для выравнивания интерфейса, который рисует направляющие и находит элементы мимо линии

pritamux/gridlines (создан 2026-11-21, 235 звёзд, MIT, всего 2 коммита) — скилл для «прохода по выравниванию». Принцип из README: сначала нарисуй линии, потом двигай элементы. Скилл рисует вертикальные направляющие по интерфейсу (сайдбар, тулбар, панель, меню, таблица), находит элементы, которые не попали на свою линию, и правит их padding, чтобы у всего был небольшой набор общих краёв.

Состав: SKILL.md (процесс и правила), probe.js (выполняется на странице, меряет реальные края «чернил» текста, иконок и контролов, рисует линии, выдаёт список промахов), audit.mjs (headless Chromium через Playwright, делает снимок 2x с линиями и JSON-отчёт; путь к Playwright задаётся через PW_DIR), examples/sidebar.html с четырьмя подложенными промахами. Пример отчёта: «MISS y56 trailing: 15px vs 12px». probe.js можно вставить в консоль любой страницы и вызвать window.__gridlines(). Правила основаны на переработке сайдбара Linear от Karri Saarinen и главе про layout в Apple HIG. Разделы «How it works» и «The rules» в README — картинки, их текст я не прочитал; поддержка агентов кроме папки скиллов Claude Code не указана.

Для твоей связки: у тебя есть скилл frontend и Claude in Chrome, но мерная проверка выравнивания (пиксели вместо «на глаз») — новое. Первый шаг: `npx skills add pritamux/gridlines`, затем `/gridlines` на странице examples/sidebar.html, чтобы увидеть четыре промаха.

Что взять себе
  • Поставить скилл (`npx skills add pritamux/gridlines`) и подключить его из роутера frontend как шаг «выравнивание» после вёрстки.
  • Взять идею probe.js (измерять края текста и иконок в DOM и выдавать отчёт «MISS ... 15px vs 12px») и сделать такую проверку частью quality-gates для UI-проектов.
  • Добавить в правила frontend принцип «сначала нарисуй направляющие, потом двигай элементы»: агент сначала получает измеренный отчёт и только потом правит padding.
