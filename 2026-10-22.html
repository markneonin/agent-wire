01Claude Code releases21.10

Claude Code 2.1.307: событие OTel safety_event, /claude-api api-version и пачка фиксов MCP и субагентов

Релиз от 21 октября 2026. Новое: команда `/claude-api api-version` переводит код с Claude API на версию API `2026-10-21`. Ещё добавлено OpenTelemetry-событие `claude_code.safety_event`: оно создаётся на каждый вызов инструмента, который остановило, переспросило или вернуло назад правило разрешений, auto mode, safety check, хук или песочница.

Фиксы, которые касаются headless и MCP: в `claude -p` на macOS серверы MCP больше не пишут «needs authentication» при заблокированном keychain (теперь пишут причину, а следующий запуск после разблокировки подключается без нового входа). Серверы не считаются зависшими, если комп уснул во время подключения. HTTP MCP-вызовы при обрыве соединения повторяются только для read-only или идемпотентных инструментов, раньше уходили дважды. Модельный алиас `opus[1m]` не падает с model-not-found при `CLAUDE_CODE_DISABLE_1M_CONTEXT`. Битые вызовы инструментов теперь повторяются до двух раз, прежде чем ход завершится ошибкой. Форк-субагенты, запущенные пачкой, теперь знают, какой запуск их собственный, и реже лезут в работу друг друга. В транскриптах субагентов теперь настоящие токены и stop reason. Исправлены и некоторые ошибки «Autocompact is thrashing» при чтении многих PDF-страниц и картинок.

Для твоей связки это в основном стабильность: у тебя много `claude -p` в скриптах, MCP (Chrome, Telegram, RunPod) и параллельные субагенты через Workflow. Первый шаг: обновиться и прогнать `/claude-api api-version` в проекте, где есть код на Claude API; для `safety_event` включить OTel-экспорт и посмотреть, какие вызовы режут хуки и auto mode.

Что взять себе
  • Включить OTel-экспорт и собирать `claude_code.safety_event` - скормить это в скилл observability, чтобы видеть, какие вызовы режут хуки, auto mode и песочница?
  • Прогнать `/claude-api api-version` в проектах с кодом на Claude API (например, в скриптах с `claude -p --json-schema`) и посмотреть дифф перед коммитом?
  • Перепроверить Workflow-скрипты с пачкой форк-субагентов: после фикса их брифы можно не страховать от пересечения работы вручную?

02GitHub22.10

axuse: MCP-сервер для управления браузером через дерево доступности и CDP, без скриншотов

axuse (ctoldigital/axuse, 246 звёзд, создан 14 октября 2026) — MCP-сервер для браузера и десктопа, работает с Codex, Claude Code, OpenCode, Antigravity. Вместо цикла «скриншот → клик» читает DOM и accessibility tree через CDP. ax_open отдаёт полный снапшот с ссылками вроде [ref=e7]; после действий возвращается только диф (что удалено, добавлено, изменено). Ссылки привязаны к идентичности элемента и переживают вставки в DOM. Ввод идёт через CDP Input.dispatch*, то есть события isTrusted. Ошибки типизированы: REF_NOT_FOUND, STALE_STATE, DIALOG_OPEN, с подсказкой retry (reobserve, retry, never) и флагом action_sent. ax_fill заполняет всю форму одним вызовом. Нужны Node.js 22+ и Chromium-браузер, зависимостей нет.

Бенчмарк авторский (16 задач, Codex CLI, одна модель): 17 с медианы против 26 с у Codex + Chrome extension и 56 с у browser-use; токенов 4.7M против 9.8M и 8.8M; медиана вызовов 5 против 7 и 12. На сложном наборе из 7 задач axuse прошёл 7/7, Codex+Chrome провалил 2, browser-use 1. Это один прогон автора, с Playwright MCP и Chrome DevTools MCP не сравнивали. Ограничения: антибот-защиты нет, macOS-десктоп только по opt-in, расширенный бэкенд не заходит в кросс-доменные iframe. Лицензия PolyForm Noncommercial: коммерческое использование требует отдельной лицензии.

Для тебя это альтернатива Claude in Chrome и Chrome MCP, если упираешься в токены на скриншотах. Первый шаг: git clone https://github.com/ctoldigital/axuse.git, cd axuse, node src/cli.js doctor, затем claude mcp add --scope user axuse -- node <path>/src/cli.js mcp.

Что взять себе
  • Подключить axuse как MCP рядом с Claude in Chrome и прогнать одну и ту же веб-задачу в обоих, сравнив токены и время через скилл observability?
  • Взять из axuse паттерн типизированных ошибок с подсказкой retry (reobserve/retry/never) и флагом action_sent в наши самописные MCP и скрипты claude -p — добавить в code-style или скилл loop-design?
  • Взять паттерн «после действия возвращать только диф» для наших скриптов автоматизации браузера (avito, Playwright) вместо повторных полных снапшотов?

03GitHub22.10

Каталог из 12 866 open-source проектов, созданных реверс-инжинирингом, с поиском и скиллом для агента

alexgaoth/awesome-reverse-engineered (репозиторий создан 11 октября 2026) - список проектов, которые появились из реверса закрытых приложений, API, устройств, протоколов, форматов файлов и игр. Девиз: «Don't reverse engineer it twice». Сейчас 12 866 проектов, суммарно около 10,7 млн звёзд: 7 078 активных, 1 951 замедлившихся, 2 491 заброшенных, 898 в архиве. 20 категорий; крупнейшие - декомпиляции игр (3 034), устройства и IoT (3 028), RE-инструменты (741). Данные лежат в data/entries.json, ночной GitHub Action обновляет звёзды, статус архивации и мёртвые ссылки и удаляет пропавшие репозитории. Исключены эксплойты, джейлбрейки, обходы защит, расшифровщики, читы, снятие DRM, решалки капчи и боты для аккаунтов. Автор предупреждает: неофициальные API ломаются при смене на стороне вендора, а их использование может нарушать условия сервиса.

Скиллы и плагины у тебя уже есть, новое здесь - сам индекс. Агент перед тем, как писать парсер, клиент или обёртку над закрытым сервисом, сначала ищет готовое: ранжирует по звёздам, активности и лицензии, читает README и берёт инструмент. Для твоих задач с Avito, Telegram, умными устройствами это экономит исследование. Первый шаг: скачать один файл на stdlib Python: curl -sL https://raw.githubusercontent.com/alexgaoth/awesome-reverse-engineered/main/plugin/skills/find-reverse-engineered/scripts/re_index.py -o re_index.py, затем python3 re_index.py search tuya local. Либо в Claude Code: /plugin install reverse-engineered --marketplace alexgaoth/awesome-reverse-engineered.

Что взять себе
  • Поставить плагин reverse-engineered (/plugin install reverse-engineered --marketplace alexgaoth/awesome-reverse-engineered) и проверить на задаче с закрытым API, например Avito или умное устройство.
  • Добавить в скилл task-framing или feature-build правило: перед написанием клиента или парсера для закрытого сервиса сначала запустить python3 re_index.py search <продукт>.
  • Использовать подкоманды re_index.py info и clone (шаллоу-клон в vendor/) в брифе сабагента, который выбирает готовую библиотеку, и смотреть метку здоровья (active/slowing/dormant) до зависимости.

04Postgres Weekly21.10

Вышел Postgres 19 RC1: REPACK CONCURRENTLY, ON CONFLICT DO SELECT, релиз 19 ноября

PostgreSQL ты уже используешь, поэтому только новое. RC1 вышел 15 октября 2026, RC2 запланирован на 12 ноября, GA — на 19 ноября (если не всплывут проблемы). Автор (Tom Kincaid, EDB) советует держать продакшен на 18 и тестировать 19 вне прода.

Что осталось в релизе: REPACK — переписывает таблицу, возвращает место и может упорядочить строки по индексу; REPACK CONCURRENTLY позволяет читать и писать почти всё время работы: изменения ловятся через логическое декодирование и применяются в конце. Также есть pg_plan_advice (подсказки планировщику), улучшения autovacuum, синхронизация sequences в логической репликации, ON CONFLICT DO SELECT (upsert возвращает существующие строки) и IGNORE NULLS в оконных функциях. Из беты откатили: SQL property graph, слияние/разбиение партиций, включение/выключение checksums на живом сервере; по данным сообщества — ещё GROUP BY ALL и UPDATE/DELETE ... FOR PORTION OF. Причина — надёжность и предсказуемый график. Август 2026: патч-релиз 18 закрыл 28 CVE (обычно около двух).

Для тебя: REPACK CONCURRENTLY заменит pg_repack для раздутых таблиц без долгих блокировок, а ON CONFLICT DO SELECT упростит upsert в SQLAlchemy-коде без лишнего SELECT. Первый шаг: поднять postgres:19rc1 в docker-образе или CI и прогнать на копии раздутой таблицы REPACK (CONCURRENTLY) имя_таблицы. Чек-листы автора в доступной части статьи не нашёл.

Что взять себе
  • Поднять postgres:19rc1 в отдельном CI-джобе и прогнать наш pytest-набор против него, чтобы заранее увидеть поломки до GA 19 ноября.
  • Проверить REPACK (CONCURRENTLY) на копии самой раздутой таблицы и сравнить с нашим текущим способом борьбы с bloat.
  • Найти в SQLAlchemy-коде upsert'ы с ON CONFLICT DO NOTHING + повторный SELECT и проверить, упростит ли их ON CONFLICT DO SELECT.
  • Не переводить прод с 18 до GA; в планах миграций учесть, что GROUP BY ALL и FOR PORTION OF в 19 не попали.

05FastAPI releases21.10

FastAPI 0.159.0: модели параметров query, header и cookie можно делать необязательными

В FastAPI 0.159.0 (релиз 21 октября 2026) одна новая возможность: поддержка опциональных моделей параметров для query, header и cookie (PR #16584, автор @tiangolo). Другие разделы в заметках релиза отсутствуют.

Модели параметров (Pydantic-модель, которая собирает query, header или cookie в один объект) в FastAPI уже есть, и ты с Pydantic и FastAPI работаешь, так что сама идея тебе знакома. Новое здесь только то, что такую модель теперь можно объявить необязательной. В релизе и в PR нет описания деталей: нет примеров кода и не сказано, что приходит в обработчик, когда параметров нет. PR изменил три страницы документации: query-param-models, header-param-models и cookie-param-models. Судя по заголовку, речь о необязательных моделях, но точное поведение я из источника подтвердить не могу. Автор указал, что PR сделан с помощью Codex и проверен вручную. Бенчмарки CodSpeed показывают, что производительность не изменилась.

Для твоего кода это пригодится, если есть эндпоинты с группой необязательных фильтров или заголовков. Первый шаг: обнови пакет (pip install -U fastapi==0.159.0) и прочитай три страницы документации выше, затем проверь поведение на тестовом эндпоинте в pytest.

Что взять себе
  • Проверить в pytest, что приходит в обработчик с опциональной моделью query/header/cookie, когда параметров в запросе нет (None или пустая модель), до переноса на неё реальных эндпоинтов
  • Найти эндпоинты, где необязательные фильтры или заголовки описаны отдельными аргументами, и прикинуть, какие из них стоит свернуть в опциональную модель

06FastAPI releases21.10

FastAPI 0.158.0: можно объединять несколько Pydantic-моделей форм в одном эндпоинте

FastAPI 0.158.0 (21 октября 2026) содержит одно изменение: «Add support for combining form models», PR #16577 от @tiangolo. В заметках к релизу больше ничего нет: ни примеров, ни ограничений, ни пунктов о несовместимости. Из самого PR известно немного. Он затрагивает страницу документации «request-form-models» и добавляет пример docs_src/request_form_models/tutorial003_an_py310.py с моделью Preferences(BaseModel), у которой есть поле tags: list[str] = []. Код написан с помощью Codex и проверен вручную, 52 проверки CI прошли, CodSpeed не показал изменений по производительности. В ревью спорили про изменяемое значение по умолчанию []: рецензент просил так не писать, другой ответил, что Pydantic копирует такие значения, так что это вопрос стиля.

Что именно можно комбинировать и как это выглядит в сигнатуре, на странице не сказано, это я додумывать не буду. FastAPI и Pydantic ты уже используешь, а модели форм (Form с Pydantic-моделью) появились раньше, так что новое здесь только комбинирование. Пригодится, если в эндпоинте с multipart/form-data или urlencoded сейчас приходится вручную собирать поля из нескольких групп. Первый шаг: обновиться до fastapi==0.158.0 и открыть новый пример tutorial003_an_py310.py и страницу request-form-models в документации, чтобы увидеть точный синтаксис, до того как переписывать свои формы.

Что взять себе
  • Обновиться до fastapi==0.158.0 в тестовой ветке и прогнать pytest на эндпоинтах с Form-моделями: в заметках нет пунктов о несовместимости, но и деталей тоже нет.
  • Посмотреть docs_src/request_form_models/tutorial003_an_py310.py и найти у нас формы, собранные вручную из нескольких групп полей: возможно, их можно заменить комбинированными моделями.
