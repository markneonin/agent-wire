Skein: Go-бинарник для роя локальных процессов с аварийной остановкой по эпохам и отбраковкой запоздавших результатов

Skein (MIT, v0.2.0, ранний релиз) — control plane для запуска графов задач локальными командами с ограниченной параллельностью. Это не агентный фреймворк и не рантайм моделей: в JSON-манифесте задаются argv-массивы (без неявного shell), зависимости, многопроходные блоки, лимиты воркеров и таймауты на проход. Ядро — epoch fence: `skein stop` увеличивает постоянный счётчик эпохи, сбрасывает очередь и отклоняет результаты, которые приходят из старой эпохи, а не просто помечает задачи отменёнными. Стоп — идемпотентная защёлка на диске, fail-closed, эпохи не переиспользуются. Заодно убивает деревья локальных процессов (Linux, macOS, Windows). Аренда (lease) — fencing-токен, не credential: внешние системы должны проверять его через свой шлюз. Состояние лежит в `.skein/runs/<run-id>/` (report.json, events.jsonl). Статический бинарник, без демона и БД. Заявлено: 160/160 деревьев процессов остановлены, медиана 141.7 мс; граф из 1000 узлов — 1.6–3.3 мс против 0.5–0.9 с у LangGraph (одна машина, Windows). Не покрыто: песочница, подписанные lease, проверка смысла вывода агента, exactly-once побочных эффектов, восстановление после падения.

Для тебя это скорее идея, чем замена: у тебя Workflow и сабагенты, но запоздавший воркер после отмены или `/loop` может дописать результат в уже устаревшее состояние. Семантика «эпоха + отбраковка поздних результатов» закрывает именно это. Первый шаг: поставить через `curl -fsSL https://raw.githubusercontent.com/Balanov/skein/main/install.sh | sh`, прогнать `skein run --state .skein --workers 2 --include-tasks examples/fanout.json`, потом `skein stop` и `skein status` (ждём `{"stopped":true,"epoch":2}`).

Что взять себе
  • Проверить, что в твоих `claude -p` скриптах и Workflow поздний результат отменённого агента не попадает в итог: добавить в task-context/loop-design правило «номер эпохи/прогона в имени файла результата, чужую эпоху игнорировать».
  • Взять идею идемпотентной защёлки стопа: в скилл loop-design добавить файл-флаг stop с проверкой перед каждым шагом и перед записью результата (fail-closed).
  • Попробовать skein как раннер для локальных батчей (whisper, MLX, Remotion) с `--workers N` и `skein stop`, который убивает деревья процессов целиком.
  • Для writer-агентов в worktree вести events.jsonl по образцу `.skein/runs/<run-id>/` для разбора в скилле observability.

02GitHub03.11

Verdict: крошечный локальный классификатор, который по выводу команды решает, правда ли она сработала

Verdict — исследовательское превью от Balanov (репозиторий создан 2026-11-02, 217 звёзд). Это классификатор результата CLI-вызова: на вход команда, exit code, stdout и stderr, на выходе одна из меток success, failure, blocked или unknown. Идея: «exit code 0 — не доказательство», например pytest с «collected 0 items / no tests ran» вернёт 0, но успехом не является.

Внутри мультиклассовая логистическая регрессия по хешированным символьным 3–5-граммам и словным 1–3-граммам: 196 608 int8-весов, модель 197 KB. Только стандартная библиотека Python, без GPU, сети и телеметрии, медиана инференса 0,54 мс. На 192 отложенных синтетических примерах из 48 семейств CLI точность 93,2% и macro-F1 93,2%, у базовой проверки по exit code 47,9% и 31,9%. Лицензия Apache-2.0, датасет CC0.

Ограничения важны: корпус синтетический и англоцентричный, на реальных трассах агентов не проверялся, вероятности не откалиброваны, и автор прямо называет инструмент советующим, а не заменой детерминированным проверкам. Он не судит о корректности кода или выполнении задачи. В README нет интеграции с Claude Code и хуками.

Для твоего сетапа это идея для PostToolUse-хука: ловить «зелёные» Bash-вызовы с пустым или подозрительным выводом (0 тестов, no tests ran). Первый шаг: git clone https://github.com/Balanov/verdict.git && python -m pip install ., затем printf 'collected 0 items\nno tests ran\n' | verdict --command 'pytest tests/' --exit-code 0 и прогнать на своих логах.

Что взять себе
  • Сделать PostToolUse-хук на Bash, который гонит команду, exit code и вывод через verdict и при метке failure/unknown на exit 0 возвращает агенту предупреждение — попробовать на тестовых прогонах?
  • Прогнать verdict на накопленных логах сессий и bot-session, чтобы замерить его точность на реальных трассах (автор этого не проверял) до внедрения в хук?
  • Добавить в quality-gates правило: «0 тестов собрано» считается провалом, даже если exit code 0, с verdict как мягким вторым сигналом?

03Claude Code releases03.11

Claude Code 2.1.317: предупреждения в /schedule, защита email от утечки, onFailure: "block" для хуков SDK и много исправлений

Релиз 2.1.317 (3 ноября 2026) — в основном исправления, но есть несколько заметных изменений. /schedule теперь предупреждает, если новая облачная задача получила коннекторы, которые вы не просили, и подсказывает, как их убрать. Перед вызовом веб- или shell-инструмента, который отправляет email вашего аккаунта в сеть, Claude Code теперь спрашивает разрешение. В хуках Agent SDK появился onFailure: "block": если callback упал, действие блокируется, а не выполняется.

Поведение, которое может задеть ваши скрипты: (1) claude -p, запущенный внутри сессии (облачной или на self-hosted runner), раньше использовал ID и транскрипт этой сессии; теперь у него свой. Старое поведение возвращает CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1. (2) claude -p теперь выходит с кодом 1, а не 0, если из-за полного диска или квоты потерялся транскрипт или запись в ~/.claude.json. (3) Субагенты и тиммейты на другой модели, чем основная, берут сохранённый или дефолтный effort этой модели, а не effort сессии. (4) SendMessage в работающий фоновый агент доходит раньше: его текущая команда уходит в фон, но не останавливается. (5) Read больше не отдаёт заглушку «file unchanged since your last Read» — возвращает содержимое. Также исправлено: Ctrl+C при очистке ввода убивал всех фоновых агентов; Grep/Glob по таймауту выдавали частичный результат как полный; самопланируемые /loop иногда не ставили wakeup; «Prompt is too long» после автокомпакции при большом CLAUDE.md. В OTel добавлены атрибуты anthropic.plan, anthropic.seat_type, anthropic.provider, anthropic.custom_base_url.

Для вас: сначала проверьте скрипты с claude -p --json-schema, которые вызываются из сессии или бота: при вложенном запуске ID сессии теперь другой, а при сбое записи будет код 1. Первый шаг: обновить Claude Code и прогнать такой скрипт изнутри Telegram-сессии, а в агентах на Sonnet под Opus проверить, какой effort они теперь получают.

Что взять себе
  • Прогнать скрипты с claude -p --json-schema изнутри Telegram-сессии после обновления и проверить, что вложенный запуск с новым session ID и код выхода 1 при сбое записи ничего не ломают (при необходимости CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1)
  • Пересмотреть агентские файлы, закреплённые за моделью и effort: субагенты на другой модели теперь берут её сохранённый/дефолтный effort, а не effort сессии — убедиться, что это то, что нужно
  • Добавить в скилл loop-design заметку: Grep/Glob по таймауту раньше отдавали частичный результат как полный, и самопланируемый /loop мог не поставить wakeup — после обновления перепроверить свои /loop
  • Если пишете хуки на Agent SDK, ставить onFailure: "block" для проверочных callback'ов, чтобы сбой не пропускал действие

Frontier-модель «GPT-6 Astra» читает и правит веса сетей напрямую; в Qwen3.5-0.8B убрала петли и подняла MATH-500 с 7,9% до 48,1%

В блоге «Sparks of Weight-Space Programming» LLM (GPT-6 Astra) без оптимизатора и градиентов читает сырые веса, рассуждает, что они считают, и пишет новые. Девять экспериментов. По весам определила игру у 4 PPO-политик (MLP, 17 253 веса) и язык у 7M-трансформеров. Одной правкой 3,5% весов починила политику Kinetix: 0 успехов в 256 эпизодах, потом 1024 из 1024. Сети MinAtar (600→32→32→6) написала с нуля без данных. Главный результат: в Qwen3.5-0.8B нашла в MLP слоёв 15 и 19 одно направление, вызывающее зацикливание, и убрала его из 131 072 весов (0,016%). MATH-500 вырос с 7,9% до 48,1%, GSM8K с 13,8% до 67,1%, IFEval с 21,0% до 62,3%, ответы, упёршиеся в лимит 32 768 токенов, упали с 93% до 33,1%.

Ограничения: авторы называют результаты очень ранними. Gemma 3 270M, которая не зацикливается, не улучшилась. Сикофанта в Gemma по одним весам найти не удалось, получилось только с паттернами внимания (голова 10.2: 85,7% против 0,75%). В Qwen нужно было ~50 прямых проходов. В обсуждении HN (2466 баллов) критики пишут, что это steering-вектор/abliteration под новым названием, «математика» — по сути исправление багa зацикливания, а независимая проверка с Claude на мелких классификаторах давала правки, снижавшие точность. Для твоего сетапа это скорее сигнал, чем инструмент: агент с PyTorch-обвязкой может вести интерпретируемость почти без человека. Первый шаг: открыть логи github.com/RikiyaT/lm_understand-logs (промпты, код, оценки) и модель RikiyaT/Qwen3.5-0.8B-weight-space-programming на Hugging Face; команд запуска в статье нет.

Что взять себе
  • Взять логи lm_understand-logs как образец «агент + песочница + прямые проходы»: у тебя уже есть RunPod и MLX, можно повторить Exp. 8 на локальной Qwen и проверить правку на MATH-500.
  • Добавить в скилл loop-design проверку «зацикливание и упор в лимит токенов»: в статье доля ответов у лимита 32 768 упала с 93% до 33,1%, это метрика сбоя, которую дёшево считать.
  • Перенять их контрольный приём: после правки гонять контрольную модель, где дефекта нет (у них Gemma), чтобы отличить снятие блока от добавления способности. Оформить как правило в скилле testing.
