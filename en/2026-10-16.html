Meta releases Muse Spark Open weights: 816B parameters, 1M context, restricted license

On October 15, 2026 Meta published the weights of Muse Spark Open: a natively multimodal model with 816B total parameters (42B active) and a 1M-token context, aimed at coding and long-horizon agentic work. It ships under the Muse Model License with limited commercial terms; per the HN thread the key clause bars offering it as a service once company revenue passes $20M. Weights are on Hugging Face, SageMaker, Google Cloud Model Garden and Microsoft Foundry; hosted APIs are Baseten, Fireworks, Groq, Modal, Nebius, OpenRouter and Together. It supports SGLang, vLLM, TensorRT-LLM, Transformers, MLX, llama.cpp and Unsloth. The page has no numeric benchmarks; a full evaluation report is promised later. Meta's demo: Muse Code fixing and fully building iOS changes to the Ice Cubes app on-device.

Running it locally is heavy: Meta used two Apple M5 Ultra Mac Studios with 512 GB each (commenters estimate $20–30k). HN opinion on quality is mixed: Artificial Analysis puts it below GLM 5.3 Flash and Qwen 3.8 Flash Next, and for coding people mostly recommend GLM 5.3 Flash and DeepSeek V4.1 Flash. For your setup it is not an Opus 5.5 replacement, but a possible cheap second opinion or worker via OpenRouter. First step: add Muse Spark Open through OpenRouter to the vendor-review skill and compare its review with Codex and Gemini on the same diff.

Take for your setup
  • Add Muse Spark Open (via OpenRouter) to the vendor-review skill as another reviewer and compare it with Codex/Gemini on the same diff.
  • Test tool-call reliability in your own scripts across several providers: HN reports failed tool calls and stray tokens from third-party hosts, likely due to aggressive quantization.

open_scion released: an open-source implementation of Scion, a version-control server for coding agents at scale

open_scion (MIT, v0.1.0, ~1000 stars in a day, 6 commits) is an independent implementation of Scion, the system Anthropic described publicly but keeps internal. The premise: classic Git assumes a human who clones, works for hours and pushes once, while agents run thousands of short tasks touching a few files on the same branches. So the work moves to the server. It is a fork of GitLab's Gitaly, with ordinary Git repositories underneath. Inside: sparse clones of only the needed paths (`graft clone`, `graft sparse`); blame, history and search computed server-side and memoized per commit; instead of a merge queue, `UserLand` rebases and lands with a compare-and-swap, batching concurrent lands; conflicts go to a resolver you pick (an LLM, a deterministic tool, or none); `graft-verify` tests the tip, bisects failures and reverts the culprit; each agent gets its own token, RPC allowlist and branch policies; a changeset log can be watched live. The server never calls a model itself. Storage is SQLite/PostgreSQL plus S3/GCS/Azure. Limits: interfaces will change before 1.0, no pack garbage collection yet, needs Go 1.26, Meson and Ninja.

For your setup (a worktree per writer, parallel agents) it is not a replacement but a view of what breaks at scale: merging and post-land verification. You likely don't need a server with a handful of agents, but the patterns carry over. First step: `git clone https://github.com/feder-cr/open_scion && cd open_scion && make build && examples/graft/quickstart.sh` — a demo with a server, two agents and a land.

Take for your setup
  • Post-land verification like `graft-verify`: after merging branches from parallel writers, run tests on the tip, bisect on failure and revert the culprit commit — make it a skill or Stop hook in our feature-build pipeline?
  • Semantic review rules: require less review for comment-only or docs changes than for logic changes — add this rule to our reviewer agents (quality-reviewer, business-reviewer)?
  • Per-agent permissions (like the RPC allowlist and branch policies): define in a PreToolUse hook which branches and git commands each custom agent may use?
