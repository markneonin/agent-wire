Skein: a Go binary for swarms of local processes with epoch-based emergency stop and rejection of late completions

Skein (MIT, v0.2.0, early release) is a control plane that runs task graphs of local commands with bounded concurrency. It is not an agent framework or a model runtime: a JSON manifest holds argv arrays (no implicit shell), dependencies, reusable multi-pass blocks, worker limits and per-pass timeouts. The core is an epoch fence: `skein stop` bumps a persistent epoch counter, invalidates queued work and rejects completions arriving from the old epoch, instead of just marking tasks canceled. The stop is an idempotent on-disk latch, fail-closed, epochs are never reused. It also kills tracked local process trees (Linux, macOS, Windows). A lease is a fencing token, not a credential: external systems must check it through their own gateway. State lives in `.skein/runs/<run-id>/` (report.json, events.jsonl). Static binary, no daemon or database. Claimed: 160/160 process trees stopped, median 141.7 ms; a 1000-node graph runs in 1.6–3.3 ms vs 0.5–0.9 s for LangGraph (one Windows machine). Not covered: sandboxing, signed leases, semantic validation of agent output, exactly-once side effects, crash recovery.

For you this is an idea more than a replacement: you have Workflow and subagents, but a late worker after a cancel or a `/loop` can still write into stale state. Epoch plus late-result rejection targets exactly that. First step: install with `curl -fsSL https://raw.githubusercontent.com/Balanov/skein/main/install.sh | sh`, run `skein run --state .skein --workers 2 --include-tasks examples/fanout.json`, then `skein stop` and `skein status` (expect `{"stopped":true,"epoch":2}`).

Take for your setup
  • Check that in your `claude -p` scripts and Workflow a canceled agent's late result can't land in the final output: add a rule to task-context/loop-design, "put a run/epoch number in the result filename and ignore other epochs".
  • Borrow the idempotent stop latch: add a stop flag file to the loop-design skill, checked before each step and before writing any result (fail-closed).
  • Try skein as a runner for local batches (whisper, MLX, Remotion) with `--workers N`, using `skein stop` to kill whole process trees.
  • For worktree writer agents, keep an events.jsonl per run, modeled on `.skein/runs/<run-id>/`, for the observability skill to analyze.

Verdict: a tiny local classifier that judges from command output whether a tool call really succeeded

Verdict is a research-preview classifier for CLI tool calls by Balanov (repo created 2026-11-02, 217 stars). Input: the command, exit code, stdout and stderr. Output: one label from success, failure, blocked or unknown. The point is that "exit code 0 is not proof": pytest printing "collected 0 items / no tests ran" returns 0 but is not a success.

Under the hood it is a multiclass logistic regression over hashed character 3–5-grams and word 1–3-grams: 196,608 int8 weights, a 197 KB model. Python standard library only, no GPU, network or telemetry, median inference 0.54 ms. On 192 held-out synthetic examples from 48 CLI families it reaches 93.2% accuracy and 93.2% macro-F1, versus 47.9% and 31.9% for an exit-code baseline. Code is Apache-2.0, the dataset CC0.

The limits matter: the corpus is synthetic and English-biased, not validated on real agent traces, probabilities are uncalibrated, and the author calls it advisory, not a replacement for deterministic checks. It does not judge code correctness or task completion. The README has no Claude Code or hooks integration.

For your setup this is an idea for a PostToolUse hook: catch "green" Bash calls with empty or suspicious output (0 tests, no tests ran). First step: git clone https://github.com/Balanov/verdict.git && python -m pip install ., then printf 'collected 0 items\nno tests ran\n' | verdict --command 'pytest tests/' --exit-code 0 and run it on your own logs.

Take for your setup
  • Build a PostToolUse hook on Bash that pipes command, exit code and output through verdict and warns the agent when an exit-0 call is labeled failure/unknown — try it on test runs?
  • Run verdict over your accumulated session and bot-session logs to measure its accuracy on real traces (the author did not validate that) before wiring it into a hook?
  • Add a rule to quality-gates: "0 tests collected" counts as a failure even with exit code 0, with verdict as a soft second signal?

Claude Code 2.1.317: /schedule connector warning, email-leak check, onFailure: "block" for SDK hooks, and many fixes

Release 2.1.317 (November 3, 2026) is mostly fixes, with a few notable changes. /schedule now warns when a new cloud scheduled task gets connectors you did not ask for, and tells you how to remove them. Claude Code now asks before a web or shell tool call sends your account email address to the network. Agent SDK hook callbacks get onFailure: "block": if the callback fails, the action is blocked instead of running.

Behavior changes that can affect your scripts: (1) claude -p run inside a cloud or self-hosted runner session used to share that session's ID and transcript; it now gets its own. CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1 restores the old behavior. (2) claude -p now exits 1 instead of 0 when a full disk or quota loses the transcript or ~/.claude.json writes. (3) Subagents and teammates on a different model than the main conversation use that model's saved or default effort, not the session's effort. (4) SendMessage to a running background agent arrives sooner: its running command moves to the background without being stopped. (5) Read no longer returns the "file unchanged since your last Read" stub; it returns the content. Also fixed: Ctrl+C clearing typed text stopped all background agents; Grep/Glob treated partial results from a timeout as complete; self-paced /loop sometimes failed to schedule a wakeup; "Prompt is too long" after auto-compaction with a large CLAUDE.md. OTel gains anthropic.plan, anthropic.seat_type, anthropic.provider and anthropic.custom_base_url.

For you: check any claude -p --json-schema scripts that run from inside a session or the Telegram bot, since the nested session ID differs now and a write failure exits 1. First step: update Claude Code, run such a script from inside the Telegram session, and check which effort your cross-model subagents (for example Sonnet under Opus) now get.

Take for your setup
  • After updating, run your claude -p --json-schema scripts from inside the Telegram session and check that the new nested session ID and exit code 1 on write failure break nothing (CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1 if needed)
  • Review your agent files pinned to model and effort: subagents on a different model now use that model's saved/default effort, not the session's — confirm that is what you want
  • Add a note to the loop-design skill: Grep/Glob used to return partial results on timeout as complete, and self-paced /loop could miss scheduling a wakeup — re-check your /loop runs after updating
  • If you write Agent SDK hooks, set onFailure: "block" on validation callbacks so a callback failure does not let the action through

Frontier model "GPT-6 Astra" reads and edits network weights directly; on Qwen3.5-0.8B it removed looping and lifted MATH-500 from 7.9% to 48.1%

The blog post "Sparks of Weight-Space Programming" has an LLM (GPT-6 Astra) read raw weights with no optimizer or gradients, reason about what they compute, and write new ones. There are nine experiments. From weights alone it named the game for 4 PPO policies (MLPs, 17,253 weights) and the language of 7M-parameter transformers. One edit to 3.5% of the weights fixed a Kinetix policy: 0 successes in 256 episodes became 1,024 of 1,024. It wrote MinAtar networks (600→32→32→6) from scratch with no data. The headline result: in Qwen3.5-0.8B it traced looping to one direction written by the MLPs of layers 15 and 19 and removed it from 131,072 weights (0.016%). MATH-500 went from 7.9% to 48.1%, GSM8K from 13.8% to 67.1%, IFEval from 21.0% to 62.3%, and answers hitting the 32,768-token limit fell from 93% to 33.1%.

Limits: the authors call the results very early. Gemma 3 270M, which doesn't loop, did not improve. The sycophantic Gemma could not be found from weights alone, only with attention patterns (head 10.2: 85.7% vs 0.75%). Qwen needed about 50 forward passes. HN commenters (2466 points) say it is steering vectors/abliteration renamed, the "math" gain is really a loop bug fix, and an independent test with Claude on tiny classifiers produced edits that lowered accuracy. For your setup this is a signal more than a tool: an agent with a PyTorch harness can run much of an interpretability workflow with little human input. First step: open github.com/RikiyaT/lm_understand-logs (prompts, code, evals) and the Hugging Face model RikiyaT/Qwen3.5-0.8B-weight-space-programming. The article gives no run commands.

Take for your setup
  • Use lm_understand-logs as a template for agent + sandbox + forward passes: you already have RunPod and MLX, so try repeating Exp. 8 on a local Qwen and verify the edit on MATH-500.
  • Add a looping / token-limit-hit check to the loop-design skill: in the article the share of answers hitting the 32,768 limit fell from 93% to 33.1%, a cheap failure metric.
  • Copy their control trick: after an edit, run a control model without the defect (they used Gemma) to tell removing a blocker from adding an ability. Put it as a rule in the testing skill.
