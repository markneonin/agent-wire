Scrawl: screen recording with voice and drawn marks that an agent reads as a bundle of frames and text

Scrawl (kitlangton/scrawl, Rust + GPUI, MIT, created 14 Oct 2026) lets you show an agent a problem instead of describing it. Press ⌥⇧S to record screen and voice; holding Shift and moving draws a red stroke, Shift-click drops a numbered pin. The output is a bundle: contact-sheet.png (annotated keyframes), frames/frame-XX.png, summary.md (time-aligned transcript and interaction timeline) and scrawl.json. The agent navigates it with scrawl zoom <bundle> --at 0:12 (or --at "a phrase"), scrawl frames --from --to, and scrawl send --clipboard or --session ses_.... It also has auto-crop to the active area, cabled iPhone recording and ScrawlKit for iOS 18+. scrawl export writes an MP4 with the marks burned in. Transcription is on-device by default (Apple SpeechAnalyzer). Auto-send targets only OpenCode sessions; everything else goes via the clipboard. Requires Apple silicon and macOS 26+; Windows is an unsigned preview. Media goes to Trash after 7 days, bundles after 30.

For you this fills a gap on visual UI bugs and Remotion video: instead of screenshots and a retelling, Claude Code gets a marked-up frame plus the spoken remark on one timeline. There is no auto-delivery to Claude Code, only the clipboard or a bundle path, and it doesn't replace Claude in Chrome (that acts; Scrawl only shows). First step: brew install --cask kitlangton/tap/scrawl, then bunx skills add kitlangton/scrawl, record 20 seconds of a bug and hand the agent the bundle path.

Take for your setup
  • Install the skill with bunx skills add kitlangton/scrawl, or read it via scrawl skill and fold it into your frontend/process skills as a step: for a UI bug, start with a Scrawl bundle.
  • Add a rule to subagent briefs: read summary.md and contact-sheet.png first, and expand only the needed moments with scrawl zoom --at instead of loading every frame into context.
  • Try scrawl export --zoom for Remotion video fixes: record what is wrong and give the agent the bundle instead of a text description of timecodes.

Superlite: a Claude Code plugin that builds from a spec with one approval and parallel agents

Superlite (github.com/iha2/superlite) is a Claude Code plugin in the Superpowers mold, aimed at autonomous builds: you hand over a spec, approve the plan once, and it builds, tests and reviews on its own. Every decision it would normally ask about is logged as a "ruling" with a rationale and the cost if wrong. Plan tasks list owned files, interfaces and required tests; independent tasks run in parallel. Roles: Opus coordinates and may not edit code, Sonnet builds and reviews, Haiku takes only small fully specified tasks, a fresh Opus reads a packet built from logs and only reports findings, and tiered fix-only agents repair them. Rules are enforced by hooks, not prompts: no code edits by the coordinator, test runs moved to the background, no killing processes by name, and the plan must pass `lint --stable`. Tokens, cost and time per agent go to `.superlite/metrics.jsonl`, with a soft warning at 70% of the budget.

Author's benchmark (one project, one harness, 177 hidden tests): 16.1 min versus 33.6 for stock Superpowers and 23.5 for orchestrated; 177/177 passed, 21 agents, up to 18 at once. On a smaller project: 8.8 vs 34.4 min. The author calls it "a strong hint rather than peer-reviewed science". HN skeptics call heavy process "planning theater" and say newer models need it less. You already have Workflow, subagents, hooks and superpowers, so what's new is enforcement in code and the decision log. First step: `/plugin marketplace add iha2/superlite`, then `/plugin install superlite@superlite-dev` (don't enable it alongside Superpowers in one session).

Take for your setup
  • A PreToolUse hook that forbids the lead/orchestrator from editing project files (as in Superlite) — add it to our task-lead and subagents skill?
  • A "rulings" log (decision, rationale, cost if wrong) in tasks/<slug>/decisions.md for hands-off "decide yourself" runs — adopt that format?
  • A hook that moves raw test runs to the background and writes the result to a file like test-summary.json — add it to our testing/feature-build skills?
  • A per-agent metrics hook (tokens, cost, time into metrics.jsonl) with a soft warning at 70% of budget — wire it into the observability skill?

audio-studio-mcp is an MCP server that generates music and sound effects locally with Stable Audio 3

audio-studio-mcp (created 18 Oct 2026, 281 stars) is an MCP server that runs Stable Audio 3 locally to make background music, loops and sound effects. No cloud, no API key. Tools: generate_audio (text to music/loop/SFX, 1–4 candidates, optional BPM), edit_audio (variation, inpaint for a time range, continue to extend), process_audio (trim, silence trim, mono, LUFS, seamless loops, fades, WAV/OGG/FLAC export; never modifies the input), unload_models. The medium model (1.4B) goes up to 380 s; sm-music and sm-sfx are faster, up to 120 s. Output is 44.1 kHz 24-bit stereo WAV with a JSON sidecar holding prompt and seed.

Requirements: Apple Silicon (M1+, 16 GB recommended, about 6 GB disk) or an NVIDIA GPU with 8 GB+ VRAM on Windows. Intel Macs and AMD are unsupported. Speed on M1 16 GB: 20 s of music in about 10 s warm. Instrumental only, no vocals. Code is MIT, weights use the Stability AI Community License. Limits: timing instructions in prompts are unreliable, so generate first and fix with inpaint/continue; use WAV/OGG for loops, not MP3.

For you: you already have Remotion, ElevenLabs and MLX on your Mac, so this fills the missing layer: free local music and SFX for videos (mediaresource). First step: git clone https://github.com/kanaworksai-hue/audio-studio-mcp.git, then ./install.sh and claude mcp add --scope user audio-studio -- /path/to/audio-studio-mcp/.venv/bin/audio-studio-mcp.

Take for your setup
  • Connect the audio-studio MCP and write a video sound-design skill: English prompts under ~45 words, for SFX state source, action, material and space, then process_audio to the target LUFS.
  • Add a step to the Remotion pipeline: music via generate_audio, seamless loop via process_audio in WAV/OGG (not MP3), length fixes via edit_audio continue/inpaint instead of timing in the prompt.
  • Copy their JSON sidecar habit (prompt and seed next to each file) and keep sidecars beside channel tracks so good sounds are reproducible.
  • With many sessions, run one warm server with --http 8765 --preload and set AUDIO_STUDIO_IDLE_UNLOAD_MIN so 5–7 GB of memory isn't held next to local LLMs.

Read-only WhatsApp MCP on Cloudflare Workers: search your own chats from Claude Code (not actually free)

finereli/whatsapp-mcp is a small read-only MCP server: you deploy it to your own Cloudflare account, link it like WhatsApp Web (QR), and an agent can search and read your messages. It cannot send. Inside: Baileys (unofficial WhatsApp Web protocol) with three shims for Workers, one Durable Object with SQLite (FTS5 index), and KV for OAuth. There is no persistent connection: it connects when the agent asks and once daily at 04:00 UTC via cron. Tools: list_chats, get_messages, search_messages, unnamed_chats, set_contact_names, sync_now, link_status, relink. Read tools refresh first if the copy is over 10 minutes old.

Limits: the "free" in the title is disputed. It needs Workers Paid ("a few dollars a month"); the author hasn't tried the free plan. Media is not downloaded or transcribed. History is delivered once per link. Tested on one real account. The README says it violates WhatsApp's ToS, ban risk is low but "isn't zero"; HN commenters reported bans with unofficial clients generally, though none confirmed for this project. Another criticism: the people you chat with never agreed to their messages going to an AI.

For you: you already have Telegram and Google MCPs and a chatting skill for WhatsApp, so this adds searchable chat history as context. First step: npm install, wrangler kv namespace create OAUTH_KV, wrangler secret put OWNER_PASSWORD, npm run deploy, then claude mcp add --transport http whatsapp https://your-url/mcp. Preferably use a secondary number.

Take for your setup
  • Wire this MCP into the chatting skill: before replying to a real person on WhatsApp, look up the history with search_messages / get_messages
  • Add a CLAUDE.md rule: WhatsApp MCP is read-only, never send, and chat contents must not go to external services (cross-vendor review, Codex, Gemini)
  • Copy the set_contact_names pattern: the agent matches phone numbers to names via the Google Workspace MCP you already have and saves them so search works by name

Guide to tmux for Claude Code: send-keys, capture-pane and six limits of the approach

A guide from crystl (a macOS terminal; the end promotes their product) on running Claude Code in tmux. Basics: one tmux session per repo (`new-session -A` attaches or creates), a window per task, panes only for the 2–4 agents you watch side by side. Claude Code has `--worktree` and `--tmux` (requires `--worktree`; on iTerm2 `--tmux` gives native panes, use `--tmux=classic` for real tmux). Driving an agent: `send-keys -l` for literal text, Enter as a separate call after ~0.3 s (otherwise the agent's input box swallows it), `C-c` to interrupt. Reading: `capture-pane -p -J -S -`; logging via `pipe-pane`. Config: history-limit 100000, escape-time 10, allow-rename off, monitor-activity. Limits: you can't tell a waiting agent from a working one, no completion notification, capture-pane is brittle screen scraping, no shared state, scrollback eats memory, everything dies on reboot. monitor-silence is only a proxy for "done": a thinking agent is silent too.

The HN thread (155 points) calls the piece an ad; suggested alternatives are Zellij, Herdr, workmux, and `claude agents` (a daemon that survives SSH drops). One commenter argues agents should run as headless daemons, not be scraped through a TUI. With your Workflow, SendMessage, background agents and `claude -p`, this mostly confirms that tmux scraping is a dead end; the only new bits are around remote sessions. First step: on a remote box run `ssh -t <host> tmux new-session -A -s <repo>` and try `claude agents` as the alternative.

Take for your setup
  • Try `claude agents` (a daemon that survives SSH drops) for long remote tasks instead of tmux, and note the result in the subagents skill?
  • If you ever have to automate an interactive TUI through tmux, record the rule: `send-keys -l`, ~0.3 s pause, then a separate Enter; read with `capture-pane -p -J -S -`.
  • Take the HN tip of wrapping frequent commands in scripts the agent calls from a skill instead of long instructions, and check which of your skills have long instructions that a script could replace.

MiniMax releases M3.1 Flash: a cheap, fast agentic model, weights later

On 2026-10-19 MiniMax announced M3.1 Flash, a model aimed at agentic tasks, coding, computer use and cybersecurity. It claims 200+ tokens/s in everyday use (P50 170+) and online inference nearly three times faster than before. Price per 1M tokens: $0.15 input, $0.60 output, $0.015 cached input; MiniMax says agentic tasks cost 70% less than on the predecessor. Benchmarks from the page: DeepSWE v1.1 73.7%, OSWorld V2 61.7 (first among Chinese models), Agents' Last Exam 29.6, BankerToolBench 76.2, CyberGym 82%. It is available via the MiniMax API, the M Plan subscription and MiniMax Code. Weights are promised later with no date; context length and parameter count are not on the page. MiniMax Pro comes later.

The HN discussion is skeptical: people who tried the stealth version "Space Bunny" in OpenCode Go found it weaker than the benchmarks suggest. One data-analytics test put it level with Opus 5.5 on accuracy but the slowest, because it burns many tokens. DeepSeek V4.1 Flash is the usual comparison, and many find it more reliable and better value. Comments mention ~428B parameters (23B active), but that is not from the page itself. For your setup this is not a replacement for Opus 5.5 or Sonnet 5.5, but a candidate for a cheap second opinion or a bulk worker in Workflow. First step: get a key at platform.minimax.io and run 2–3 of your real tasks through opencode next to your current model, measuring tokens and time.

Take for your setup
  • Add M3.1 Flash to the vendor-review skill as another cheap reviewer (via opencode) and compare its findings with Gemini and Codex.
  • Run 2–3 real tasks on M3.1 Flash and your current model, logging tokens and time: HN says it is verbose, so it may not end up cheaper.

Reason Network: a p2p daemon that lets coding agents of different people and vendors message each other

reason-network (formerly tincan, by Lars Talian of Reason, MIT/Apache-2.0, 512 stars, Rust) is a small daemon on each machine. It links a team's computers directly over iroh (same Wi-Fi or internet), with no central server. If a direct connection fails, traffic goes through a relay that sees only encrypted bytes. The default relay is run by n0; you can set your own with `reason-network relay <url>`. Messages to offline people wait until they return.

The installer adds an MCP server `reason-network` and hooks to the agents on the machine. Tools: `list_team`, `send_message`, `ask_user`, plus `check_inbox` where push isn't possible. Session status (repo, branch, busy/idle) comes from the session's own title and todo list. Supported: Claude Code, Codex, Cursor, Gemini CLI, Copilot CLI, Grok CLI, opencode, pi, DeepSeek Harness. Messages reach a live session immediately in Claude Code, Codex, opencode and pi, and wake an idle one. Cursor, Gemini, Copilot and Grok get them at the next step. `ask_user` shows the human an Approve/Deny pop-up, and the answer goes back to the requesting agent as the person's decision, not an ordinary message. Commands: `reason-network who`, `send alice/api-claude "..."`, `send '*'` (broadcast, only from a human), `send repo:api`.

What's new for you: your SendMessage works inside one session, while this connects agents of different people and machines, including Codex and Gemini. It's useful if you run several machines (Mac and a server) or get a teammate. First step: run the installer from the latest GitHub release, run `reason-network init 'test' --as mark` on two machines, then try `reason-network who` and `send`. The README also covers Reason's cloud agents, but without an account you only install the engine.

Take for your setup
  • Install reason-network on the Mac and on a RunPod/server box and check that Claude Code on one machine can message a session on the other via `send`
  • Try `ask_user` as an approval channel: a background agent asks Approve/Deny instead of waiting in a terminal, and compare it with our Telegram bot
  • Set your own relay with `reason-network relay <url>` if you don't want traffic going through n0
  • Borrow the idea of deriving session status from the session title and todo list for our observability hooks
