Simon Willison hides agent-written PR descriptions inside &lt;details&gt; and leads with a short human-written opener

Most changes to Willison's projects arrive as PRs opened by Claude Code or Codex. The agent descriptions are accurate but long: several paragraphs facing anyone who opens the PR. His pattern: a short opener on top, written by him or lifted from the agent, and the full agent description inside a collapsed `<details><summary>` block. The `<summary>` label is the model and often the effort level, e.g. "Claude Opus 5.5 Medium". He sometimes adds a screenshot.

Example opener for datasette PR #3042: "`edit-tools.js` (~220KB) was loaded on every table, row and database page, even for users who couldn't edit anything." GitHub Markdown supports these blocks in PR descriptions and comments, but the editor has no button for it, so typing it on mobile is tedious. The trick doesn't shorten the text or improve review quality; it only hides detail and shapes the first impression.

It fits your setup if agents open your PRs (feature-kickoff, the MR step of feature-build): the reader sees at once whether a PR deserves attention. First step: add a rule to the PR description template: "first paragraph is at most 2 sentences on what and why it matters; everything else goes in `<details><summary>model + effort</summary>`".

Take for your setup
  • Add an MR description template to the feature-kickoff skill: a 1-2 sentence opener, then the full description inside `<details><summary>model + effort</summary>`.
  • Have the PR-authoring agent write the opener itself under the rule "the shortest text that gets a human up to speed", so it can be reused without edits.
  • Put the model and effort in `<summary>` (your agent files already pin them) so a reviewer sees which agent produced the PR.

tinker-ai-skill turns your Claude Code sessions into a dataset and fine-tunes a local model on them via Tinker

drost-ai/tinker-ai-skill (MIT, created 7 Nov 2026) is a 9-step skill with 11 scripts. It takes transcripts from ~/.claude/projects/, copies them with checksums (skipping subagents, tiny sessions and private projects), normalizes them to OpenAI-style messages, strips harness noise, replaces credentials and assigns a random fake identity per session (one constant identity got memorized by the model). It then slices to context length with the model's real renderer without splitting a tool call from its result, adds a compacted-context block on continuation slices, holds out whole sessions, trains a LoRA on Tinker, compares base vs checkpoints, merges, and builds a BF16 GGUF for llama.cpp. The author, Migel Tissera, used this for Tess-4-27B and Tess-4.5-27B. November 2026 prices: 1,000 rows (~45M tokens) cost ~$55 on Qwen3.6-35B-A3B and ~$185 on Qwen3.8-27B. Lessons: put the system prompt and tool definitions in every row or tool use regresses; judge by behaviour, not loss (two "collapses" happened while loss fell); serve with the same flags used in training.

This is a new branch for you: you have many sessions and local MLX models, but no fine-tuning on your own sessions. Claude Code deletes sessions after 30 days by default. First step: set `cleanupPeriodDays: 3650` in ~/.claude/settings.json, clone the repo into ~/.claude/skills/tinker-ai-skill, and run the five-minute dry run on synthetic data (`make_sample_transcript.py`, then `train_tinker.py` without `--train`, which is an offline smoke test).

Take for your setup
  • Set `cleanupPeriodDays: 3650` in ~/.claude/settings.json so sessions aren't deleted after 30 days and the dataset material keeps accumulating.
  • Clone the skill into ~/.claude/skills/tinker-ai-skill and run the free offline dry run on synthetic data (no `--train`) to see a row's format and token count.
  • Borrow their scrubbing scheme: credential replacement, a random identity per session, and failing on any leak; useful for any export of our transcripts, e.g. for the observability skill.
  • Adopt their evaluation rule: compare checkpoints and local models by behaviour on held-out sessions, not by loss.

Scott Hanselman released sandbox-mcp: disposable Windows 11 guests from Windows Sandbox for agents, via the sbx CLI and an MCP server

sandbox-mcp (repo created 2026-11-06, release v1.2.0) runs Windows apps in a disposable Windows 11 guest using Windows Sandbox. It ships a `sbx` CLI and an optional MCP server named `windows-sandbox`, both on one engine. Each run boots a fresh guest, installs or launches the app, captures evidence (screenshots, recordings, errors) and destroys the guest. Results go to `%LOCALAPPDATA%\sandbox-mcp\runs\<timestamp>`.

MCP tools include `sandbox_run`, `sandbox_exec`, `sandbox_deploy`, `sandbox_screenshot`, `sandbox_ui_tree`, `sandbox_ui_action` (clicks and typing via UI Automation), `sandbox_install_test`, `sandbox_detonate` (untrusted file, network `off|firewall|on`), `sandbox_snapshot` and `sandbox_diff`. The CLI takes `--json` everywhere. Limits: needs Windows 11 24H2+ Pro/Enterprise/Education, only one Sandbox at a time, a logged-in host session, no Store, winget or Terminal in the guest, snapshots take 10–20 seconds. The author warns that output should be treated as untrusted and that Sandbox is not an escape guarantee. The README has no Claude Code section; it gives configs for VS Code, Copilot CLI and Claude Desktop.

This matters for you only if you test Windows apps: you are on a Mac, so you would need a separate Windows machine. The idea travels, though: an agent checks what it built in a clean environment and sees the result through screenshots and the UI tree. First step on Windows: `git clone https://github.com/shanselman/sandbox-mcp`, `npm ci --omit=dev`, `npm link`, then `sbx doctor` and `sbx run C:\Windows\System32\charmap.exe --open`.

Take for your setup
  • If you get a Windows machine: add the `windows-sandbox` MCP (`node ...\src\server.js`) to Claude Code and run `sandbox_install_test` on your own installer.
  • Borrow the pattern of a clean environment per run + `--json` + artifacts in a per-timestamp folder for your own scripts where an agent verifies what it built.
  • Add a rule to the quality-gates skill: treat sandbox output (especially from `detonate`) as untrusted, as the author advises.

cc-remote: Claude Code runs on a remote server while Read/Edit/Bash execute on your machine

cc-remote (AkaraChen, 338 stars, created 2026-11-01) is an ACP agent built on claude-agent-acp. The `claude` process runs on a server via `ssh -T`, with its built-in file and shell tools disabled. cc-remote supplies local replacements with the same names and inputs (Read, Write, Edit, NotebookEdit, Bash, Glob, Grep), plus local MCP servers from ~/.claude.json and .mcp.json. The model, login/subscription, system prompt, session, web search, subagents, skills and server settings stay on the server. Requirements: passwordless ssh, Claude Code 2.1.248+ on the server, Bun to build. Works with acpc, Zed, paseo.

Permissions: Read/Glob/Grep never prompt; Bash approvals cover a prefix (`npm test:*`), and commands with `;`, `&`, `|`, redirects or `$(…)` are never auto-approved. Limits: the project's `.claude/` (commands, skills, agents, settings) is not sent to the server, checkpoints/rewind can't see local edits, LSP, Monitor and worktree tools are disabled, MCP resources and prompts are unavailable. For you this is niche: useful if the model and subscription live on one machine and the code on another, but losing project skills, hooks and worktrees hurts your stack. First step: `git clone https://github.com/AkaraChen/cc-remote && cd cc-remote && bun install && bun run compile && bun link`, then `echo <server> > ~/.config/cc-remote/host && cc-remote doctor`.

Take for your setup
  • The Bash approval-by-prefix rule (`npm test:*`) with no auto-approve for `;`, `&`, `|`, redirects, `$(…)`: compare with our PreToolUse hook and add any missing cases?
  • The `cc-remote doctor` check (ssh plus remote claude version): build a similar preflight script for bot/RunPod sessions?
  • Try cc-remote on a test server, knowing the limits: project `.claude/` isn't sent and worktrees are off, so first check that the needed skills live in the server's ~/.claude?

Pack of four skills for one person who hands tasks to AI assistants and checks the results

solo-to-team-skills (author 大冰, v0.9-draft, 350 stars, created 7 Nov 2026) is not software but a set of methods packaged as four skills. dispatch-accept-verify: before handing out a task you write a "待收" (pending) registration line (who does it, who collects it, who checks), then record separately "accepted", "result received", "verified". A task leaves the open list only when verified or cancelled with human authorization. evidence-before-done: no "done" without evidence matching the current version (open the file, rerun a check, repeat the steps); adapted from obra/superpowers. beginner-ops-writing: step-by-step instructions for novices, one step at a time. ops-case-notes: sanitized real cases. Also included: templates/task-register-line.md and examples/walkthrough-meeting-notes/.\n\nThe author states the limits: hooks are empty (`hooks: {}`), there is no automatic dispatch or reminders, so you or the host must check tasks on schedule; there is no controlled experiment, so lower error rates are not proven. Install is documented for Codex and several Chinese hosts; a Claude Code structure exists but is not in the first release.\n\nMostly covered by what you have: task-context, feature-build, process ("don't claim done without verification") and subagents. The one new idea is a ledger of dispatched tasks with three separate statuses. First step: open templates/task-register-line.md and compare it with the context.md in task-context.

Take for your setup
  • Add to task-context a table of dispatched tasks with statuses accepted / result received / verified, closing a task only after verification
  • Add a "who verifies and how" field to each subagent task line before launch, not after
