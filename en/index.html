uncut: a minimal headless Go coding agent that never truncates files or command output

uncut (Balanov/uncut, MIT, v0.1.1) is a single static binary of about 7 MB, 837 lines of Go. No TUI, telemetry, plugins, background agents, automatic retries or context compaction. Four tools: read_file (whole UTF-8 file), write_file, replace (exactly one occurrence; zero or several is an error), run_command (exit code plus complete stdout+stderr). The entire history is sent to the model on every call. If a response is cut at the output limit, the agent exits with code 3 instead of passing the partial text off as an answer; binary files and invalid UTF-8 are rejected rather than silently byte-replaced. Exit codes: 0 success, 1 error, 2 bad usage, 3 length cut-off, 4 --max-steps reached (default 32). It works with any OpenAI-compatible Chat Completions endpoint (OpenRouter, Ollama; smoke-tested with qwen3:8b), non-streaming, no images. It is not a sandbox: commands run with your user's permissions. Flags: --json (NDJSON events), --session file.jsonl (append-only, resumable), --cwd, --no-agents, --request-timeout. The README gives no benchmark numbers (they are in BENCHMARKS.md, which I did not see); bench/proof.py tests transport only, not model quality.

For you this is not a Claude Code replacement but a reference for a deterministic headless layer for local models (MLX/Ollama) and pipelines like git diff | uncut "Review this diff". The useful ideas are hard exit codes on truncated output and on a step limit. First step: download uncut-darwin-arm64 from the v0.1.1 release, verify it against checksums.txt, then run UNCUT_BASE_URL=http://localhost:11434/v1 UNCUT_MODEL=qwen3:8b uncut "Explain this repository".

Take for your setup
  • Adopt uncut's rule that a truncated answer is an error: in our claude -p --json-schema scripts check stop_reason and fail with a distinct exit code instead of accepting partial output. Add it to the loop-design skill?
  • Add a step limit with its own exit code (like --max-steps → exit 4) to the loop-design skill for cron and fix-until-green agents?
  • Run uncut against a local model via Ollama or an OpenAI-compatible MLX server as a light agent for pipelines (git diff | uncut ...) and compare it with opencode?
  • Build a bench/proof.py-style check for our headless scripts: a deterministic fake provider that tests large files, cut-offs and session resume with no API key?

ai-design-check: 87 design rules and a zero-dependency checker for UIs built by AI agents

The repo enmerasoftware/ai-design-check (MIT, 178 stars, created 28 Oct 2026) is a set of 87 design rules for spotting what makes an interface look AI-generated, plus a zero-dependency checker on plain Node 20+ that needs no API key. It covers web (.tsx, .jsx, .vue, .svelte, .html, Blade, CSS, i18n JSON), SwiftUI and Jetpack Compose. 50 rules are checked automatically; 37 need review by a human or an agent. Rules are in English and Turkish and span accessibility, type, copy, components, layout, motion and localisation. Mobile checks include spacing off the 4 pt grid, radii off the scale, fixed text ignoring Dynamic Type, and tap targets under 44 pt / 48 dp. Class rules read only class strings (class/className/cn()/clsx()/cva()), so comments don't trigger them. An ignore without a reason after `--` doesn't count. Reported results: a dashboard went from 266 findings to 0, an iOS app from 23 to 0. Extra commands: inventory, narrow (320 px render check, needs Chrome), story (before/after video, needs Chrome and ffmpeg), system, --write-baseline.

You already have hooks, skills and a frontend skill, so what is new is the ready content: a rule set and a deterministic checker. The README's hook is a post-edit hook on `Edit|Write|MultiEdit` running `npx -y @enmera/ai-design-check hook`; clean files are silent, findings go to stderr with exit code 2, so the agent fixes them right away. The `ai-design-fix` skill is documented as never deleting content to lower the count. First step: run `npx @enmera/ai-design-check` in a UI project, then `npx @enmera/ai-design-check --write-baseline` to see only new findings.

Take for your setup
  • Add a hook to .claude/settings.json on Edit|Write|MultiEdit running `npx -y @enmera/ai-design-check hook` (exit 2 with findings on stderr) for UI projects, as one more gate in quality-gates?
  • Wire RULES.md (node_modules/@enmera/ai-design-check/RULES.md) or the `rules` list into the frontend skill as a checklist for generated UI?
  • Borrow the `ai-design-fix` pattern: the agent reports findings before/after and never deletes content to lower the count. Add that condition to our UI-fixing skills?
  • Run `narrow page.html --width 320` on a bot page or landing to check long text on a narrow screen?

stack-diagram skill draws an architecture diagram with official logos from a one-sentence stack description

caru-ini/stack-diagram is an agent skill (Claude Code, Codex, Cursor and others), created 1 Nov 2026, already 737 stars, MIT licensed. You describe your stack in a sentence or two (e.g. a Next.js and Hono app on Vercel with Neon, Clerk, Stripe and GitHub Actions), and the agent fetches logos, routes connector lines around labels, renders the diagram and checks it before returning it.

Logos come in order from svgl, devicon, gilbarbara/logos, or the brand's own repo; AWS icons come from AWS's own package. They are downloaded at build time, not bundled, and the scripts never recolor or redraw them. Outputs: a self-contained HTML file with fonts and logos inlined (default), PNG, a dependency-free React component, or a Claude Artifact; light and dark themes both work. Requires Python 3.9+ and network access; PNG export needs Playwright with Chromium. The agent may offer to post the diagram to the public gallery at stacks.caru.moe, only after two confirmations, and your prompt is not sent.

For your setup: you already have Artifacts and Remotion, but this covers a narrow job — quick architecture diagrams for READMEs, review-page or tickets without hand-made layout. First step: `npx skills add caru-ini/stack-diagram`, then ask for a diagram of your bot (Telegram + Claude Code + MCP) and inspect the HTML.

Take for your setup
  • Install with `npx skills add caru-ini/stack-diagram` and generate a diagram of the bot (Telegram + Claude Code + MCP servers) for manager/ or a README.
  • Hook the skill into review-page: embed an architecture diagram as self-contained HTML in plan-approval pages.
  • Borrow the 'render and verify before returning' pattern (checking label/line overlaps) into our skills that produce visual artifacts.

OmniDiff: a fast structural diff tool in Rust for git, with JSON output

OmniDiff (Rust, AGPL-3.0, v0.3.0, with a paid commercial license) is a content-aware difftool. Code in 25 languages is parsed with tree-sitter and compared as trees (APTED, falling back to Myers on degenerate trees), so a moved function shows up as a move rather than a deletion plus an insertion. Binary formats are diffed by meaning too: pictures pixel by pixel, archives file by file, fonts glyph by glyph, PDFs page by page. Speed on 2,302 code fixtures: p50 4.2 ms, p99 177 ms. Robustness: 99.95% of ~442k before/after pairs from ~7,500 repos completed. Failures are huge generated files (in the thread the author named a tree-sitter stack overflow). By the author's own numbers, difftastic is perfect on 64% of diffs and OmniDiff on 90%. Accuracy goals are not yet met: zero mismatched bytes in 60% of cases (--full) and 69.6% (--minimal). Three-way merge is unsolved. External PRs are not accepted.

For your setup the useful part is the non-TTY mode: --headless turns on automatically when stdout is not a terminal, and there are --mode json (JSON Schema in the repo) and --exit-code. Agents and hooks could get a structural diff instead of line-level noise. The project itself is built with Claude Code and has an AGENTS.md. First step: brew install ivankovic/omnidiff/omnidiff, then omnidiff git configure or GIT_EXTERNAL_DIFF=omnidiff git diff (output is plain text, no TUI).

Take for your setup
  • Try GIT_EXTERNAL_DIFF=omnidiff git diff on a large refactor with moved code and compare its size and readability for a reviewer subagent against plain git diff.
  • Check omnidiff --mode json on a real diff and decide whether to feed it into the code-review and vendor-review skills, so reviewers see function moves instead of delete/insert pairs.
  • Run omnidiff on changed images, PDFs and archives (Remotion frames, assets) as a content-level check of outputs instead of eyeballing them.
