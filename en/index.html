01GitHub30.10

Jim Manico released a /threat-model skill: the agent builds a repo threat model with file-and-line citations

grim-prompter (MIT, 185 stars, created 2026-10-28) is a set of prompts plus one skill, `threat-model`, for Claude Code and Codex CLI. The agent inspects a repo strictly read-only, writes only under `threat-model/`, and must cite a file and line for every finding. Anything the code doesn't show is recorded as a gap, not assumed. It ships 36 architectures (Web, API, Microservices, RAG, Agentic AI, OT/ICS, blockchain and more) in quick and deep variants, and 29 methods: STRIDE, PASTA, LINDDUN, STPA, MAESTRO, MITRE ATLAS, ATT&CK, CVSS, DREAD and others. A deep run has six stages (scope, system modeling, threat analysis, challenge, treatment planning, reporting), each reading the previous stage's file. Output is `SYSTEM_UNDER_REVIEW.md`, `report.md` and JSON artifacts. For MCP servers and agent tools it maps tools to backend credentials and permissions, and marks unknown grants as gaps. `change main...feature` compares a branch against a saved JSON baseline. Limits: the prompts are drafts; builds, tests and network need explicit authorization; a verification plan is not a passed test; reports can be sensitive, so keep them out of git.

You already have vendor review, `/code-review` and subagents, but no dedicated threat-model layer. It fits best on bots with MCP (Telegram, Google Workspace, RunPod) and for checking branches. First step: `git clone https://github.com/jmanico/grim-prompter.git ~/grim-prompter`, then `ln -s ~/grim-prompter/skills/threat-model ~/.claude/skills/threat-model`, start a new session and run `/threat-model quick agentic` in the bot repo (check the architecture name in `catalog.md`).

Take for your setup
  • Symlink the `threat-model` skill into `~/.claude/skills` and run `/threat-model quick` on the Telegram bot repo with its MCP access.
  • Borrow their runbook rule "unknown goes to a gap, not a guess" plus file:line citations for our review and research skills.
  • Add `threat-model/` to each project's `.gitignore`, since reports can contain sensitive details.
  • Run `/threat-model change main...feature` as a separate step before merging risky branches, keeping a JSON baseline.

02Simon Willison29.10

Spawn: a multiplayer game built by a swarm of Fable agents, shipping to production hourly

Jacob Sansbury described how Spawn works: a massively multiplayer game where players change the world with prompts and talk to an in-game AI, Savi, that helps build games. He says development is run almost autonomously by a swarm of agents on the Fable model. Token spend is above $3M a month, "30x payroll". Agents edit live code and ship to production hourly, reading errors, bug reports and metrics themselves. About 60% of work starts from a production error, a Savi bug report, an odd log entry or a feature request. Savi files bugs herself; an agent triages each as a real bug, a wontfix, or intentional design needing a decision. Most become fixes within an hour.

Rules: an hour without a ship is a SEV-0, because an agent holds only a few hours of work in context and frequent shipping keeps it coherent. A broken change rolls back in 30 seconds, targeting only that change. Monitors and log alerts start or wake an agent that owns the incident. The team deliberately breaks things to test recovery paths. On models: Opus 5.5 reportedly didn't meet their needs, and GPT-6 Astra, applying security fixes, disabled features and the product stopped working. Simon Willison doubts this fits higher-stakes software.

For your setup this is a pattern for closing the loop: a production error starts an agent on its own. First step: on one small project, wire an alert or log monitor to launch `claude -p` for triage (bug, wontfix, needs a decision) and per-change rollback.

Take for your setup
  • A triage agent for incoming errors: classify as bug / wontfix / needs a human decision. Add this as a skill to the alert scripts built on `claude -p --json-schema`?
  • Roll back one change, not the whole release: each agent fix as its own commit with a seconds-fast revert command. Add this rule to CLAUDE.md?
  • A rule against fixing by disabling: GPT-6 Astra turned features off for security. Add to review-agent briefs a ban on disabling functionality, plus a check that features still work?
  • A log monitor that wakes an incident-owner agent, via `/schedule` or a hook. Try it on one project?

03GitHub30.10

Kensaku: a local file and screenshot search tool with OCR and MCP access for agents

Kensaku (yjid/kensaku, MIT, Rust + Tauri + Bun) is a free local search launcher. It searches file names (the author reports about 1.3 ms across 100k files on Linux), text inside PDF, DOCX, PPTX, XLSX, EPUB, ODT, RTF, code and logs, including CJK, and text in images through OCR. OCR defaults to PP-OCRv6, with an optional Indra engine (about 27 MB, downloaded on demand) and Tesseract as a fallback; Intel Macs use Tesseract only. It also has search by meaning, typo tolerance, natural-language dates like "last week", and a query language (`type:`, `ext:`, `size:`, `content:`, `re:`). Indexing is incremental, with no cloud and no telemetry. It runs on Windows, macOS and Linux. Builds are unsigned, the auto-updater is not wired up, and Windows has the most testing. The README does not name the embedding model or list the MCP tools by name. The repo is a week old (created 2026-10-24) and has 241 stars.

For agents: `kensaku-cli mcp` runs as an MCP server, and `kensaku-cli serve` offers HTTP on loopback with a bearer token. Access is read-only by default, and `reindex` must be enabled explicitly. For you this gives Claude Code search over screenshots, PDFs and office documents on disk, which codebase-memory does not cover because it works on the code graph. The project is young, so check which tools it exposes first. First step: download a release, index a folder of screenshots and documents, run `kensaku-cli search --json <query>`, then add an `mcpServers` entry with the command `kensaku-cli mcp`.

Take for your setup
  • Add `kensaku-cli mcp` under `mcpServers` and check which tools it exposes: none of your current MCP servers covers search over screenshots, PDFs and DOCX on disk.
  • Use `kensaku-cli search --json` in scripts that call `claude -p --json-schema`, as a cheap local document lookup before launching an agent.
  • Keep the default read-only access and leave `reindex` off until you have checked the server's behavior. If you need HTTP, run only `kensaku-cli serve` on loopback and keep the token in Keychain through the secrets skill.

04Pydantic releases29.10

Pydantic 2.14 drops Python 3.9, adds 3.15, fixes two vulnerabilities

Pydantic 2.14.0 came out on 8 October 2026. It drops Python 3.9 and adds 3.15. Two vulnerabilities are fixed: GHSA-gj4f-r7mf-jjxh (Fraction validation accepted huge exponents) and GHSA-955g-x97g-8mcp (the URL prefix was re-validated in multi-host URLs).

New: multiple_of for the fraction and timedelta schemas, a __namespace__ parameter in create_model(), and the ordered-dict and counter core schemas. Changes that may affect your code: NameEmail now rejects newlines; multiple_of must be positive; enum constructors are called in both validation modes; ser_json_timedelta no longer applies to all datetime types in serialization inference; model_config is no longer mutated. The rest are fixes: OverflowError in ByteSize, OS errors in ZoneInfo, exceptions in Decimal, and JSON Schema for stdlib dataclasses and TypedDict (config, init, kw_only, extra). The maintainers say some changes count as non-breaking under their versioning policy, but you should read them before upgrading.

You already use Pydantic (FastAPI, SQLModel), so this is a normal upgrade, and the points above are what is new. If you accept Fraction, multi-host URLs or named emails from clients, the upgrade closes those holes. If your schemas and OpenAPI come from dataclasses or TypedDicts, the output may shift slightly. First step: bump pydantic to 2.14.0 on a branch, run pytest, and diff openapi.json before and after. If any service is still on Python 3.9, upgrade the interpreter first.

Take for your setup
  • Bump pydantic to 2.14.0 on a branch and diff openapi.json before and after: JSON Schema for dataclasses and TypedDicts changed.
  • Grep for Fraction, multi-host URLs and NameEmail on API inputs, where the vulnerabilities were fixed, and add tests with odd values.
  • Check which services and CI images are still on Python 3.9 and plan a move to 3.10+ or newer.
  • Find uses of ser_json_timedelta and multiple_of in your models: their behaviour changed.
