Claude Code team explains how it verifies code that Claude writes about 90% of

Addy Osmani (claude.dev, Nov 16, 2026) describes how the Claude Code team verifies agent work: about 90% of their code is written and reviewed by Claude. The idea: without verification loops you can run 1–2 agents; with them, dozens or hundreds. A separate grader checking work against a rubric gave up to +10 points of task success on structured file generation.

Specifics. Three test types: E2E (give the agent "hands and eyes" via a `verify` skill in `.claude/skills/`, CDP, simulators), property tests (fast-check, Hypothesis, proptest: round-trip, invariants, idempotency, equivalence) and differential tests (old system as oracle, a list of approved differences). A 39-item reliability checklist with diff-readable triggers: 3–10 matching items run per change. REVIEW.md is read from the base branch, not the PR, so a change can't edit its own checker. After three failed rounds Claude escalates to a human. The commit gate has off/observe/enforce modes; after two blocks in a session the next commit passes. Rules from misses: a pattern in ≥2 PRs that three agents fail to disprove; or replay: three bug finders, if ≥2 find the bug it is detectable. Flaky tests may not be retried or masked with sleeps. HN pushback is about cost: cheap deterministic checks (linters, Playwright) should come first.

For your setup: skills, hooks, review and /loop are already there; what's new is the discipline around them. First step: have a Stop hook stamp how each commit was verified, and run a commit gate in observe mode that only logs what it would have blocked.

Take for your setup
  • Commit gate in observe mode: a hook logs commits made without /code-review or /verify, switch to enforce after checking false positives. Set it up?
  • Read review rules (REVIEW.md, gates) from the base branch, not from the change, so a PR can't edit its own checker, in our cross-vendor review and quality-gates skills.
  • CLAUDE.md rule: never retry or mask flaky tests with sleeps; if root cause isn't found, delete the test and record why. Plus a cap: three failed check rounds, stop and call a human.
  • A per-project `verify` skill that boots the app and runs a scenario, plus property tests (Hypothesis) for parsers and migrations. Start with one project?

02GitHub18.11

rust-anything: incremental Rust rewrite of an app, verified against the original's recorded behavior

rust-anything (GitHub, created 2026-11-16) is a CLI plus MCP server that walks a coding agent through rewriting code in Rust one piece at a time. It covers CLIs, HTTP servers and libraries in TypeScript/JS, Python, C, Go, Ruby and Java (PHP and C# in preview). Steps: `profile` finds hot code under a real workload, `analyze` lists units, order and risks, `bridge` generates a Rust crate with a wrapper so callers keep the original API, `record` runs the original on generated edge cases and saves outputs. The agent or a human writes the Rust in `port.rs`; `diff` replays every recording against it, `bench` measures speed, and `gate` demands fmt, clippy, tests, an unsafe audit and error-path coverage. For whole apps: `app record`/`app replay`, a Rust "front door" forwards unported commands to the original, and `app lift` removes the original at the end. Claimed up to 20x on hot paths and 38,251 cases replayed with 0 mismatches; examples: x18n search over 50,000 keys 20x, Python slugify 17x, Go 4x, Java 3x. Per-call ports are often slower than a JIT: 29 x18n functions came out slower than TS, so batching is needed.

Limits: passing means matching recorded cases only; regex engines differ, float formatting must match exactly, and timing, memory, concurrency and side effects are not compared. It doesn't rewrite code automatically. For you it is a ready pattern of an agentic migration with an oracle: record the original's behavior, replay as the done criterion, which fits your loop-design and quality-gates skills. First step: `cargo install rust-anything && rust-anything setup` (registers the MCP server and skill in Claude Code, Codex, Gemini CLI), then run `rust-anything profile` on a small script.

Take for your setup
  • Add the "record the original's behavior, replay as the done criterion" pattern to loop-design/quality-gates for any refactor or migration, not just Rust
  • Borrow the "front door" idea: new code sits in front of the old and forwards what isn't ported, and `app lift` removes the old at the end; package it as a skill for gradual rewrites
  • Run `rust-anything setup` and try it on one hot script from the bots (`profile` then `analyze`), porting in batches rather than per function

03Simon Willison17.11

Simon Willison and Prime Radiant release three external sandboxes for code that agents execute

Simon Willison worked with Prime Radiant on an "external sandbox" pattern: the agent runs outside, and all code it executes is sent to a separate sandbox over a localhost API. The goal is to make local models safer to try, so a mistake or prompt injection can't damage the machine. There are three implementations with the same API: external-sandbox-v86 (Node.js, Alpine Linux in WebAssembly via v86), external-sandbox-container (Python, Alpine in Apple Containers) and external-sandbox-quicksand (Python, Microsoft's Quicksand library bundling QEMU and Alpine). All are under github.com/prime-radiant-inc. Pi, Claude Code or Codex are configured to send code-execution calls to the sandbox.

There is an optional HTTP/HTTPS allow-list proxy limiting which hosts the agent's code can reach. A credential replacement mechanism lets authenticated API calls work without giving the secret to the agent. A web UI changes the proxy policy while the sandbox runs: allowed destinations, a policy JSON editor and recent proxy activity. The page gives no performance numbers or setup commands; details are in the Prime Radiant post.

This matters for you because you run local models on MLX and agents through a Telegram bot. First step: clone external-sandbox-container (you are on macOS) and read its README on how to route Claude Code's command execution into it.

Take for your setup
  • Clone external-sandbox-container and test routing Claude Code's Bash calls into it for the Telegram bot session
  • Borrow the allow-list proxy idea: let the agent reach only needed hosts, with rules editable at runtime
  • Borrow credential replacement: keep secrets from the secrets skill out of the agent's context by injecting them outside the sandbox

04GitHub18.11

antialgorithm skill makes Claude name its first, most average pick and move away from it

mankidev/antialgorithm is a Claude Code skill for creative work: names, copy, stories, game ideas, posters, UI. The idea: the model first names its first, most average pick, then moves away from it for a reason taken from the project. Created 2026-11-14, 286 stars, 9 commits, MIT.

It ships three scripts. seed.py rolls a random starting point when the request is thin: for visuals method, colors, layout, type; for text voice and register; for ideas a verb, constraint, scale, pressure (system randomness, so identical prompts start in different places). rough.py gives SVGs a hand-made look by shaking lines and letters and breaking even spacing; only for print, paint, stamp, ink styles. check.py renders an SVG at full and icon size and flags text off the edge, under a shape, low contrast, too small. Needs Python 3, and for check.py numpy, Pillow and rsvg-convert or cairosvg. No benchmarks; in the showcase the bottom row of posters was picked from about a dozen runs, so it is not a typical result. The full technique is in SKILL.md, which the page did not show.

For you it is relevant to the frontend and image-create skills, where the model also drifts to the average. The seed.py idea (a random seed instead of the same first thought) ports easily into your own skills. First step: git clone https://github.com/mankidev/antialgorithm ~/.claude/skills/antialgorithm and run the same 400x600 SVG poster prompt with and without the skill.

Take for your setup
  • Add a random seed in the spirit of seed.py (method, palette, layout, type) to the frontend skill so landing pages stop converging to one look?
  • Wire check.py (SVG render at full and icon size, contrast, text off the edge) in as an automatic check for SVG artifacts and posters?
  • In image-create and human-writing, require naming the first average pick and moving away from it for a project-based reason?

05Hacker News17.11

Microsoft ships MAI Code 2 and Code 2 Flash coding models, 50% promo price in Copilot

Microsoft AI announced two in-house coding models. MAI Code 2 targets everyday enterprise work: deep debugging, multi-file implementation, repo-wide reasoning, UI. MAI Code 2 Flash targets high-volume work: code explanations, targeted edits, routine fixes. There is also MAI Work Flash for Microsoft 365 and Fabric IQ.

Microsoft's own numbers (average of DeepSWE 1.1, Terminal Bench 2.1, SWE-Atlas, FrontierCode v1.1, max reasoning effort, GitHub Copilot CLI, no subagents): Code 2 reaches 98% of GPT 6.1 Sol at 40% of the cost, and 96% of Claude Opus 5.5 at 5% of the cost. Flash is comparable to GPT-6 Luna and Claude Haiku 5.5 at 65% and 20% of their cost. No absolute prices, no context window stated. Available in GitHub Copilot (50% promo price now); Flash is in limited Foundry preview; OpenRouter, Vercel, Hermes, Open Code and Kilo are promised soon. Weights are closed. Microsoft itself says the models are not yet tuned for harder problems or very long-horizon agentic work.

HN skeptics point to comparison against max-effort versions, uncontrolled harnesses, and one table placing it behind Qwen and DeepSeek. One Copilot user said they felt no difference from Opus on Python build issues and Azure Bicep. Another team cancelled Copilot over credit limits.

For you: nothing urgent, Opus 5.5 stays primary. It is a candidate cheap executor or extra opinion for vendor-review once it lands in opencode or OpenRouter. First step: when it appears in Open Code, run one routine task of yours and compare cost and result against Sonnet 5.5.

Take for your setup
  • Add MAI Code 2 to the vendor-review skill as another reviewer once it shows up in opencode/OpenRouter.
  • Run an A/B on one routine task: Code 2 Flash vs Haiku 5.5 on cost and quality before changing the model pinned in the low/medium agent files.

06uv releases17.11

uv 0.13.9: smaller lockfile, `uv lock --locked` fix, rejects wheels served under a different package name

uv 0.13.9 was released on 2026-11-17. Performance: the lockfile is smaller and reads faster because repeated conditions in environment markers are factored out (#23184). Fixes: `uv lock --locked` no longer rejects a lockfile that contains equivalent platform markers written in different forms (#23185); marker values containing apostrophes are now quoted correctly (#23185); uv rejects wheels that an index advertises under a different package name (#23261); when musl interpreter detection fails, uv reports which interpreter did not return a readable version (#23213). Preview features: PEP 832 `.venv` redirect file support for project environments (#21822), and `http2-keep-alive`, which closes unresponsive HTTP/2 connections that have active requests (#23236). The minimum Rust version for building uv is now 1.98 (#23263).

For your FastAPI/Celery projects this is mostly a routine tool update: `uv lock --locked` in CI should fail less often on false marker mismatches, and the lockfile diff after a re-lock may be large (fewer repeated conditions), which is expected. The wheel-name check is a small supply-chain safeguard if you use a private index. First step: `uv self update`, then run `uv lock` in one project and review the diff; if downloads hang over HTTP/2, try the `http2-keep-alive` preview feature.

Take for your setup
  • Update uv (`uv self update`) and run `uv lock --locked` in one service's CI to confirm the false marker-related failures are gone
  • Commit the re-generated lockfile as a separate commit so the marker-factoring diff doesn't mix with real dependency changes
  • If CI builds sometimes hang while downloading packages, enable the `http2-keep-alive` preview feature on one pipeline
