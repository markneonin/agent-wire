Theo (t3dotgg) published tstack: skills that take a PR from change to merge unattended

tstack is a t3dotgg repo (MIT, created 2026-10-24, ~1.7k stars, 3 commits) of skills the author uses daily; it works with Claude Code and Codex. The main skill, `full-send` (trigger "full send"), takes a change to a merged PR: it proves the change works, reviews it, files the PR, monitors it and merges. `full-stop` does the same but stops when the PR is ready for you to merge. The chain underneath: `sol-loop` (reviews with GPT Sol in a loop until both agents agree), `file-pr` (short PR that leads with the problem), `babysit-pr` (watches CI and review bots and fixes real findings, using a python3 `pr-wait` script). Also: `takeover` (finish someone else's PR, branch or agent thread while keeping their credit), `modernize` (rebases an old PR and decides whether it should still exist), `leaving-pr-comments` (formats comments posted on your behalf). Its `council` gets review from three models from different providers and loops until they agree.

You already have council, so what is new is the whole PR pipeline: babysit, takeover, modernize. You have feature-kickoff and feature-build, but nothing in your list is an autonomous loop through CI and review bots to merge. It needs an authenticated `gh` and python3. First step: clone the repo and copy the contents of `skills` into `~/.claude/skills/`, starting with `babysit-pr`. The author suggests keeping personal settings (which models sit on the council) in CLAUDE.md so updates don't overwrite them.

Take for your setup
  • Copy `babysit-pr` (with its `pr-wait` script) into `~/.claude/skills/` and try it on one PR: it watches CI and bots and fixes real findings - we have no loop like that through to merge
  • Add a final step to feature-kickoff in the spirit of `full-stop`: drive the PR to ready-to-merge and stop
  • Borrow the `takeover`/`modernize` idea: a skill for finishing an old branch or PR that first decides whether it should still exist and keeps the original author's credit
  • Borrow the `file-pr` idea: a CLAUDE.md rule that PR descriptions are short and lead with the problem

02GitHub27.10

pitupitu: an open-source Rust agent that lets you start and unblock Claude Code and Codex by voice from your phone, on your own machines

pitupitu (klarluft, Apache 2.0, 212 stars, repo created 17 Oct 2026) is a "box agent": a process on each of your machines (macOS or Linux) that acts as the client for the hosted pitupitu.chat service. You talk by voice from a phone or browser to start, check, or unblock Claude Code and Codex sessions. The cloud handles voice and conversation (the README doesn't describe the pipeline, only says "audio is never stored"). The agent dials out over a WebSocket to wss://api.pitupitu.chat/v1/box, so there are no open ports, VPN, or certificates. Sessions run in herdr, a terminal workspace manager for coding agents; the herdr server survives agent restarts, and opening herdr locally shows the same sessions. Your own unmodified claude and codex stay signed in by you; pitupitu never reads their credentials or adds permission flags. The cloud may only request a fixed set of operations: list/open/close workspaces and tabs, start an agent in a pane, send prompts or keys, read a screen, wait, update. No shell, no arbitrary commands. Logs hold metadata only; history is on by default (7 days, newest 300 sessions, prompts cut to 1000 chars, answers to 600).

For you this is not a replacement for the Telegram bot with Claude Code but a second channel: voice and several machines at once, through a third-party cloud (only the client is open source). Downsides: you must trust pitupitu.chat, and the chain depends on herdr. First step: on a test machine run `brew install klarluft/tap/pitupitu`, then `pitupitu setup` (code or QR sign-in, installs herdr, starts a launchd service) and `pitupitu status`. Read docs/box-link.md first for the allowed operations list.

Take for your setup
  • Install pitupitu on one test machine (`pitupitu setup`, `pitupitu status`) and compare the voice channel with our Telegram bot for Claude Code?
  • Read docs/box-link.md and calls.rs: a fixed operation list with no shell is a model for limiting what our bot and skills can do. Adopt the pattern?
  • Try herdr as a manager for long-lived Claude Code/Codex sessions that survive restarts, instead of hand-managed terminals?
  • Copy their pattern of outbound-only connection with a per-machine key for remote access to our agents?

Simon Willison evaluated webframe, which runs a web page like a program: fine as a scraper, rough as a sandbox

webframe is a small Go tool by Jeff Lindsay, built on the glaze library. You point it at a URL or local file, it runs the page in a hidden headless web view, sends console.log() to stdout and exceptions to stderr. It bundles no browser: glaze uses the system engine (WKWebView on macOS, WebKitGTK on Linux, WebView2 on Windows). Simon Willison compares it to his shot-scraper: much smaller and with no Playwright dependency.

He had Claude Opus 5.5 explore and run webframe, build prototypes and write a report on two uses: as a sandbox, and as a scraper using the patterns of shot-scraper's javascript command. Verdict: fast and lightweight, suitable for scraping, performance comparable to shot-scraper. Rough edges: CSP failures, a 0×0 viewport, hanging page loads, missing HTTP metadata, limited browser controls. The page gives no timings and no security details; those are in the report.

For your setup it is a light alternative to Playwright/Chrome for scripts that just run JS on a page and capture the output. I would not use it to isolate agent code without reading the report first. First step: look at github.com/tractordev/webframe and the report at github.com/simonw/research/tree/main/webframe-evaluation, starting with the sandbox section.

Take for your setup
  • Read the sandbox section of simonw/research/webframe-evaluation before considering webframe as isolation for agent code
  • Try webframe instead of Playwright in a simple scraping script (URL → JS → console.log to stdout) and compare it with the current setup on CSP failures and hanging page loads
