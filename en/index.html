01Claude Code releases12.11

Claude Code 2.1.323: experimental Code Mode (Claude writes JavaScript to call tools), plugin engines field, tighter Bash permissions

Released 12 November, 262 items. The main new thing is Code Mode, an experimental opt-in where Claude writes JavaScript that calls its tools instead of making individual tool calls. Enabling it, and disabling it for an organization, is described at code.claude.com/docs/en/code-mode. I could not open that page (404), so I don't know how execution works, what the limits are, or which setting turns it on.

Also: plugin.json gets engines["claude-code"]; plugins outside the stated version range are not installed, updated or loaded. `claude plugin validate` now type-checks a plugin's TypeScript hooks module (warnings, failing under --strict). New CLAUDE_CODE_DISABLE_AGENT_PROGRESS_SUMMARIES=1 and a 30-second heartbeat while hooks run long in `claude -p`. The cap on messages your own sessions can send each other rose from ~20 to 100,000. An unrecognized model ID now assumes a 1M window instead of 200K (CLAUDE_CODE_DISABLE_1M_CONTEXT=1 keeps 200K). Many Bash permission fixes: `Bash(NODE_ENV*)` now prompts, deny/ask rules catch commands via sudo/env, the sandbox makes `git worktree add/move/remove` read-only, and `claude -p` stops at startup if a --settings file with a sandbox key is invalid rather than running unsandboxed. For you: Code Mode is closest to your Workflow tool but a different mechanism (code calling tools inside one session). First step: read the Code Mode docs once the page is reachable, and check your Bash allow rules that have `*` in a variable value (there is now a startup warning).

Take for your setup
  • Audit your Bash allow rules for `*` inside a variable value and attached wildcards like `Bash(ls*)`: they now prompt or warn at startup
  • For scripts using `claude -p` with --settings and sandbox: make sure the JSON is valid, since startup now stops otherwise
  • Add engines["claude-code"] to plugin.json in your own plugins (plannotator, runpod, etc.) and run `claude plugin validate --strict`
  • If subagents in Workflows add noise or extra requests, try CLAUDE_CODE_DISABLE_AGENT_PROGRESS_SUMMARIES=1 to turn off progress summaries

02GitHub13.11

cook: a skill for long visual builds where the agent iterates until output matches reference images or video

Leonxlnx/cook (268 stars, created 2026-10-31, MIT) is a skill for tasks where output must match reference images or video: 3D worlds in three.js, films, games, UI. You give targets, a bar and time. The agent asks all its questions once, each with a default, then runs unattended, even overnight. The loop: every reference becomes a shot (video is analyzed frame by frame), and each dimension (composition, light, color, materials, detail, motion) gets a numeric bar, e.g. 99.9% for stills and at least 9/10 for video. It renders stills at the same shots, puts them side by side with the references, has zero-context critics score them, fixes the weakest area and logs the round in cook/ROUNDS.md. Your own estimate of the result calibrates the critics' scores, since models rate themselves too high. Demos have an 8-hour minimum (finishing in 2h "means something is wrong") and usage pacing against plan limits. Stills go to you after each round without pausing, and the final render waits for approval. Example: Athenaion took about 45 hours, 55 subagents (up to 12 in parallel), ~45k lines of JS, ~11M tokens, 4K on an integrated Radeon 780M.

Overlap with your setup: Workflow, subagents, /loop, loop-design and task-context already cover orchestration and state. New for you: zero-context critics with score calibration against your own estimate, side-by-side reference comparison, and a hard time floor against early stopping. First step: npx skills add Leonxlnx/cook, then /cook build this ... match the 9 attached references. The comparison script needs Node 18+ and ffmpeg: node scripts/side-by-side.mjs --out compare.jpg ref1.png render1.png.

Take for your setup
  • Zero-context critics with calibration against your own estimate: add a rule to loop-design that the agent's self-score is checked against your reference score.
  • Take scripts/side-by-side.mjs (reference left, render right) into the Remotion pipeline and the montage skill for frame checks.
  • Minimum run time plus a cook/ROUNDS.md ledger: borrow it as a guard against premature stopping in long /loop and /schedule jobs.
  • Stills-only gate: send screenshots after every round without pausing and do the final render only after approval; add to the frontend skill for visual tasks.

03Hacker News12.11

Google ships Gemini 4 Hydrogen in Antigravity plus Orchestrator, which switches between Carbon and Hydrogen within one task

Google (Antigravity blog, 12 Nov 2026) is rolling out Gemini 4 Hydrogen, a model for everyday agentic coding. It scores 51 on the Artificial Analysis Intelligence Index (Argon 50, 54 at its highest setting) and 57% on Terminal-Bench 4.1 versus 18.2% for 3.8 Flash. It has four reasoning levels: low, medium, high (default) and a new xhigh.

Orchestrator is a new model-dropdown option. Within a single task it switches between Gemini 4 Carbon and Hydrogen: Carbon does read-only exploration and planning, Hydrogen does edits, package updates and tests. If Hydrogen hits friction, the task goes back to Carbon to repair the plan. On Terminal-Bench 4.1 it gets near-Carbon success with on average 24% less quota and 19% faster. Earlier that week Google shipped Carbon and the /swarm command (parallel agent teams across worktrees). The Antigravity SDK lets you wire the pair together in code; the demo is an open-source issue triage system where Hydrogen triages and codes, and Carbon handles larger refactors and security checks. Access: Hydrogen for Google AI Pro and Ultra, Orchestrator (Carbon) for Ultra only, Orchestrator (Argon) for Pro and Ultra. The article gives no prices or quota limits. On HN: commenters note Anthropic's advisor mode and GitHub's multi-model pipeline do the same; Antigravity gets criticised for burning Pro quota fast; one person reported 60% savings with Opus delegating to cheaper DeepSeek models.

The idea is not new for you: you have per-model, per-effort subagents, task-lead, a /swarm-like Workflow, and the use-antigravity skill for agy -p. What is new is the pattern: strong model reads and plans, cheap model edits, failure returns to the planner. First step: check that your executor agent (medium or low) hands a failing-tests task back to the lead instead of patching it itself.

Take for your setup
  • Add an escalation rule to the subagents skill: when an executor (low/medium) fails tests repeatedly, it returns the task to the lead for re-planning instead of patching blindly.
  • Split permissions by phase like Orchestrator does: the exploration/planning agent is read-only, a separate agent does edits and tests. Pin this in the agent files.
  • Measure quota and time savings in your own Workflows for a strong-planner plus cheap-executor pair versus one strong model, as Google did on Terminal-Bench (-24% quota, -19% time).

antiglaude: a local gateway that points Claude Code at Google Antigravity models through a risky workaround

antiglaude (168 stars, created 2026-11-03, MIT, on PyPI, Python 3.10+) is a local proxy on 127.0.0.1:8080. It accepts Claude Code requests (POST /v1/messages, Anthropic Messages API) and OpenAI-compatible clients (/v1/chat/completions), translates them into Google Cloud Code/Antigravity calls and converts the replies back. Models: claude-sonnet-4-6 (default), claude-opus-4-6-thinking, gemini-3-flash, gemini-2.5-pro; an unknown model name falls back to the strongest active one while the response echoes the requested name. Internals: it strips JSON Schema keywords (propertyNames, anyOf, const) that cause HTTP 400 on tool calls; auto-renews the roughly 60-minute access token using refresh credentials pulled from local app state; sends SSE heartbeats against dropped connections; backs off on rate limits; ships a TUI with a quota meter, routing matrix and request journal; and a macOS LaunchAgent. Downsides per the README: no real authentication (any local process can hit the gateway), "identity scrubbing" to dodge upstream filters, muddled model labels (sonnet-4-6 listed as Claude 3.7), and the 1,500 requests/day limit appears only in a dashboard example. The author warns that Google bans accounts using unofficial proxies and recommends a throwaway account.

For you this is mostly curiosity: you run Opus 5.5 and Sonnet 5.5 directly, and already use agy -p for Google AI Pro work through the official path. The reusable ideas are overriding ANTHROPIC_BASE_URL with CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1 to populate the /model picker, and schema normalization for a foreign backend. If you try it, use a burner account only: uvx antiglaude start, then antiglaude setup-claude (it rewrites ~/.claude/settings.json, so back that file up first).

Take for your setup
  • Check that ANTHROPIC_BASE_URL + CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1 populate /model with foreign models, and note it in the use-antigravity skill as a possible gateway route.
  • If you try it: back up ~/.claude/settings.json first, run uvx antiglaude start on a separate account, and verify with make status.

05ruff releases12.11

Ruff 0.17.5: new ASYNC401 rule, B008 ignores frozen dataclasses, several autofix bugs fixed

Ruff 0.17.5 was released on 12 November 2026. Stable changes: B008 (function call in argument default) now ignores frozen dataclass instantiation, removing false positives. Autofixes were repaired for B010 (parenthesized setattr), PYI034, UP031 (it duplicated a closing parenthesis), ICN001 (name shadowing when fixing import aliases), and for fixes that add or remove a keyword argument with a parenthesized value. Ruff no longer crashes when logging to a closed stderr pipe. There are also 18 performance PRs.

In preview: ASYNC401 (pytest-raises-exception-group), PLE0211 (no-method-argument), RUF202 (renamed-rule), and RUF101 now covers other suppression comments. The G004 fix (f-strings in logging) is now marked unsafe, and FURB103 no longer offers a fix when write is nested in an expression. For a FastAPI/Pydantic stack the most visible change is B008: if your argument defaults use frozen dataclasses, those warnings go away. ASYNC401 helps with asyncio tests that use ExceptionGroup under pytest. First step: upgrade (`pip install -U ruff` or `uv tool upgrade ruff`; installer script: `curl --proto '=https' --tlsv1.2 -LsSf https://releases.astral.sh/github/ruff/releases/download/0.17.5/ruff-installer.sh | sh`), run `ruff check` and see what changed for B008. To try the previews: `ruff check --preview --select ASYNC401,PLE0211`.

Take for your setup
  • Run `ruff check --preview --select ASYNC401,PLE0211` over asyncio tests and classes to evaluate the new rules before enabling them in config
  • Remove B008 `per-file-ignores`/`noqa` entries that existed only because of frozen dataclasses in defaults, and check they're no longer needed
  • If CI runs `--fix` with G004, don't rely on the autofix: it is now unsafe and needs `--unsafe-fixes`
