Chrome, Edge, Firefox and MDN ship Modern Web Guidance 1.0: a skill and CLI that steer coding agents to native web APIs

Modern Web Guidance (GoogleChrome/modern-web-guidance, Apache-2.0) is a set of 203 real-world use-case guides covering 250 web features (CSS 140, HTML/DOM 36, JS/APIs 74), shipped as a skill (markdown files in skills/modern-web-guidance/guides/) plus a CLI. The premise: models trained on legacy code know an API exists but still write old patterns. Guides on Popover API, view transitions, anchor positioning, container queries, scheduler.yield and similar are pulled into context. Commands: `npx modern-web-guidance@latest install | search "..." | retrieve "<id>" | legacy-scan .`. Plugin manifests exist for Claude, Codex, Cursor, Gemini and others. From the HN thread: on ~200 tasks with ~1,700 Playwright/AST assertions, pass rate rose from 55% to 92%; legacy-scan was trained on 30k repos (92% precision); search takes ~10 ms. Downsides: one user reported ~$5 of tokens per run, legacy-scan found only 2–3 issues for commenters, some features are Chrome-only (critics compare it to IE6), and the guides' tone is overly imperative.

For you this is a ready-made external skill to sit under your frontend router: it targets exactly the "agent writes old-style code" problem, and the guides are pruned by evals to skip what models already know. It partly overlaps your frontend skill (that one is routing and design; this adds fresh platform APIs). Watch token cost and Safari/Firefox support: check the support table in each guide. First step: in a test web project run `npx modern-web-guidance@latest legacy-scan .`, then `npx modern-web-guidance@latest install`.

Take for your setup
  • Wire modern-web-guidance into the frontend router as a skill, but load guides on demand via `search`/`retrieve` per task rather than all at once, to avoid the reported ~$5 token cost per run.
  • Add a CLAUDE.md rule for web projects: check the support table in a guide and write a Firefox/Safari fallback before using a native feature, instead of obeying the guides' "DO use" literally.
  • Run `legacy-scan .` on older web projects as a cheap deterministic audit and add it to quality-gates as an optional step.

02Simon Willison10.11

Gemini 4 Carbon is open to everyone at $2/$10 per million tokens, price doubles December 1

Simon Willison released llm-gemini 0.36, a plugin for his llm tool, adding Gemini 4 Carbon. The model was announced two weeks ago for "a subset of cyber defenders" and opened to everyone on November 10, 2026. Launch price is $2 per million input tokens and $10 per million output, the same as GPT-6.1 Sol and Claude Sonnet 5.5. On December 1 the price is scheduled to double to $4 / $20, matching Opus 5.5.

Also from the post: thinking effort is adjustable (low, medium, high), with medium as the default. The author compared SVG pelicans at all three levels. In Antigravity IDE he gave it a Three.js task (a mech walking through New York using OpenStreetMap data); a second prompt was needed to get a standalone HTML file with no external dependencies. An update says Antigravity's /swarm feature built a playable pelican game, available in AI Studio. The post gives no model IDs, commands or limits.

For you: you already have Gemini CLI and Antigravity, so this is a reason to run Carbon as an extra reviewer in vendor-review and use-antigravity while the price is half. First step: update the plugin (`llm install -U llm-gemini`) and check `llm models` for the exact ID.

Take for your setup
  • Add Gemini 4 Carbon to the vendor-review skill as a reviewer and compare it with Codex on the same diff before December 1, while it costs $2/$10.
  • In use-antigravity and the Gemini skills, set thinking effort explicitly (default is medium) and note which level to use for which tasks.
  • If the price becomes $4/$20 after December 1 (same as Opus 5.5), recheck whether Carbon still belongs in cheap tasks like summarisation.

03GitHub11.11

maxagent: hooks for Claude Code and Codex that surface checked "atoms" of experience and record new ones

maxagent (MIT, Node 18+, 220 stars, created 8 Nov 2026) installs a shared workspace (default ~/maxagent) into Claude Code, Codex, Antigravity and OpenClaw: AGENTS.md, experience/, projects/, sync.md, inbox/. Experience is stored as short checked recipes called atoms (format in experience/_spec.md). Hooks surface a relevant atom at three points: when the user sends a message, before a command runs, and after an error. Agents write atoms themselves as they work; the README doesn't detail how. Your own atoms can block a command known to fail; shared atoms from downloaded packs are advisory only: at most one per message, shown only when your own shelf has nothing relevant. Packs are JSON files on GitHub Releases with sha256 and precomputed int8 vectors; the client verifies the checksum and scans the text for download-and-run commands, attempts to rewrite agent rules, secret exfiltration, destructive commands and hidden characters, rejecting the whole pack on any hit. Meaning search pulls multilingual-e5-small (~270 MB) and needs Python, otherwise keyword-only. Separately, maxagent-bridge is an MCP server for your own Chrome via an unpacked extension and Native Messaging, with per-agent approval, a site blocklist, an action log and a stop button. The README gives no effectiveness benchmarks.

You already have auto memory, CLAUDE.md, skills and Chrome automation, so what's new is automatic hook-driven delivery of experience at those triggers (especially after an error and before a command) and the vetting of imported packs. First step: `npx maxagent init`, then `npx maxagent doctor`. Try it on a separate project first: the installer edits agent hooks and rules (with backups), and `npx maxagent uninstall` reverts it.

Take for your setup
  • An after-error hook that searches a base of short checked recipes by the error text and feeds the match to the agent: build one on top of our auto memory?
  • A PreToolUse hook that blocks a command our own notes record as failing (own entries only, never imported ones): add it?
  • Use the atom format (title, first step, check) from experience/_spec.md as a template for entries in our skills and memory?
  • If we ever import third-party rule or skill packs, copy their vetting: sha256 plus a scan for download-and-run, rule rewriting and hidden characters: add it to quality-gates?

Python 3.16.0 alpha 2 is out: faster uuid4/uuid7, richer re, quicker startup

On November 10, 2026 the second of seven alphas of Python 3.16 was released (release team: Savannah Ostrowski, Ned Deily, Steve Dower, Julien Palard). It is for testing only, not for production.

What's new: uuid4() and uuid7() now have C implementations, about 15-30x faster in microbenchmarks. re gains nested character sets, set operations (intersection, difference) and matching by Unicode properties such as uppercase letters. Interpreter startup is faster, with optimizations to garbage collection and built-in object construction. Error messages are improved. ssl adds Encrypted Client Hello (needs OpenSSL 4.0+). Builds for tvOS, watchOS and visionOS exist but are outside the PEP 11 tiers. Schedule (PEP 826): alpha 3 on December 15, 2026, beta 1 (feature freeze) on May 4, 2027, RC1 on July 27, 2027, final on October 5, 2027.

For your stack: if you generate UUIDs as PostgreSQL primary keys or as message ids in Kafka/Celery, hot paths will benefit, and uuid7 gives time-ordered keys. Faster startup helps CLIs and workers. First step: download https://www.python.org/downloads/release/python-3160a2/ and run your pytest suite in a separate environment; report bugs at https://github.com/python/cpython/issues.

Take for your setup
  • Run our pytest suite on 3.16.0a2 in a separate venv or an allow-failure CI job to catch dependency breakage early
  • Benchmark uuid4()/uuid7() on 3.15 vs 3.16a2 on our hot paths (id generation for Kafka/Celery messages) and decide whether to move to uuid7 for PostgreSQL keys
  • Put December 15, 2026 (alpha 3) and May 4, 2027 (beta 1) in the calendar as compatibility-check checkpoints
