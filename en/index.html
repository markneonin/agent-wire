GVS5H harness lifts Qwen3.8-27B from 66.8% to 92.4% on LiveCodeBench; HN disputes the result

GVS5H (repo slee-persis/GVS5H, MIT code) is a training-free method: fresh instances of a single model decompose a problem and coordinate through a shared filesystem holding a plan, notes and the current solution (working state in runs/ws/). The authors call it "ledger-based zero-shot self-orchestration". Benchmark: LiveCodeBench, the 100 latest hard problems, pass@1, eleven models, gains up to 25.6 points. Locally served Qwen3.8-27B goes from 66.8% to 92.4%. Orchestrated Qwen3.8 Flash Next scores 93.0% vs Fable 5's 90.4% at about 9% of the cost. The authors attribute the gain to decomposition and persistent context. Caveats: for some models the effect is zero or negative; Opus 5 was run on an earlier scaffold in a single pass via OpenRouter, so that comparison is not like-for-like. The README does not describe roles or any verification/voting; that is in paper/paper_latest.pdf.

The HN thread (about 50 comments) is skeptical: an old, probably contaminated benchmark; the original modes have no tools while the harness adds an agentic loop with delegation and Python execution; no comparison with other harnesses or current frontier models. This is not a new mechanism for you: Workflow, subagents and context.md already give orchestration with shared on-disk state. What is interesting is the claim that plan/notes/solution in files plus a fresh worker per step can substitute for model size. First step: from codebase/v2-current run `escalation/run_bench.py --engine multiagent --only lcb --lcb 100 --parallel 8` (needs uv and an API key; `--engine single` is the baseline) and compare against single on your model.

Take for your setup
  • Run `--engine single` vs `--engine multiagent` on a local model (MLX) to see whether orchestration helps on that specific model - the authors report zero or negative effect for some.
  • Read paper/paper_latest.pdf for how instance roles and exchange via plan/notes/solution are set up, and compare with your task-context and context.md for anything worth borrowing.
  • For cheap workers in Workflow, try the pattern "fresh instance per step, state only in plan and notes files" and measure it on one of your tasks against a single call.
