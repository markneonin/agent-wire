01Hacker News16.10

Claude Code team describes its code review process: multi-agent reviewer with voting, REVIEW.md, risk tiers and incidents turned into evals

Anthropic (Addy Osmani and others, post dated Oct 15, 2026) says Claude writes about 90% of Claude Code's code. Changes landing in the monorepo grew from ~2,500 a day (May) to 30,000+ (September). The goal is the minimum human review time that doesn't raise reverts or incidents. From June to September the share of reverted changes fell by more than 40% while merged PRs more than doubled. The review layer works like this: parallel agents hunt bugs, a separate group votes on each finding, and only findings with enough agreement get posted. Style and cleanup findings are dropped. Comments are tagged Important, Nit or Pre-existing. A separate security pass runs too, and open findings block merge. The number of human approvals depends on the risk of the change, not the author: none, one or two people. An agent's approval never counts as a human one, and an approval covers one specific commit. Repo rules live in a short CLAUDE.md and in a REVIEW.md written by code owners: what failure looks like, a cap on nits, paths to skip, file and line as evidence, and a summary that starts with a count. Every incident or revert becomes an eval case, and the reviewer is re-scored whenever its prompts, tools or model change. One PR went through 50+ review rounds overnight, so they added a 3-round cap, diff-only re-review and no repeated findings. HN commenters doubt the numbers and the SOC2 fit, call the post marketing, and mention Goodhart's law.

You already have /code-review, ultrareview and cross-vendor review. What is new is REVIEW.md, evals built from incidents, and guards against endless author-agent versus reviewer-agent loops. First step: add a REVIEW.md to one project with the post's items (what failure looks like, nit cap, paths to skip, file:line evidence) and feed it to your review skill.

Take for your setup
  • Add REVIEW.md to your projects and make the review skill read it: what failure looks like, nit cap, paths to skip, required file:line, summary starting with a count.
  • Start an eval set from your own reverts and bugs, and re-run the review skill against it whenever its prompt or model changes: keep a change only if the score rises.
  • Add to loop-design and the review pipeline a 3-round cap, diff-only re-review and no repeated findings, so author and reviewer agents don't loop.
  • In the review skill, add Important, Nit and Pre-existing tags and a vote by separate subagents on each finding, dropping findings without agreement.

02GitHub17.10

earshot: local "ears" for coding agents — an MCP server that listens to, measures and synthesizes audio on CPU

earshot (Leonxlnx, MIT, created 2026-10-15) is a CLI, Python API and MCP server that lets a coding agent "hear" audio on CPU only. It describes sounds (AudioSet labels, measurements), scores how well a sound fits a text description (CLAP), ranks candidate files and finds the best moments in long recordings; it estimates whether a sound is a real recording or code-synthesized; `measure` gives loudness, true peak, spectrum, tempo/key with no models; `timeline` gives a second-by-second transcript of a film, `sheet` an annotated image, `critique` scores a launch video against seven reference films. It also has `forge` (code-based synthesis recipes, a critic and evolutionary search) and `fit` (writes a recipe that re-renders a recording).

README numbers: a "strong" library-search match was the right kind of sound 98% of the time and the exact variant 61%; real-vs-synth ROC-AUC 0.92; about 93% of effects placed in a 60-second mix were detected. Blind tests are small: a forge sound was picked 8 of 15 times (about chance). It can't judge taste, emotion, speech or licensing; busy mixes give only hints; the forge critic can be "pleased" without improvement.

For your setup: you have a Remotion pipeline, montage, ElevenLabs and speak, but the agent reviews audio blind. earshot gives checkable metrics. First step: follow the README (Python 3.10+, ffmpeg, CPU torch, `pip install -e ".[mcp,llm,dev]"`), run `earshot doctor --load` (first run downloads ~1.4 GB of models), then `claude mcp add earshot` pointing to the venv's Python and the mcp module. The MCP server keeps models loaded, avoiding a 20–40 s load per call.

Take for your setup
  • Add earshot as an MCP server and give the montage skill a post-render step running `measure` (loudness, true peak) and `timeline` before delivering a clip?
  • Give the visual-meaning-reviewer agent an audio check: `critique`/`sheet` on the finished Remotion video against reference films?
  • Pull the two skills shipped in the repo's `skills/` (`earshot`, `real-sound`) as a template and adapt them to our voiceover and soundtrack pipeline?
  • Follow the author's caveat: trust the metrics for loudness, timing and isolated sounds, keep taste and naturalness for human listening, and write that into the skill's rules.

03GitHub17.10

Open-source implementation of server-side version control for agents, following Anthropic's design: gitai (graft)

feder-cr/git-ai (gitai, MIT, version 0.1.0, created Oct 15, 9 commits, 1.1k stars) is an independent implementation of the server-centric source control design from Anthropic's "Redesigning source control". Anthropic's internal system, Scion, is not public, and the project is not affiliated with Anthropic. Clients (agents, CI, sparse workspaces) talk to the server over gRPC, optionally through a graft-cache daemon. The server keeps a changeset log in SQLite/PostgreSQL, objects live in file/S3/GCS/Azure storage, and local git repos are just rebuildable caches. The server never calls a model itself.

Features: sparse fetch of only the requested paths, server-side blame, path history and code search, landing without a merge queue (rebase onto the tip plus compare-and-swap, batching concurrent lands), conflict resolution through a pluggable resolver (any LLM, a deterministic tool, or none), post-land tests with bisection and automatic revert of the culprit, per-agent tokens, an RPC allowlist and branch policies. Limits: interfaces may change before 1.0, known gaps are in LIMITATIONS.md (e.g. pack garbage collection), it needs Go 1.26, Meson and Ninja, builds its own Git, and is based on a Gitaly fork.

For you this is mostly reference reading: your worktree-per-writer setup solves the same parallel-agent problem more simply, and gitai matters once dozens of agents share one monorepo. First step: git clone https://github.com/feder-cr/git-ai.git && cd git-ai && make build && examples/graft/quickstart.sh, which starts a server, a cache, two agents and one land in a temp directory.

Take for your setup
  • Auto-revert after landing: bisect and revert the culprit commit. Add that step to our fix-until-green loops (loop-design) or a Stop hook after merging writer branches?
  • A log of every ref update with agent and operation: set up the same journal (commit trailer or file) for our worktree writers, so we can see which subagent landed what?
  • Per-agent token and RPC allowlist: check whether a similarly narrow permission policy is worth adding to our subagent files?

04ty releases16.10

ty 0.0.89 adds opt-in return type inference for unannotated functions

ty is Astral's Python type checker. Release 0.0.89 (2026-10-16) adds return type inference for functions and methods without a return annotation (#29253). It is off by default and is enabled with analysis.return-type-inference = "always". In pyproject.toml: [tool.ty.analysis] return-type-inference = "always"; in ty.toml: [analysis] return-type-inference = "always". The authors ask for problem reports in astral-sh/ty#4739.

Also in this release: updated vendored typeshed (#29402); a panic when negating dynamic type aliases is fixed (#29427); tuple literal lengths are widened when other collection elements contain nested tuples (#29147); ty now reports invalid Generic and Protocol arguments containing nested variadic type variables (#29146); narrowing for generic class patterns is faster (#29240).

For your stack this helps if your FastAPI/Celery code has many unannotated helpers, service functions and tests: ty will see their results and catch errors at call sites without code changes. It is an early feature, so false positives are possible. First step: add [tool.ty.analysis] with return-type-inference = "always" to pyproject.toml, run ty check on one service and compare the number of diagnostics before and after.

Take for your setup
  • Enable return-type-inference = "always" under [tool.ty.analysis] on one service and compare diagnostic counts before/after - want me to try it?
  • If false positives show up, file a minimal example in astral-sh/ty#4739 - add this to the ty upgrade checklist?
  • Pin ty 0.0.89 in dev dependencies and re-run typeshed-dependent checks with it - should I do that?
