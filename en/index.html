vvv: reusable Remotion video templates plus a skill that fills them with photos and copy

vvv (Vibe Vision Video, v0.1, MIT, 293 stars, 4 commits, created 2026-10-22) is a set of editable Remotion templates plus an Agent Skill. The idea: scenes, layouts, timing and render checks are built once, and each new film changes only the photos, names and dates, copy, music and format. You describe the film in one sentence; the agent picks a template, places photos, writes copy, renders a sample, runs checks and hands back the film with its editable project. A recreate mode rebuilds a reference video from your own material. There are six templates: Doodle, Album (plus vertical Album 9:16), DV Story, Comedy, Starter; layouts are 16:9 and 9:16. CLI: `vvv.py describe` lists photo slots, copy fields and settings, `validate` catches bad inputs before rendering, and `vvv check` measures format, audio, stills and beat alignment, though a human still judges some results. Video and voice are not generated. The token-saving claim has no benchmark, it is the authors' assertion. Verified on Claude Code and Codex, macOS ARM64. Needs Python 3.9+, Node.js 26, npm.

You already have a Remotion pipeline, montage and ElevenLabs, so the value is not Remotion itself but the pattern: a template with a declared contract (slots, fields) and validation the agent runs before the expensive render. First step: `/plugin install vvv --marketplace actionow-ai/vvv`, then ask for a film in one sentence and look at the `describe` and `validate` output.

Take for your setup
  • Borrow the describe/validate pattern: have our Remotion templates expose slots and fields and validate inputs with a cheap command before rendering — add it to the video pipeline skill?
  • Add an automatic post-render `check` (format, audio, beat alignment) to the pipeline and leave only the doubtful cases to a human — do it?
  • Install `/plugin install vvv --marketplace actionow-ai/vvv` and compare its templates and recreate mode against our pipeline on one film.

motion2code: a skill that rebuilds a video as a looping SVG+GSAP animation and checks it frame by frame against the source

lovisdotio/motion2code (192 stars, created 2026-10-20, MIT) is a skill set for coding agents. The author's premise is that agents "animate blind": they can't watch the video, so they guess timing, easing, colors and text, and loops jump. The process is split into hard steps. study_video.py grabs a frame every 0.25 s, frames around each hard cut, a contact sheet, the flat palette and a loop score (all in study.json). The agent writes a page under the contract window.anim = { tl, duration, seek(t), play(from), pause() }, where seek(t) is a pure function of time and the last moment returns to the opening frame. frame_diff.py puts source and code side by side, scores the difference per time and lists the worst five moments. check_anim.py checks the contract, the script allowlist and that no raster or video is embedded; with --runtime it runs the page headless and checks console errors, network requests, loop seam, deterministic seek and autoplay. render_anim.py renders exact frames to MP4/GIF/PNG. For screen recordings of websites it builds a working site with GSAP ScrollTrigger. Examples: six 10–15 s clips, 24–60 KB each, rebuilt with Claude Opus 5.5. The README gives no pass/fail thresholds or definition of the diff metric. Needs Python 3.9+, ffmpeg, Playwright.

You already have review skills, Remotion and a frontend router; what's new is the technique itself: make the agent "see" its output through a deterministic seek(t) plus frame-by-frame comparison. It fits your Remotion pipeline and animation tasks. First step: claude plugin marketplace add lovisdotio/motion2code, then claude plugin install motion2code@motion2code, and run it on a short clip.

Take for your setup
  • seek(t) as a pure function of time: add a rule to the frontend skill for animations so any frame can be rendered and compared to a reference.
  • frame_diff.py lists the five worst moments by difference from the source: borrow that for visual-task checks (before/after screenshots) in the process skill.
  • check_anim.py --runtime catches console errors, network requests and non-determinism in a headless run: wrap it as a Stop hook for HTML artifacts.
  • Install the motion2code plugin and compare it with your Remotion pipeline on one short clip.

Moonshot releases Kimi K3.1 Pro and Highspeed: open-weight 3T model with 1M context, weights due by Nov 4

Moonshot released Kimi K3.1 Pro, a post-trained K3 with substantially more post-training compute: 3T-class, 1M-token context, full open weights promised by Nov 4, 2026 (license not named). Highspeed is a variant 2-3x faster (no tokens/s given). API IDs: kimi-k3.1-pro and kimi-k3.1-pro-highspeed, with Zero Data Retention available. The blog gives no prices; HN commenters cite $2 input / $10 output per million tokens. Reported benchmarks: Terminal-Bench 4.0 65.7% (Opus 5.5 66.4%, GPT-6 Astra 58.2%); BenchCAD with tools 92.7% (Opus 5.5 96.2%); claim-level hallucination on their Hallu Bench Hard 8.3% vs 23.4% for K3 (Opus 5.5 15.0%). Some runs used the Claude-Code harness. Cyber data was removed from training for the open weights, so cyber ability trails closed frontier models (xdev-bench-hard 81.0% vs 33.3% for K3).

On HN (854 points) the main complaint is subscription limits: some say one task burned a 5-hour limit. Others note verbose reasoning makes per-task cost higher than per-token price suggests. Benchmarks are doubted by some; some praise it as a planner with a cheap implementer, others call it too verbose. For you this is not an Opus 5.5 replacement in Claude Code: the page does not say the model runs inside it. It is a cheap second-opinion candidate once weights land. First step: in Kimi Code run /model and pick Kimi K3.1 Pro, or call kimi-k3.1-pro via the API on one of your own tasks.

Take for your setup
  • Run kimi-k3.1-pro on one real task and compare cost per task (not per token) with Sonnet 5.5; HN reports verbose reasoning.
  • Add Kimi K3.1 Pro as another reviewer candidate in the vendor-review skill if API access is available.
  • When the weights ship (by Nov 4), check the license and whether anything from the family runs locally on MLX.

Antirion: open-source Rust LLM gateway with routing, budgets and a per-request log

Antirion (eliasbiondo/antirion, Apache-2.0, repo created 17 Oct 2026, 180 stars) is a self-hosted gateway between apps and providers: OpenAI, Anthropic, Gemini, Bedrock, Azure OpenAI, Vertex AI, Mistral, vLLM. One Rust binary with a built-in console. It does routing (fallback chains, weights, least-cost/least-latency, retries, hedging, circuit breakers), budgets and rate limits in dollars or tokens at org, team, project and key level (soft/hard/approval-gated), guardrails for PII, secrets, regexes, JSON schemas and tool permissions, exact and semantic cache, MCP and A2A gateways, Prometheus and OTLP. The request log records route, attempts, tokens, cost and guardrail verdicts.

Claimed overhead: 0.53 ms median at 5,000 RPS on 4 vCPUs (Bifrost 2.2.4: 19.7 ms; LiteLLM 1.103.1: 100% errors at that load). These are the authors' own numbers; the harness is in bench/. Native binaries are Linux-only; on macOS use the container or build from source.

For you it is a single place to track spend across Claude/Codex/Gemini and your claude -p scripts: virtual keys with budgets per pipeline or overnight agent, fallback between providers. The README does not mention Claude Code or ANTHROPIC_BASE_URL, so compatibility needs testing; Anthropic SDKs point to http://localhost:8080. First step: docker run -p 8080:8080 -p 8081:8081 -v antirion-data:/var/lib/antirion eliasbiondo/antirion, take the admin token printed on first start and open http://localhost:8081/ui/.

Take for your setup
  • Run Antirion in Docker and send one claude -p script through it by setting the base URL to http://localhost:8080 with a virtual key, to check whether it works with Claude Code.
  • Create a separate virtual key with a hard daily budget for overnight agents and /loop routines so they can't burn money unattended.
  • Use the request log (tokens, cost, cache status) as a data source for the observability skill instead of estimating by hand where tokens go.
