01Claude Code releases25.11

Claude Code 2.1.332: skills from MCP servers (beta) and a PreSkillShellCommand hook

The 25 November release lets MCP servers provide skills (beta). In the `/` menu they show as `server:skill`, and other skills keep their names. There is also a new `PreSkillShellCommand` hook event. It can refuse the inline shell commands of a skill or command as it loads. On 2.1.331 and older, a settings file that names it opens a dialog at start, so update every machine at once.

Most of the rest is fixes. Freezes are fixed when a hook prints output without end or a local MCP server floods stdout (Ctrl+C was ignored before). Hook output over about 50,000 characters is now shortened, and a read of a named pipe (for example a `.env` mounted by a locked secrets manager) fails after 20 seconds. CLAUDE.md and rules are no longer sent twice after a session moves into a worktree under `.claude/worktrees`. A PreToolUse hook's reason for asking now shows on Read, Grep, Glob, Edit and Write prompts. `/permissions` refuses rules that would be skipped at the next start, such as `rm -rf` with no tool name. OpenTelemetry gets an `assistant_response` event (on with `OTEL_LOG_ASSISTANT_RESPONSES=1`). `computer-use` is now a reserved skill name on Macs with computer use on.

This matters for you because you have many skills and hooks and use a worktree per writer. First step: update, and check that you have no skill named `computer-use`. Then look at how one of your MCP servers (for example codebase-memory) could ship skills, and try the `PreSkillShellCommand` hook on skills that use inline shell.

Take for your setup
  • Add a `PreSkillShellCommand` hook to settings.shared.json that blocks risky inline shell commands in third-party skills and plugins (plannotator, superpowers). Update every machine to 2.1.332 first, or 2.1.331 will open a dialog.
  • Check whether we have a skill or command named `computer-use`: on a Mac with computer use on it stops loading, so rename it.
  • Try shipping skills from our own MCP servers (codebase-memory, runpod) as `server:skill`, instead of copying them into ~/.claude/skills.
  • If our hooks write long logs, account for the ~50,000-character cut on hook output, and check OpenTelemetry filters for the desktop `service.name`, which is now `claude-code-desktop`.

shrink-anything: a CLI that deletes dead code, files and dependencies and keeps only the cuts after which tests still pass

shrink-anything (MIT, npm @el4cteo/shrink-anything and crates.io, repo created 2026-11-23, 218 stars) removes dead code, unused files, dependencies and assets from a codebase. `scan` only lists candidates; `cut -- <check>` deletes them and runs your check. If it fails, the batch is split until the breaking cut is found and put back. A cut stays only if the check exits 0 and at least as many tests run as before. Edited files are first parsed with the language's own parser, tests are never modified, and `undo` restores files byte for byte. Dead code is found by counting name mentions, not by a call graph: it cuts only when every mention is inside the definition itself. It may miss dead code but should not invent it. Public methods, library exports and assets in public/ go to your agent or need `--aggressive`. Claimed results: TypeScript demo −45% lines, static site 913→398 KB, −46% tokens to read. With no tests, the cuts can't be trusted.

You already have ast-grep, code-review, quality-gates and a code-graph MCP, but nothing that automatically cuts and rolls back against your tests. Agents pile up code, and this targets that. First step: `npm i -g @el4cteo/shrink-anything`, then `shrink-anything doctor` and `shrink-anything scan` in a project with solid tests (say invest/ or bot/). Then `shrink-anything go --agent claude -- <your test command>`. A plugin exists too: `/plugin marketplace add EL4CTEO/shrink-anything`.

Take for your setup
  • Run `shrink-anything scan` and `cut` on invest/ or bot/ (they have tests) and see how much dead code it finds.
  • Borrow their acceptance rule for a cut: exit code 0 and no fewer tests than before. Add it to the quality-gates skill so a failing or emptied test suite never counts as green.
  • Hook it up via MCP (`claude mcp add shrink-anything -- shrink-anything mcp`) or the plugin, and run the cleanup as a separate feature-build step after large agent-written features.
  • Use `shrink-anything report` (Markdown and SVG for a PR) as an attachment to the review after a cleanup.

gridlines: a skill that draws guide lines down a UI and finds items that miss their line

pritamux/gridlines (created 2026-11-21, 235 stars, MIT, only 2 commits) is a skill for alignment passes. The README's principle: draw the lines first, then move the items. It draws vertical guide lines down an interface (sidebar, toolbar, panel, menu, table), finds items that miss their line, and fixes their padding so everything shares a small set of edges.

Contents: SKILL.md (process and rules), probe.js (runs in the page, measures the ink edges of text, icons and controls, draws guides, lists misses), audit.mjs (headless Chromium via Playwright, saves a 2x capture with guides plus a JSON report; the Playwright folder is set through PW_DIR), and examples/sidebar.html with four planted misses. A sample report line: "MISS y56 trailing: 15px vs 12px". You can also paste probe.js into any page's console and call window.__gridlines(). The rules draw on Karri Saarinen's redraw of the Linear sidebar and Apple's HIG layout chapter. The "How it works" and "The rules" sections of the README are images, so I could not read their text; support for agents beyond Claude Code's skills folder is not stated.

For your setup: you have the frontend skill and Claude in Chrome, but a measured alignment check (pixels instead of eyeballing) is new. First step: `npx skills add pritamux/gridlines`, then run `/gridlines` on examples/sidebar.html to see the four misses.

Take for your setup
  • Install the skill (`npx skills add pritamux/gridlines`) and call it from the frontend router as an alignment step after layout work.
  • Borrow the probe.js idea (measure text and icon edges in the DOM and output a report like "MISS ... 15px vs 12px") and make it part of quality-gates for UI projects.
  • Add the principle "draw the guides first, then move items" to the frontend rules: the agent gets a measured report before it edits any padding.
