01Codex CLI releases23.10

Codex CLI 0.164.0: /presets slots, inline args for /model and /permissions, credential masking

Release rust-v0.164.0 of Codex CLI adds ten numbered /presets slots. They store reusable prompts and slash commands, and you open them from a keyboard menu (#54380, #54381). /model and /permissions now take inline arguments, so model, reasoning effort, speed and permission profile can be set in one command (#54378, #54383). Images can be viewed in the fullscreen transcript on Kitty or Sixel terminals (#54216).

Also in the release: credential masking in remote Bash/Zsh sessions, including custom providers (#54309, #54432, #56049). When masking is unavailable, unified exec may fall back to the normal mode (#55719). MCP OAuth refresh coordination is on by default (#55701). Enterprise accounts can authenticate MCP connections with Codex account grants. Fixes: a failed compaction no longer leaves partial summaries in history (#53932, #55581), resume finds compressed histories and restores saved thread settings (#54008, #55923), `-c/--config` overrides persist across several subcommand levels (#56022), and queued prompts wait for pending permission choices (#55682). Sandbox checks on macOS are hardened for case-variant paths and replaceable symlinks. The worktree and voice feature flags and transcript_v2 are removed.

For your setup, Codex is the second opinion in vendor-review and use-codex. What is new for you is mostly what helps those headless calls: inline /model and /permissions arguments and a more reliable `-c` in subcommands. First step: update Codex, try /model with arguments in an interactive session, then save a couple of review prompts in /presets. Check the exact argument syntax in the commands themselves, because the release notes don't give it.

Take for your setup
  • Update Codex to 0.164.0 and check that `-c/--config` now persists across subcommands. That may simplify the calls in the use-codex skill.
  • Save two or three cross-vendor review prompts in Codex /presets so they open from the menu instead of being retyped.
  • Check in vendor-review that compaction and resume in Codex 0.164.0 keep history intact, since a failed compaction used to leave partial summaries.

02GitHub23.10

Microsoft releases TokenEconomizer, a plugin that cuts coding-agent cost 18–31% by learning from past sessions

TokenEconomizer (Microsoft, Apache-2.0, arXiv 2610.22732, UC Berkeley + MSR) is a plugin for Claude Code, Codex, Copilot CLI and Pi. It reads finished sessions in a repo and uses them to shape later ones. Three mechanisms. Micro-skills: environment facts the agent keeps rediscovering (e.g. no pytest command, but python -m pytest works) are recorded and stated at the start of the next session, with no model call. Tool pruning: a tool unused for five sessions in a row is removed through the agent's own settings (toolprune=propose asks approval per change, toolprune restore brings tools back). Failure-loop guard: when a turn loops on a failing edit-and-test cycle far beyond the repo's usual turn length, it sends one redirect, then tells you how to interrupt; it never stops the turn itself.

On SWE-Bench (277 tasks, 6 repos) mean cost per task fell 18.4–30.9% across five agent-model pairs: Claude Code with Sonnet 5 by 23.6%, with Opus 4.8 by 30.9%. Pass@1 rose in four of five. Data stays in ~/.tokeneconomizer. Limits: only Claude Code 2.1.300–2.1.307 was tested; in Claude Code its messages show only in the Ctrl+O transcript and the model may reword them; pruning writes wait for an hour of idle time to avoid breaking the prompt cache.

You already have observability and settings-cleanup skills, but those are manual; this automates pruning and learned facts. First step: clone the repo, add it as a marketplace by absolute path, install the plugin, run refresh-catalog once, then /tokeneconomizer:status. Check your Claude Code version is in the tested range.

Take for your setup
  • Install the plugin on one secondary repo with toolprune=propose and manually review which MCP tools it suggests dropping (codebase-memory, Chrome, RunPod, etc.).
  • Run ~/.tokeneconomizer/bin/te microskills (free, from the terminal) to see which environment facts it learned, and move useful ones into project CLAUDE.md files.
  • Compare its rule 'unused for five sessions in a row means prune' with the thresholds in settings-cleanup and borrow the number if it fits.
  • Borrow the loop-guard idea for /loop and routines (in loop-design): one redirect, then a prompt to the human, no hard stop.

03GitHub23.10

Vercel Labs releases durable-harness: Claude Code, Codex and other coding agents as crash-resumable workflow sessions

durable-harness (Vercel Labs, Apache-2.0, version 0.0.x, API unstable) runs coding agents (Pi, OpenCode, libfx's fx, Claude Code, Codex) as durable agents on a Workflow SDK World. Each session is a workflow run: the conversation, the turn in progress, and every model and tool call are recorded in an event log. After a crash the turn resumes from the log on another machine, and a tool call that is unsafe to repeat is never run twice. Commands and files chosen by the model run not on the machine driving the session but in a virtual workspace (virtual()) or in the session's own Vercel Sandbox (sandbox()). Claude Code and Codex run only in the session's own Sandbox, never in a shared Function. Agents have no tools by default; you add them explicitly.

Pi quick start: npm install durable-harness @earendil-works/pi-durable @earendil-works/chord @earendil-works/pi-ai just-bash. Then define the agent in lib/agent.ts, serve chatRoute({ open, agent, authorize }) in app/api/chat/route.ts, and wrap the config with withDurableHarness(nextConfig) from durable-harness/next in next.config.ts. Locally it uses the Workflow SDK local World with no setup; on Vercel you get managed storage and queues; self-hosting uses the Postgres World.

For you: you already have headless claude -p, /schedule and /loop, but none of them resumes a turn from a log after a process dies. This solves that at the infrastructure level, but only for Next.js and Vercel Sandbox. That is heavy for a personal Telegram bot, but useful as a design reference. First step: open github.com/vercel-labs/durable-harness and look at the durable-harness/claude-code module.

Take for your setup
  • Event log plus the rule "never re-run an unsafe tool call" - add a check to loop-design: what happens to a long-running agent if the process dies mid-turn, and which steps must never run twice?
  • Model-chosen commands run in a separate sandbox, not on the machine driving the session - add an isolation item to the subagents/loop-design skills for unattended autonomous loops.
  • Agents get no tools by default and everything is added explicitly - audit the custom agent files (implementer, test-engineer, etc.): does each have a minimal tools list?

04Hacker News21.10

Omnara: open-source (Apache 2.0) backend for durable agents on any model, as an alternative to Claude Managed Agents

Omnara is a self-hostable API for running agents, positioned as an alternative to Claude Managed Agents and the OpenAI Agents API. It is Apache 2.0 with about 3.2k stars. Any model works (OpenAI, Anthropic, OpenRouter, Bedrock, LiteLLM, Ollama) as long as the endpoint is compatible with OpenAI Responses/Chat Completions or Anthropic Messages. Agent state is an append-only event log in Postgres. Stateless workers run one loop step and queue the next; a failed step rolls back and retries. An idle agent costs nothing. A daemon, omnarad, is installed on a macOS/Linux machine and connects outward, so no inbound ports or SSH are needed. An agent can use several machines and fail over when one goes offline. It also has cron schedules, Slack/Discord/GitHub integrations, per-tool permissions (auto / approval / blocked), skills, shared memory stores, subagents and MCP. For comparison, Claude Managed Agents charges token rates plus $0.08 per active session-hour. On HN (110 points) commenters doubted the novelty: logs and persistence already exist in chat products, and Codex used JSONL. The author says it is a backend, "Supabase for agents", with no client included. Local defaults are intentionally insecure.

For your setup this does not replace Claude Code. It is a layer for agents that must live without your terminal: the Telegram bot, overnight jobs, monitoring. It overlaps partly with /schedule, /loop and Workflow, but adds crash recovery and a choice of model. First step: run it locally with git clone https://github.com/omnara-ai/omnara.git, cd omnara, docker compose -f compose.yaml --profile app up -d, then open http://localhost:8000. Then run npx omnara config --api-url http://localhost:8000/api/v1 --issuer-url http://localhost:8000 and npx omnara login.

Take for your setup
  • Run Omnara via Docker Compose and launch one agent from agent.yaml with machine_name pointing at your Mac, to see how the omnarad daemon works without inbound ports.
  • Connect its MCP server to Claude Code with claude mcp add --transport http omnara https://app.omnara.com/mcp, then sign in with /mcp. This lets you start long-lived agents from a session.
  • Take Omnara's per-tool permission model (auto / approval / blocked) as a template for your PreToolUse hooks: one explicit three-level table instead of scattered rules.

05Hacker News22.10

NVIDIA releases OpenShell: an agent sandbox with kernel-level policy and credential injection

OpenShell is an Apache 2.0 runtime from NVIDIA (0.1.x line, 18k stars) that runs each agent in an isolated sandbox. The kernel limits files and syscalls, and every network connection passes a policy check before it leaves. The agent never sees real credentials: OpenShell injects them only into requests to approved endpoints, inference included. Any policy widening (a new host with credentials, a new API method) is formally verified first and waits for human review. Components are gateway, supervisor and sandbox; the gateway deploys to Kubernetes via Helm (the CNI must enforce NetworkPolicy). It needs Linux, macOS on Apple Silicon or WSL 2 (experimental), plus Docker, Podman or host virtualization. SDKs exist for Python, TypeScript, Go and Rust. Anonymous telemetry is on by default; disable it with OPENSHELL_TELEMETRY_ENABLED=false.

The HN discussion's main objection: if an agent has any outbound channel, data can leak, and only an air-gapped setup fully closes that. Alternatives mentioned: Anthropic's sandbox-runtime, matchlock, iron proxy, Docker sbx.

For your setup the useful parts are secret injection at the boundary and a network allowlist. Today your keys come through the secrets skill, and Claude Code with permissions skipped, or inside the Telegram bot, reaches the network with no such boundary. First step: curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh, then openshell sandbox create --name demo. After that, follow the "Run Your First Agent" tutorial (OpenCode on a free OpenRouter model).

Take for your setup
  • Install the project's skill: npx skills add NVIDIA/OpenShell. It teaches an agent to write policies and debug the gateway; check what is worth borrowing into our settings-change skill.
  • Run background and overnight agents (/schedule, /loop, the Telegram bot) in an openshell sandbox with a network allowlist instead of on the bare host; try it on one routine first.
  • Borrow the "key injected at the boundary, agent never sees it" design for the secrets skill: today a secret lands in the process environment, while here it could live only in the proxy.
  • Add a rule to loop-design: any widening of agent permissions (new host, new API method) waits for human review, as in OpenShell policies.

06FastAPI releases22.10

FastAPI 0.160.0: extra="forbid" on parameter models now also rejects fields declared by other parameters

You already use FastAPI, so only what changed. Release 0.160.0 (22 October 2026) changes the behavior of query, header, cookie and form parameter models. Previously a model's extra setting looked only at its own fields. Now it applies to all submitted fields in the same location (query, headers, cookies, form), including fields declared in other models, in individual parameters, or in dependencies. This matches Pydantic behavior. The change is marked as breaking (PR #16594, by @tiangolo).

The result depends on extra. With extra="forbid", anything not in the model is rejected, even if another parameter or dependency declares it. With extra="allow", those fields end up in the model as extras. With extra="ignore" (the default) they are ignored. So the riskiest case for you: a filters model with extra="forbid" in query, plus a separate Query parameter or a dependency (say pagination, or an api_key header) on the same endpoint. It used to work and may start returning 422 after the upgrade. The release has no code examples or migration guide. First step: bump fastapi to 0.160.0 on a separate branch and run pytest, and grep for model_config with extra="forbid" on models used via Query(), Header(), Cookie(), Form().

Take for your setup
  • Grep for models with extra="forbid" used in Query/Header/Cookie/Form and check whether the same endpoints have separate parameters or dependencies from the same request location
  • Add a pytest case for endpoints with parameter models: a request with a field from a sibling dependency must not return 422
  • If you are not ready to migrate, pin fastapi<0.160.0 in dependencies and upgrade deliberately
