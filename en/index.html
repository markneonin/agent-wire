lend: agents on a remote VM run commands on your laptop after Touch ID, secrets never leave the laptop

lend (blog.antonio.cx, Hacker News, 100 points, 57 comments) sits in front of your SSH agent: you forward its socket to the VM instead of the real one. A request (a command or an SSH signature) goes to `lend agent` on the laptop, is checked against a local policy (default deny), then approved, typically by Touch ID (`biometric:inline`). The approved command runs locally; stdout, stderr and exit code stream back to the agent. A rule names an executable and can restrict subcommands with `args_prefix`. `secret_reader` (e.g. `op read`) injects a secret into env (`GH_TOKEN`) only for the approved command, so the VM never sees it. SSH keys are filtered by fingerprint, `max_signatures` caps signatures per session. Leases give time- or use-limited approval for the exact same command. Commands: `lend ssh --config policy.json -- host`, `lend mcp` (a `run_local_command` tool requiring a reason), `lend exec --reason`, `lend doctor`, `lend pause --all`, `lend history`, `lend approve` (routes permission prompts, e.g. Claude Code's `PermissionRequest` hook, to the laptop). Limits: no sandbox, approving a shell, `env` or `op` grants broad access; stdin isn't shown in the prompt; no PTY; biometrics macOS only; early-stage project. Commenters criticize: the dialog gives too little context, agents can mint new tokens, secrets leak into transcripts. Alternatives: a separate agent account, short-lived tokens, proxies swapping placeholders.

For you: your secrets skill (Keychain/Vault by alias, no printing) and PreToolUse hooks cover part of this, but not "agent on a remote machine, secrets and signing stay home, approval on your device". Relevant if you run agents on RunPod or VMs. First step: `brew install antoniomika/tap/lend`, then `lend doctor` and `lend ssh --config policy.json -- host` with a policy allowing one `gh` subcommand prefix.

Take for your setup
  • For agents on RunPod/VMs, install lend and run `lend ssh --config policy.json -- host` with a policy using a single `args_prefix`, secret via `secret_reader` from your Keychain.
  • Wire `lend approve` into Claude Code's `PermissionRequest` hook so permission prompts from remote sessions land on the laptop with Touch ID.
  • Add the article's rule to the secrets skill: never approve a shell, `env` or `op` as commands, only narrow prefixes, plus a `max_signatures` cap for SSH keys.

A Claude Code skill for hill-climbing local LLM server speed with controlled measurements and stability gates

sybil-solutions/inference-optimisation-skill (MIT, created 2026-11-16, 408 stars) is a skill that walks an agent through speeding up a local LLM server: decode, speculative decoding, prefill, KV size, startup and TTFT. Six steps: compute the theoretical ceiling (bytes per token / bandwidth, FLOPs, KV limit), change one thing at a time, measure against interleaved controls, log every result including failures, gate on long-context retrieval (needle), and qualify a clean pinned build. A change is accepted only if it beats both neighboring controls and regresses nothing by more than 3%. Before calling anything "best" it needs a needle test and a concurrent full-KV soak.

Contents: SKILL.md (procedure, stopping rules), references/ (loaded on demand), and standard-library scripts: bench.py for any OpenAI-compatible server, ceiling.py, queue.sh (interleaved A/B), mem.sh. Engines: vLLM, SGLang, llama.cpp, ExLlama. Examples: Intel Arc B390 43.6→53 tok/s, startup 113→43 s; Arc Pro B70 91.2 tok/s on vLLM vs 25.0 on llama.cpp Q4_K_M; RTX 3090 96–141 tok/s; 4×H200 229 tok/s. Single-run noise is ±5–10%; results are hardware-specific and Apple MLX does not appear in them.

For you: little direct use for MLX, but it is a ready template of the "ceiling → one lever → control → log" loop, and useful for llama.cpp runs on RunPod. First step: git clone https://github.com/sybil-solutions/inference-optimisation-skill, then cp -r inference-optimisation-skill/skills/inference-optimisation ~/.claude/skills/ and run bench.py against your local server.

Take for your setup
  • Add the acceptance rule "beats both neighboring controls and regresses nothing by more than 3%" to loop-design for loops that measure something
  • Use bench.py (any OpenAI-compatible server) to benchmark local MLX models and llama.cpp on RunPod instead of manual runs
  • In use-runpod, add a long-context needle test and a full-KV soak before a config counts as working

OpenCode ships Browse: an MCP server and extension that gives agents your real Chromium browser

OpenCode Browse is an MCP server plus an extension for Chromium browsers (Chrome, Edge, Brave, Arc, Helium, Vivaldi, Opera). The agent works in your real profile: open tabs, logins and extensions, no API keys. Its tabs open in the background, in collapsed groups. It can read pages, click, type, take screenshots, and record tabs and network traffic. For logins, 2FA and payments the agent hands the tab back and continues after you click Continue. You can lend it a tab you already have open and restrict it to sites you name. It works with Claude Code, Codex, Cursor, Zed and OpenCode. The page gives no pricing or limits.

The HN thread (224 points, 119 comments) notes that the extension pairing often disconnects, Firefox and Safari are unsupported, a CDP-driven browser can be flagged as a bot, and a logged-in profile exposes you to prompt injection from web pages, so a separate profile is recommended. Most of the arguing is about OpenCode V2 itself (no permission prompts, breaking configs), not Browse. For you this is an analogue of claude-in-chrome, which you already have, but not tied to Claude. What is new: per-site restriction and network and tab recording. First step: `npm install -g @opencode/browse && browse install`, then add it to Claude Code as an MCP server and compare it with claude-in-chrome on one task that needs a login.

Take for your setup
  • Install `npm install -g @opencode/browse && browse install` and compare it with claude-in-chrome on a login-gated task (e.g. the avito skill)
  • Borrow the per-site restriction idea: add a rule or hook to the browser-use skill limiting which domains the agent may visit
  • Create a separate Chrome profile for agents so prompt injection from web pages cannot reach your main accounts
