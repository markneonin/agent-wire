renderlint: a rendered-UI linter with 40 rules and a Stop hook for Claude Code

renderlint (npm package @ngocanhnckh/renderlint, MIT, Node 18.17+) opens your app in headless Chromium and finds visual defects that TypeScript and ESLint miss. It has 40 rules: text-overflow, text-clipped, element-overlap, contrast (measured from real pixels, WCAG 2 AA), emoji icons, placeholder-text (undefined, NaN, [object Object], lorem ipsum), broken-image, native-dialog (alert/confirm), tap-target, focus-indicator, console-error, dead-link and more. It renders at phone, tablet and desktop widths, plus dark mode, plus a sweep over 13 widths from 320 to 1920 px. It then reruns the page with longer text, long words and bigger numbers. Anything that breaks only under that stress is reported as a fragile-layout warning. Each finding gives the element, source file and line (React, Vue, Svelte, Astro dev builds), a numbered screenshot and a fix hint. `npx renderlint` exits 1 on errors. A page takes 4-10 seconds; `--no-sweep` speeds it up. Limits: canvas can't be inspected, menus and dialogs are only checked via `states` or Playwright, and pages behind a login need an `auth` block.

The agent integration matters most for your setup. `init` installs a Stop hook (`npx renderlint hook`) that stops Claude from ending its turn while UI errors remain in files it changed (it gives up after 4 attempts). It also writes rules into CLAUDE.md and AGENTS.md and installs three skills: renderlint-setup, renderlint-fix, renderlint-e2e. There is also a Vite plugin and a Playwright wrapper. It is a closed verification loop like your hooks and quality-gates, but for layout. First step: in a test frontend project run `npx -y @ngocanhnckh/renderlint init`, then `npx renderlint explain contrast`.

Take for your setup
  • Add the Stop hook `npx renderlint hook` to our frontend skill for web UI projects, so the agent can't end its turn with layout errors in changed files?
  • Wire `npx renderlint --format github` or `--min-coverage` into quality-gates as a UI check next to lint and types?
  • Adopt the stress-pass idea (longer text, long words, bigger numbers, 13-width sweep) as a checklist item in the frontend skill and in UI tests?
  • Try `init` on one project to see what it writes to CLAUDE.md and how the renderlint-fix and renderlint-e2e skills are worded, and borrow the good phrasing?

code-review-skill: code review with four probes, JSON evidence and a merge gate derived from JSON

kyy-logs/code-review-skill (v0.1.1, MIT, created 2026-10-29, 305 stars) is a skill for Claude Code and Codex. It reads the diff, surrounding source, tests and project rules; it builds nothing, runs nothing and never edits code. Four probes, each in a fresh context writing its own JSON: behavior-review (behavior vs contract), test-coverage, repo-guard (repo rules; .java/.ts/.tsx/.vue by default) - these three are required - and optional impact-analysis (callers, contract changes, blast radius). All probes use the same model; the author calls this separation of duties, not independent review.

Each finding carries location, summary, evidence, severity and status (open/reconciled/wontfix/false-positive). High needs a method signature plus the violated contract, or a concrete code path; unverified hunches are capped at medium. collect-metrics validates the JSON and derives counts; the fact sections of code-review.md are rendered from JSON and re-verified. A failed required probe or an open high finding blocks the merge. Line coverage below line_target (85) blocks; branch coverage is advisory. Results are modest: on 11 Java cases it found 5 of 7 targets with 0 confirmed false positives; no comparison against single-agent review exists.

You already have /code-review, vendor-review and quality-gates, so what's new is the "JSON is the source of truth for the gate" design and the evidence rule. First step: npx -y skills add kyy-logs/code-review-skill --agent claude-code --skill code-review --yes in a test project, then say "Review these changes with code-review".

Take for your setup
  • Adopt the evidence rule: a high finding in review skills needs a signature plus the violated contract or a code path, otherwise it caps at medium - add this to vendor-review and quality-reviewer?
  • JSON-derived gate: have reviewers write findings as JSON with a status, then a script or `claude -p --json-schema` computes the block (open highs) and renders the report's fact sections - do this in feature-build?
  • Install the skill in a test project and compare its findings on one diff against our /code-review and vendor-review - the author has no such comparison.

Codex CLI 0.167.0: agent command center, backend switching, and patch review inside approval prompts

Codex CLI rust-v0.167.0 shipped on November 6. Main item: `codex agents --no-daemon` opens an agent command center. It and the session picker mark unread results (#58238, #58239, #58263, #58264), and tasks are sorted by recency within status groups. From the terminal session picker you can switch between connected backends, and drafts are kept (#58280, #58457). While an approval prompt is open you can expand patch details (#58281). Local image attachments preview while composing, and paths to viewed images are clickable. "Sign in another way" now offers API key and cloud providers. The `gcp_setup_wizard` feature sets up Google Cloud Vertex AI via Application Default Credentials or a credential file. System proxy for macOS/Windows is opt-in under `/experimental`.

Internals: Guardian review can now review recorded exec calls directly, and PreToolUse hooks run before the direct-review policy checks (#58368). Subagent parent links are persisted before child storage exists, and the subagent picker puts pending approvals first (#58129, #58720). Automatic context compaction now counts retained output from failed responses (#58404). For you this is mostly a second-opinion tool: Codex is already your cross-vendor reviewer and you have your own orchestration in Claude Code. The command center is a different take on the same problem, one screen for all agents and unread results. First step: update Codex and run `codex agents --no-daemon` to see whether it beats your background agents for tracking parallel work.

Take for your setup
  • Update Codex and run `codex agents --no-daemon`, then compare its overview of parallel agents with our background agents and SendMessage
  • Borrow the unread-results idea: in a Stop or SessionStart hook, flag which background agents finished but whose result hasn't been read yet
  • For use-codex and vendor-review: if you want Codex on Vertex AI, enable `gcp_setup_wizard` and check whether it works as a separate backend

Poki: a local MCP server that lets Claude Code operate a real iPhone, no jailbreak

Poki (JosssphZhou/poki, AGPL-3.0, created 5 Nov 2026, 314 stars, release v0.1.1) lets agents operate a real iPhone. It has two parts: a local MCP server and a standalone terminal Poki Agent, which can also run through iMessage or Telegram. No jailbreak and no extra hardware: a Mac talks to the phone through idevice tools (physical devices, needs USB pairing) or a simulator adapter. The tool list lives in docs/tools.md; the README only shows the example list_devices. Poki remembers past tasks and runs repeats faster.

Requirements: macOS 15+, Xcode, Node.js 24+, ffmpeg; the prebuilt package is Apple Silicon only. Limits: on physical phones only the Chinese interface is verified, portrait orientation only. Screen contents are sent to the configured model, and if asked to send a message or pay, Poki will do it.

For you this gives Claude Code hands on mobile: testing iOS apps and running scenarios on the simulator, wired in like your Chrome MCP. Start with the simulator, not your personal phone: git clone, ./bin/setup, npm start, then claude mcp add (exact command is in the README), and call list_devices.

Take for your setup
  • Connect Poki as an MCP next to Chrome MCP, but on the simulator only, and check that list_devices sees it
  • If you move to a physical phone: use a separate test iPhone/account and a PreToolUse hook that requires confirmation for sending messages and payments, since Poki does them without asking
  • Write a skill modeled on browser-use for iOS: the main session doesn't call Poki tools itself and hands the task to a subagent, so screenshots don't bloat the context
