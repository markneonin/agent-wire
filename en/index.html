Cheap model Jev escalates uncertain cases to Opus, matching its accuracy at about a quarter of the cost

Hightouch tested LLM judges for identity resolution: finding over-merges, where one identity holds records of several people. Benchmark: 1,000 identities from a synthetic town (pseudopeople), half of them over-merges. Opus 5.5: 99.0% accuracy, $3.86 per 1,000, 2.2 s per identity. Cheap "decision" models return a 0–1 confidence: Luna 97.3% at $0.10, Jev 95.7% at $0.05, over 10× faster. On a harder set (typos in birth date, twins, Jr/Sr) Opus scored 95.1%, Jev and Luna about 89%.

Hybrid: Jev scores everything, and if confidence falls in a 30–90% band (about 22% of cases), the item goes to Opus. Easy set: 98.8% at $0.88 vs $3.86. Hard set: 95.3% at $2.94 vs 95.1% at $5.39 for Opus alone. Luna plus Opus reached only 91.6%: Luna is overconfident, with errors at 90–100% confidence, so its mistakes can't be caught. Jev's errors cluster near 50%, so it is calibrated. Limits: synthetic data, one task, and the hard set was built by the authors. HN commenters criticize calibration claims without ECE and ambiguous labels. One reports that with a good Haiku the escalation layer added little.

For your setup: you already have subagents on different models and `claude -p --json-schema`, so the only new part is the pattern "cheap model + confidence threshold → escalation". First step: in one script using `claude -p --json-schema`, ask Haiku to return a confidence field (0–1), re-ask Opus below a threshold (say 0.9), and compare cost against all-Opus on 50–100 labeled examples. HN mentions an `/advisor` setting where a weaker model calls a stronger one; the source doesn't cover it, so check it separately.

Take for your setup
  • Add a 0–1 confidence field and escalation to Opus only inside the uncertainty band to our `claude -p --json-schema` scripts, instead of running everything through Opus.
  • Before enabling it, measure the cheap model's calibration: check where it errs at 90–100% confidence. If there are many such errors, as with Luna, escalation won't work.
  • Tune the escalation threshold on a labeled sample by plotting share sent to Opus vs accuracy vs cost, as in the article (30–90% band → 22% of cases).

devvm: a separate Lima VM per project folder for Claude Code, Codex and opencode

devvm (MIT, repo created 6 Nov 2026, 252 stars) gives each project folder its own isolated VM built on Lima. Run `devvm` in a folder: it detects toolchains from project files (a package.json gives node), shows what the VM will get, and after you confirm opens a shell at the same path as on the host. Inside, you run `claude`. The first run builds a base image in a few minutes; later VMs start in seconds as copies of it, with toolchains shared read-only. Built-in layers: docker, nix, desktop; your own via `devvm layer new`.

Isolation: the VM mounts only the project folder, the network defaults to an allowlist (only permitted hosts), and GitHub and Claude Code tokens stay on the host. With `--clone` the VM works in its own clone of the repo, away from your working tree and .git; you pull the result on the host with `git fetch devvm` and review it with `git log -p main..devvm/main`. The authors say plainly that no sandbox closes every gap. Requires macOS 13+ or Linux and Lima 2.2+; tested on Apple silicon and Linux, Intel Macs not tested.

For your setup (Claude Code in the terminal and the Telegram bot, a git worktree per writer) it is a way to run an agent with broad permissions without risking the host or secrets: instead of a worktree you get a whole VM with a clone. Agent settings, skills and MCP carry over via `devvm agent import`; log in with `devvm agent login claude`. First step: `brew trust --formula devvmhq/tap/devvm && brew install devvmhq/tap/devvm`, then `devvm doctor` and `devvm --clone` in a test project.

Take for your setup
  • Run writer subagents and the Telegram bot session inside `devvm --clone` instead of git worktrees, pulling results with `git fetch devvm` and reviewing `git log -p main..devvm/main` — try it on one project?
  • Put unattended loops (/loop, /schedule, fix-until-green) into a VM with an allowlist network so the agent has no access to tokens or extra hosts — add this rule to the loop-design skill?
  • Move the environment into a VM with `devvm agent import` and check that skills, hooks and MCP (codebase-memory, Telegram) work there — run that test?
  • Add a CLAUDE.md rule: risky experiments and third-party code run only in a devvm VM, with secrets kept on the host (secrets skill)
