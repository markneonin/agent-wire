Kinetograph: a Rust/GPU video renderer with no Chrome, Remotion-compatible, with MCP

Kinetograph (v0.2.0, Beta, repo created 2026-10-23, 234 stars) is a programmatic video engine for agents. You write video in TypeScript using the Remotion API (plus CSS, SVG, Canvas 2D, WebGL, Web Audio). Imports of `remotion` and `@remotion/*` resolve to its own implementation, so existing Remotion projects should run unchanged. Node runs the project code and builds the per-frame tree, while a Rust addon (napi-rs, wgpu + Skia, FFmpeg) draws frames on the GPU. Per the README, pixels never enter JS and rendering needs no Chrome. Numbers on an Apple M4 with `--concurrency 4`: a 33 s vertical video (988 frames) renders in 24 s, 37 s of 1080p in 13 s, and the 1,184-frame launch film with sound in 26 s. Every command takes `--json`; there are `still`, `strip` (contact sheet), `inspect --frame N --json`, `studio` and `mcp`. License is PolyForm Small Business (free under 100 people and 1M USD revenue); the API may change.

You already run a Remotion pipeline and MCP servers, so what's new is a native renderer replacing Chrome, plus an agent-oriented interface: `still`/`strip`/`inspect` let an agent look at a frame and the scene tree without a full render. Studio sends the agent the selected layers, source locations and a picture of the area over ACP; only Claude Code has been tested. First step: on macOS run `brew install ffmpeg pkgconf`, build the repo (`npm ci && npm run build`), and render one of your Remotion projects with `npx kinetograph render <index.tsx> --concurrency 4 -o out/x.mp4`, comparing time and output with your current render.

Take for your setup
  • Run one of our Remotion projects through `npx kinetograph render ... --concurrency 4` and compare time and output with the current render - worth switching?
  • Add an agent self-check step to the video skill: `kinetograph strip -n 12` and `inspect --frame N --json` instead of a full render after every edit.
  • Connect `npx kinetograph mcp` as an MCP server for the montage project and see whether it replaces our render scripts.

02Latent Space27.10

Author runs an offline OpenCode + Ollama + Qwen3.5 9B agent on a Mac and fixes a bug with no network

Rittika Jindal's Latent Space post (2026-10-27) shows a coding agent running fully on a laptop with the internet off, since outages are common in the Himalayan foothills. Stack: OpenCode 1.19.4 (agent), Ollama (model server), qwen3.5:9b (about 6.6–7.6 GB download; estimated 12–16 GB RAM, possibly more at a 64k context). Ollama starts with: OLLAMA_HOST=127.0.0.1:11434 OLLAMA_NO_CLOUD=1 OLLAMA_CONTEXT_LENGTH=65536 ollama serve. OpenCode runs with --pure (no external plugins). In opencode.json, model and small_model point to the local model, baseURL is http://127.0.0.1:11434/v1, web tools are blocked, and edits and shell commands ask for permission. Per Qwen's model card, the 9B scores LiveCodeBench v6 65.6 and BFCL-V4 66.1 (4B: 55.8 and 50.3). These are model-card numbers, not measured on the laptop.

The test was modest: a one-line bug in expense_total.py (Decimal(amount) should be total += Decimal(amount)). 3 of 5 tests failed before, all 5 passed after, and the agent left the tests untouched. Speed was not measured and large repos were not tried. The agent proposed pytest in a unittest project, so the author advises naming the exact test command. This is a fallback for no-network days, not a Claude Code replacement. You already have opencode and local MLX models, so little here is new. First step: ollama pull qwen3.5:9b, start ollama serve with the flags above, turn off Wi-Fi and check curl --noproxy '*' --fail http://127.0.0.1:11434/api/tags. The config is in the repo RittikaJ/opencode-qwen-local-setup.

Take for your setup
  • Copy opencode.json from RittikaJ/opencode-qwen-local-setup (local provider only, web tools blocked, permission prompts) as an offline opencode profile?
  • The author verified offline mode with two curls: 127.0.0.1:11434/api/tags must answer and example.com must fail. Add this check to a skill or launch script for the local model?
  • The agent picked pytest in a unittest project. Add the exact test command to project CLAUDE.md files, plus a 'don't change the tests, install nothing' rule in prompts for weaker local models?
  • Try qwen3.5:9b via Ollama as a free offline reviewer in our vendor-review skill?

ty 0.0.93: preview diagnostic baselines for adopting ty on existing code, plus fixes for a panic and a hang

ty is the Python type checker from Astral (the makers of ruff and uv). Release 0.0.93, dated 2026-10-28, mainly adds a preview feature, diagnostic baselines (#27636), meant for adopting ty in projects that already have errors. In pyproject.toml you set [tool.ty] baseline = "ty-baseline.json", then record the current diagnostics with ty check --update-baseline. Later runs filter matching diagnostics out of CLI output and show them as hints in the language server. The release notes warn that the baseline format may change while the feature is in preview.

The rest is fixes. A panic when checking truthiness in a loop (#29759) and a hang when negating recursive unions of instance types (#29652) are fixed. Narrowing of strings and ints compared with enum members (#29743), narrowing after guarded match captures (#29558), @override on overload implementations in stubs (#29470), and constraint merging for repeated ParamSpecs (#29172) were corrected. ty also no longer synthesizes primary keys for abstract Django models (#29744). Several speed-ups landed too: match narrowing over large unions, long boolean expressions, and Linux x86-64 builds optimized with LLVM BOLT.

For your stack (FastAPI, Pydantic, SQLAlchemy), a baseline helps when you bring ty into an older service: CI fails only on new errors, and the old debt doesn't block you. First step: upgrade to ty 0.0.93, add the baseline setting under [tool.ty], run ty check --update-baseline and commit ty-baseline.json. Since the format may change, expect to regenerate the file after upgrading ty.

Take for your setup
  • Adopt ty in an older service via a baseline: add baseline = "ty-baseline.json" to [tool.ty] and record the existing debt with ty check --update-baseline - set that up?
  • Add a CI step running ty check that fails only on new diagnostics beyond the baseline - configure it?
  • Pin ty (0.0.93) in dev dependencies and regenerate the baseline when upgrading, since the preview format may change - add that rule to the project README?
