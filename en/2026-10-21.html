01GitHub21.10

Harp: a Warp terminal fork with a sidebar for running many Claude Code and Codex agents

Harp is an unofficial, macOS-only fork of the open-source Warp terminal. A sidebar replaces the tab bar and shows, for each Claude Code or Codex session, whether it is working, waiting for you, or done. An unread mark stays until you look; a dot means background work is still running; a moon marks a tab you set aside. Tabs can go into named groups. With the tmux integration on, group and order are stored on the tmux sessions and survive restarts, and agents are detected by polling every 10 seconds. A session started over SSH from a phone can request a tab with `tmux set-option @warp_adopt 1`. The footer shows two rings per provider (5-hour window and weekly limit); Harp does not fetch the numbers, it reads a local JSON file, format in `docs/limit-rings.md`. For Claude Code there is a hook in `integrations/claude-code` that reports background tasks. Mostly AGPL-3.0. Warp's AI and cloud features still talk to Warp's servers; login through Harp is untested. It runs alongside Warp with its own bundle ID and `~/.harp` folder.

You already have workflows, subagents and background agents inside one session; Harp solves something else: an overview of many separate sessions in different tabs, showing which one waits for input. It helps if you run several parallel Claude Code sessions in worktrees. First step: download `Harp-<version>.dmg` from Releases, set `[integrations.tmux] enabled = true` in `~/.harp/settings.toml`, and look at the hook in `integrations/claude-code`. For debugging statuses: `WARPOSS_STATUS_TRACE=1`, log at `~/Library/Logs/harp.log`.

Take for your setup
  • Look at the hook in Harp's `integrations/claude-code` and compare it with our Stop/UserPromptSubmit hooks: could we emit a 'waiting for you' status to an external indicator the same way?
  • Enable `integrations.tmux` in `~/.harp/settings.toml` and run parallel worktree sessions in tmux so groups and order survive restarts.
  • Produce a JSON file with the remaining 5-hour and weekly limits in the `docs/limit-rings.md` format and point `integrations.limit_rings.file` at it.

02FastAPI releases20.10

FastAPI 0.154.0: request parameters get Pydantic validation options

You already use FastAPI and Pydantic, so the only new thing is this: release 0.154.0 came out on 20 October 2026. It has a single change, the feature "Add Pydantic validation options to request parameters" (PR #16542 by @tiangolo). Going by the title, request parameters (Query, Path and similar) now accept Pydantic validation options directly in their declaration.

Neither the release page nor the PR says which options exist or which parameter types get them. The PR description is only an AI-use disclaimer, and the changed files were not visible. The release has no bug fixes and no code examples. CI passed (41 checks) and CodSpeed showed no performance change. No breaking changes are declared in the notes, but there are no details either.

For your stack: if you now tune validation through separate Pydantic models or Depends, some of it may become simpler. Until you read the diff, that is a guess. First step: open https://github.com/fastapi/fastapi/pull/16542, go to Files changed and read the signatures and tests. Then on a branch run pip install -U fastapi==0.154.0 and run pytest.

Take for your setup
  • Read Files changed in PR #16542 and note which Pydantic options Query/Path/Header/Cookie now accept before using them.
  • Bump fastapi to 0.154.0 on a separate branch and run pytest to confirm current parameter validation behaves the same.

03FastAPI releases20.10

FastAPI 0.155.0 removes deprecated **extra from Path, Query, Header and the rest; unknown arguments now raise TypeError

You already use FastAPI, so I'll skip the framework and cover only the change. Release 0.155.0 came out on 20 October 2026 and has a single item, a breaking one (PR #16545 by @tiangolo). The deprecated arbitrary keyword arguments (**extra) were removed from Path, Query, Header, Cookie, Body, Form and File. Before, an extra kwarg was accepted and ended up in the schema with a deprecation warning. Now an unknown argument raises TypeError.

What to change: any extra JSON Schema properties go into json_schema_extra. Query(custom="value") becomes Query(json_schema_extra={"custom": "value"}). This matters for you because the error fires when the module declaring the endpoint is imported, so the service won't start, rather than failing on a request. If fastapi is unpinned in pyproject or the lock file, an upgrade in CI or an image build can break the build. First step: before upgrading, grep the code for non-standard kwargs in Query(, Path(, Header(, Cookie(, Body(, Form(, File( and move them to json_schema_extra. Then bump to 0.155.0 and run pytest. If you get a TypeError about an unexpected argument after the upgrade, look at exactly that spot.

Take for your setup
  • Grep the repos for custom kwargs in Query/Path/Header/Cookie/Body/Form/File and move them to json_schema_extra before upgrading
  • Pin the fastapi version in pyproject and the lock file, and bump to 0.155.0 in a separate PR with a pytest run
  • Add a CI test that imports the whole app, so a TypeError in endpoint declarations is caught before deploy

04FastAPI releases20.10

FastAPI 0.151.0: explicit JSON null in request bodies no longer falls back to the default

FastAPI 0.151.0 (released 20 October) is a breaking change, PR #16536 by tiangolo. JSON request bodies now distinguish an explicit null from an omitted value. For individual Body parameters, null is validated as None: nullable types accept it, and non-nullable types reject it even when a default is defined. Defaults and default factories apply only when the value is omitted. This covers parameters inside JSON objects and parameters that represent the whole body. If a JSON object is expected (Body(embed=True) or several body parameters) and the client sends null as the entire body, it now returns a validation error.

Previously, null on a field with a default could effectively yield that default. If you have clients, a frontend or other services that send null to mean "use the default", they will start getting 422 after the upgrade. You already use Pydantic and FastAPI, so only this behavior is new. First step: before bumping to 0.151.0, run your pytest endpoint tests for body parameters with added cases for explicit null and for a missing field. Clients that used null to request a default should omit the field instead, as the release notes advise.

Take for your setup
  • Add parametrized pytest cases for every endpoint with Body: field omitted / explicit null / null as the whole body, and assert the expected 200 or 422.
  • Find schema fields with default or default_factory that are not declared nullable, and decide: allow None in the type, or fix clients so they stop sending null.
  • Pin the fastapi version in the lock file before upgrading and roll out to staging first, watching for a rise in 422s in logs and metrics.
