01Hacker News18.11

Mastra open-sources Factory, the Slack-driven agentic kanban board it uses to maintain Mastra itself

Mastra Factory is an open-source "software factory" that the Mastra team uses to build Mastra itself. It is a configurable agentic kanban board you can @-tag in Slack. Columns: triage, plan, build, review, shipped. Underneath: durable agents, conversational memory, a markdown wiki with source citations, PR-comment signals feeding sessions, and a customizable cloud sandbox with a coding harness. The default harness is mastracode; Claude Code and Codex support is only planned. Last week Factory opened and merged 238 PRs versus 630 merged by humans. After three months the team mostly drives it through Slack, and senior engineers run several sessions in parallel. They closed the repo to outside contributors because of low-value PRs and now ask for detailed issue repros. From the discussion: the plan phase is often overhead, so they are moving toward automated triage→build; you can set skills per column, pick models, steer agents mid-run and add approval gates; risky work gets more supervision. A skeptic said Issues+PRs already do this. By default agents act as the "Mastra Platform" GitHub App; a PAT makes them open PRs as a user.

You already have Workflow, subagents, worktrees, feature-build and /schedule, so the orchestration is familiar. New for you: triggers from Slack/PR comments, a persistent staged board, a cited wiki as memory, and automation level by risk. First step: run `npm create factory` or open https://github.com/mastra-ai/template-factory and see how per-column skills are set up.

Take for your setup
  • Automation by risk: they run low-risk work without a plan and keep risky work supervised with approval gates. Add this rule to feature-build so small fixes skip the grilling/plan stage?
  • A skill per column (triage, plan, build, review) with a chosen model. Split our feature-build into such separate skills with pinned models?
  • A cited markdown wiki as project memory. Try a wiki with links to code/PRs next to CLAUDE.md and auto memory?
  • PR-comment signals as a session trigger. Build a hook or /schedule routine that picks up PR comments and starts an agent?

02Codex CLI releases20.11

Codex CLI 0.171.0: GPT-6.2 Sol and Astra models, TUI workspace on by default, codex exec --remote

Codex CLI 0.171.0 (Nov 20, 2026) adds GPT-6.2 Sol and Astra to the model catalogs, with Sol now the default selection. The TUI workspace is on by default: searchable document previews, image previews and subagent transcripts next to the main conversation. Also new: configurable undo/redo in the non-Vim composer, /rc and /remote to manage local remote control and show device pairing codes, and custom MCP status line selection and authoring via /statusline (gated by tui_extensions_statusline).

For automation the key item is `codex exec --remote <ADDR>`: it starts or resumes a noninteractive session on an existing app server. Fixes include preserved drafts and queued follow-ups across session switches, permission profiles kept when changing working directory, late completion events no longer cancelling approvals for a newer turn, and enterprise MCP sign-in for identity providers that issue ID tokens without refresh tokens. The changelog has ~200 PRs from ~80 contributors: sandboxing (seccomp, bubblewrap, Windows), Guardian, rollout traces and budgets.

For you: Codex is your second-opinion tool via the use-codex and vendor-review skills, and the new Sol default changes which model actually does your reviews. Check which model a bare `codex exec` now picks and pin it if you need stable results. First step: update Codex and try `codex exec --remote <ADDR>` against a running app server.

Take for your setup
  • Pin the model with an explicit flag in the use-codex and vendor-review skills, since the default switched to GPT-6.2 Sol
  • Try `codex exec --remote <ADDR>` in use-codex to run reviews against a long-lived app server instead of a cold start
  • Enable the custom MCP status line via /statusline (flag tui_extensions_statusline) and see if it is useful

03Hacker News18.11

Google ships Gemini 4 Neon: mid-tier model, $3/$15 per M tokens, #1 on the Coding Agent Index

On November 18, 2026 Google announced Gemini 4 Neon, a model for complex software engineering and knowledge work. In the Gemini 4 family it sits between Carbon (hardest long-horizon projects) and Hydrogen (fast everyday work). Pricing: $3 per million input tokens, $0.15 cached, $15 output, 1M context. Four thinking levels, default high, xhigh for the hardest tasks. Model ID: `gemini-4-neon`.

Google's numbers: #1 on the Artificial Analysis Coding Agent Index (58.6), Terminal-Bench 4.1 at 65.2%, FrontierCode 2.0 at 46.2%, SWE-sweep 12.8% on mini-SWE and 39.0% in Antigravity. At high it costs 32% less per task than Carbon and, per Google, 50–80% less than top competitors. Neon can run standalone or orchestrate parallel Hydrogen subagents in Antigravity; the demos mention a `/swarm` command. Google claims fewer redundant file reads and better context compaction. It is available in the paid Gemini API tier in AI Studio and in Antigravity for Pro and Ultra; the post says nothing about a CLI or rate limits. All figures are Google's own benchmarks. The HN thread (768 comments) praises Opus 5.5 for long projects and coherence, and Gemini for more natural writing (commits, PRs). Complaints: quota cuts and Antigravity limits.

For your setup this is one more second-opinion candidate next to Codex and Gemini CLI, not a replacement for Opus 5.5. First step: run `gemini-4-neon` on one real review through the vendor-review skill and compare it with Opus.

Take for your setup
  • Add `gemini-4-neon` to the vendor-review skill as a separate reviewer and compare its findings with Opus 5.5 on one real diff.
  • HN users praise Gemini for natural text without "Claudese" and delegate commits and PR descriptions to it. Test that against our human-writing/human-english skills with `slop_check.py`, comparing Neon and Sonnet output.
  • Google claims Neon at high costs 32% less per task than Carbon. Via use-antigravity, try handing Neon bulk tasks (summaries, extraction) and measure quota use.

04GitHub20.11

diego3g/craft: a design skill set for agents that draws screens with every state and reviews them itself

craft (MIT, 280 stars, created 15 November 2026) is a skill set for Claude Code, Codex, OpenCode, Cursor and other agents. It works with Paper, pen.dev and Figma (via MCP), with plain HTML as the fallback. The README says the Figma adapter hasn't been tested in real runs yet.

/craft-setup interviews you one question at a time and writes DESIGN.md with eight sections: Product, Audience and voice, Mood, Brand, References, Constraints, a dated Decisions log and Open questions; it also builds tokens and base components. /craft takes a page, screen, flow or element, confirms scope, lists states (empty, loading, error, long content, permissions, offline) drawn with realistic messy data, draws, and checks the result. Other skills: craft-critique (findings ranked by impact, changes nothing in review mode), craft-states, craft-explore (three structurally different directions), craft-system (tokens, component index, audits), craft-sync (links a code design system to the design tool and returns changes as a reviewed diff). A hidden router, using-craft, dispatches them. Rule: "your project wins" if its design system differs from the defaults.

For your setup: you already have a frontend router skill, skills and plugins, so what's new is a ready design process with a mandatory state checklist and DESIGN.md as persistent decision memory. First step: `/plugin marketplace add diego3g/craft`, then `/plugin install craft@craft` and run `/craft-setup` in a small UI project, and compare with your frontend skill.

Take for your setup
  • DESIGN.md with a dated Decisions log and Open questions: add such a memory file to UI projects and reference it from CLAUDE.md?
  • A mandatory state list (empty, loading, error, long content, permissions, offline) before drawing: add it as a checklist to our frontend skill?
  • craft-critique: review ranked by impact that changes nothing: add a similar review-only mode for UI to the frontend skill?

05Postgres Weekly19.11

Postgres 19 released: non-blocking REPACK, query plan control, sequence replication

Postgres 19 came out on November 19, 2026. Headline: REPACK reclaims bloat and can reorder a table to match an index; REPACK (CONCURRENTLY) doesn't block reads or writes until the final swap. It supersedes VACUUM FULL and CLUSTER (kept for compatibility). Developer features: INSERT ... ON CONFLICT DO SELECT (get-or-create in one round trip), COPY with JSON output, IGNORE NULLS in window functions. Plan control: the pg_plan_advice extension lets you experiment with and guide plan choices, and pg_stash_advice applies advice automatically by query ID, so you can fix a slow plan without changing the app. Replication: logical replication can be enabled without a restart, sequences can be replicated, and WAIT FOR LSN gives read-your-writes consistency on standbys.

For your stack: ON CONFLICT DO SELECT can replace the "insert on conflict do nothing + select" pair in SQLAlchemy/asyncpg code with one query, and WAIT FOR LSN helps if you read from replicas right after writes. Before upgrading: JIT is now off by default; full text search, pg_trgm and fuzzystrmatch indexes may need a reindex after pg_upgrade; pg_upgrade --check can pass and the upgrade still fail if a role or database sets standard_conforming_strings = off or you have your own uuid-to-bytea cast (now built in). Run VACUUM ANALYZE after pg_restore. Minor releases 18.7, 17.12, 16.16, 15.20, 14.25 also shipped (52 security fixes), and Postgres 14 is end of life. First step: on a staging copy, run REPACK (CONCURRENTLY) on a bloated table and pg_upgrade --check.

Take for your setup
  • Replace the "INSERT ON CONFLICT DO NOTHING + SELECT" pattern in our SQLAlchemy repositories with ON CONFLICT DO SELECT after moving to 19
  • Add to the upgrade checklist: reindex FTS/pg_trgm, check standard_conforming_strings and custom uuid-to-bytea casts, VACUUM ANALYZE after pg_restore, decide on JIT
  • Try pg_stash_advice on one slow query by query ID instead of changing code
  • Check whether any service still runs Postgres 14, which is now end of life
