Repo with a CLAUDE.md and three prompts: plan, plan critique in a fresh context, git diff audit

Vaibhav published a personal instruction set for coding agents (172 stars, one commit, MIT): a `CLAUDE.md` with 10 principles and three prompts in `prompts/`. The 4,500+ hours figure is the author's own estimate, not telemetry. Core: Stage 1 `planning.md` produces a plan with acceptance criteria and how each is verified, then hard-stops until approval. Stage 2 `critical-plan-review.md` runs in a fresh context or subagent as an adversarial principal engineer hunting races, missing timeouts, idempotency risks and over-engineering, with a "YAGNI brake" separating real failure modes from hypotheticals. Stage 3 `production-readiness-review.md` runs fresh against raw git state (`git status`, `git diff`, `git diff --cached`, untracked files): logic bugs, nulls, secret leaks, stray artifacts. Routing: spike (one probe, two-sentence finding), bounded (1–3 files, autonomous), architectural (full pipeline). Human sign-off is required for schema migrations, public API changes, new dependencies and destructive commands. The author admits these gates are only instructions, not enforcement; real limits come from the tool's permission settings. The rest links to superpowers, Ponytail and i-have-adhd.

For your setup this is mostly familiar: feature-build, subagents, vendor-review, superpowers, i-have-adhd and grilling already exist, and Workflow does this pipeline better. Little is new: the Ponytail ladder (YAGNI → existing code → stdlib → platform APIs → installed dependencies → minimum code) and the "YAGNI brake" in plan review. First step: read `prompts/critical-plan-review.md` and `production-readiness-review.md` and compare them with your quality-reviewer and business-reviewer prompts.

Take for your setup
  • Add the Ponytail ladder to code-style or CLAUDE.md: YAGNI → existing code → stdlib → platform APIs → installed dependencies → minimum code, plus "fix the root cause at the caller, don't wrap the symptom"?
  • Add a "YAGNI brake" to the plan-reviewer prompt (review-page / feature-build stage 3) to separate real failure modes from low-probability hypotheticals?
  • Make the final reviewer inspect raw state (`git status`, `git diff`, `git diff --cached`, untracked files) rather than the implementer's summary — check whether quality-reviewer already does this?

02FastAPI releases14.11

FastAPI 0.163.0 adds a max_concurrency parameter to Depends to cap concurrent calls of a dependency

FastAPI 0.163.0 was released on 14 November 2026. Its one listed feature is "dependency concurrency limits": a Depends(max_concurrency=...) parameter, PR #16746 by @tiangolo. By its name it caps how many calls of a dependency run at once. The PR was merged into master on 14 November, labeled feature, and is documented in the Advanced Dependencies section; its description says the change was made with AI help and reviewed manually. It includes concurrency tests.

What the release and PR pages do not say: what happens when the limit is exceeded (queueing or an error), whether the limit is per dependency or global, and whether it works for sync dependencies. I am not guessing, so check the docs. The release also mentions an official skill for coding agents that guides them to features matching your installed version; install it with uvx library-skills.

For your stack this may be a neat way to protect bottlenecks (SQLAlchemy/PostgreSQL pool, an external API, Redis) without hand-written asyncio.Semaphore. First step: upgrade to 0.163.0, read /advanced/advanced-dependencies/, and test the over-limit behavior with pytest before using it in production.

Take for your setup
  • Read /advanced/advanced-dependencies/ to learn what max_concurrency does when the limit is exceeded before replacing your own Semaphores with it
  • Write a pytest test for a dependency with max_concurrency wrapping an external API call or DB pool, and check behavior under concurrent load
  • Install uvx library-skills in the project so the agent suggests features matching the installed FastAPI version
