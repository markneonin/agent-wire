Nari Labs ships Qwen3.8-27B at 3 bits (10 GB) that matches BF16 on their benchmarks

NariQ is a quantization of Qwen3.8-27B (vision-language) at 3.0 / 2.5 / 2.0 bits per weight: 10.12 / 8.44 / 6.75 GB versus 53.8 GB in BF16. The method is trellis-coded PTQ built on QTIP, calibrated on real coding-agent traces; the vision tower stays BF16 and the MTP module is not included yet. By the authors' own runs (Claude Code as the harness): DeepSWE 41.0 vs 39.8 for BF16, Terminal-Bench 2.1 63.8 vs 62.6, AIME 98.3 vs 97.7. 2.5 bpw is a bit weaker on Terminal-Bench (60.2); 2 bpw drops clearly (DeepSWE 28.6). License is Apache-2.0.

The limits are real: it needs the nari-llama.cpp fork (Ollama, LM Studio and stock llama.cpp can't load it), and it is fast only on NVIDIA (RTX PRO 6000: ~89 tok/s at 4K, ~71 at 64K); an M3 Pro manages ~3.8 tok/s. A 24 GB card fits ~135K context. On HN, commenters noted the Unsloth comparison was read off charts under a different harness, and some of the gain may come from the harness, not the model. For you this is reference material: your MLX models on the Mac won't run it, but on a RunPod/Linux NVIDIA box it lets a 27B agent run on one 24 GB GPU. First step: on a GPU pod run `curl -fsSLO https://github.com/nari-labs/nari-llama.cpp/releases/download/b12431-nariv0/run.sh && bash run.sh 3.0`, then llama-server with `--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`.

Take for your setup
  • Use the runpod skill to check whether NariQ 3.0bpw on a 24 GB card (L4/A10, ~135K context) works as a local backend for Claude Code on cheap background tasks, and compare with Sonnet on 3-5 of your own tasks.
  • The authors calibrated on real coding-agent traces and scored on DeepSWE and Terminal-Bench 2.1 - take those two benchmarks as a template for evaluating local models in the vendor-review skill.
  • Add a note to use-runpod: the nari-llama.cpp fork, `run.sh 3.0`, sampling flags `--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`, and `-c 131072` for 24 GB.

agent-sim runs the iOS simulator on plain x86-64 Linux so an agent can test iOS apps without a Mac

agent-sim (Developing-Gamer, 270 stars, created 2026-11-21, Apache-2.0; the author says it is early and rough) runs Apple's iOS simulator on Linux with no Mac and no GPU. Under the hood: x86Sim (runs the arm64 simulator runtime on x86-64), Darling for macOS kernel interfaces, dynarmic for ARM translation, and Mesa's CPU Vulkan driver with metal2vulkan for Metal. The agent installs an .ipa, reads the screen as text (`snapshot`, with `--json`), and uses `tap` by element ref, text or coordinates, plus `type`, `scroll`, `swipe`, `screenshot`, `logs` and `record`. Every action returns the resulting screen. There is a phone pool (`pool up/take/release`) and browser streaming (`serve --listen`, H.264 over WebSocket).

README numbers: boot 12–30 s, touch latency about 14 ms, scrolling about 55 fps on a Zen 5 VM. Three phones use 6.8 GB with KSM versus 8.7 GB without. It needs Ubuntu 24.04, 8+ CPUs, 16 GB RAM and 60 GB disk; setup takes about 30 minutes and downloads an 8 GB runtime from Apple. Limit: builds must be unencrypted (not App Store; use Ad Hoc, Development, Enterprise or a simulator build). The full gap list is in KNOWN_ISSUES.md, which the page does not include.

For you: it ships a ready MCP server, so Claude Code gets eyes and hands for iOS apps on RunPod or any Linux box, no Mac needed. It fits fix-until-green loops for mobile features. First step: run `install.sh` from the repo on Ubuntu 24.04, then `agent-sim setup`, `agent-sim up`, `agent-sim snapshot`, then register `agent-sim mcp` as an MCP server.

Take for your setup
  • Bring up agent-sim on a RunPod pod with Ubuntu 24.04 (8+ CPUs, 16 GB, 60 GB) and register `agent-sim mcp` in Claude Code as another MCP server next to Chrome
  • Use the repo's `SKILL.md` as the base for your own iOS-testing skill: `snapshot` → `tap` by ref → `snapshot` again
  • Use `pool take/release` for parallel subagents, one phone per agent in its own worktree
  • Check up front that the app has a simulator build or an Ad Hoc .ipa, since App Store builds will not run

AWS releases codekb: semantic search and call graph across many repositories, exposed via MCP

awslabs/codekb (created 2026-11-12, 169 stars) is a code-understanding service spanning many repositories, for people and agents. One container serves a web UI, REST API and MCP server. Everything runs in your own AWS account: Bedrock (LLM, Guardrail, Titan V2 embeddings), S3 Vectors, S3, KMS for Git tokens.

Pipeline: add a "space" (Git URL or zip) → Tree-sitter parses symbols and builds a call graph → an LLM describes each function (a Guardrail masks secrets and PII), Titan embeds the descriptions → semantic search by intent, then call-graph traversal of callers/callees. Refresh is incremental: only changed files are re-parsed and affected callers re-summarized; if a refresh fails, the last version stays searchable. "Hyperspaces" group related repos; there is a chat agent, Agent Hopper, with an Impact Analysis mode. MCP clients named: Kiro and Claude Code. Limits: a snapshot of one branch/tag at one commit, no history; up to 10,000 files, files over 10 MB skipped, clone within 5 minutes, 32 background jobs (CODEKB_PIPELINE_POOL_SIZE). The README has no benchmarks.

It overlaps with your codebase-memory MCP (code graph). What is new is cross-repo semantic search by meaning and the Bedrock/AWS dependency, so it is of little use without an AWS account. First step: read docs/local.md in the repo (single-user local run; needs Bedrock access to Claude and Titan Text Embeddings V2) and connect its MCP to Claude Code.

Take for your setup
  • If you have AWS: run codekb locally per docs/local.md and connect its MCP to Claude Code next to codebase-memory, then compare them on a task that spans several repos.
  • Borrow the pattern "an LLM describes each function in business terms, embed the descriptions, then traverse the call graph" and add a search-by-meaning step to the code-investigation skill before grep.
  • Borrow Impact Analysis (who is affected through callers) as a step in feature-build before editing shared functions. Add it?

safe-anything: a Rust vulnerability scanner that also checks AI agent configs (hooks, skills, MCP)

safe-anything (by erkamyaman, MIT, 100% Rust, repo created 2026-11-22) is a CLI scanner that needs no config or account. It finds SQL/command injection, XSS, eval, path traversal, SSRF, unsafe deserialization and weak crypto (9 languages plus SQL), and leaked secrets (redacted in output). It also checks Docker, GitHub Actions, Kubernetes, Terraform, nginx and Android/iOS settings, and matches locked dependencies against OSV.dev. It has 75 rules with CWE/OWASP references. On Juice Shop it reports 67 findings in 1,195 files in about 0.03 s on an M4. On express it reports 0 in 216 files. The noisiest rule is code.xss-inner-html.

The AI-config part is the interesting one for us. It parses Claude Code, Codex, Cursor, Gemini and OpenCode settings, MCP, hooks and skills. It flags bypassPermissions, pre-approved Bash, unpinned npx/uvx/docker MCP servers, plaintext MCP tokens, `curl | sh` in hooks, skills that read ~/.ssh, and invisible Unicode in instructions. Limits: it matches patterns and does not trace data, so a clean scan does not mean safe code. Its only network call is OSV.dev (package names and versions), and `--offline` turns it off. We already have quality-gates and vendor-review, but nothing that audits the agent config itself, and we have many of our own skills and hooks. First step: run `npx safe-anything .` in the repo root that holds .claude, then `safe-anything --list-rules` to see the agent rules.

Take for your setup
  • Run `npx safe-anything .` on the repo with .claude (hooks, skills, settings) and review the agent-rule findings
  • Add `safe-anything --offline --fail-on high` as a check in the quality-gates skill or a pre-commit hook: it exits 1 on high/critical
  • Connect `safe-anything mcp` as an MCP server (tools `scan`, `list_rules`) and use it to vet third-party skills and plugins before installing them

open-diagram: a Python library for architecture diagrams that raises LayoutError when its own layout is bad

open-diagram (MIT, created 2026-11-18, 372 stars, 37 commits) is a Python library for dense architecture diagrams, built for agents (Claude, Codex, Cursor) and people. You describe a diagram in a short script: Diagram, Panel, Tile, d.right_of(...) for placement, d.link(a, b, kind=, label=) for connections. d.save("name") writes SVG and PNG, prints a summary and raises LayoutError if it finds problems, such as blocks too close together or a line crossing a panel. The message names the specific blocks and suggests a fix: route the line with via_x/via_y, move a block, or pass cross_ok=True. The library does not fix layout automatically; it only reports.

Label widths come from font metrics and kerning (Inter is bundled), and text is drawn as shapes, so the SVG renders the same in browsers, PowerPoint, Keynote and Figma. Labels sit in lists at the top of the script. It also offers JSON and Mermaid import, a CLI, a GitHub Action, cloud icons and templates. PNG output needs Chrome, Chromium or Edge (CHROME env var).

For your setup this gives a ready "agent draws, check fails, agent fixes" loop: an error naming blocks replaces eyeballing a picture. It suits diagrams in specs, review pages and READMEs. First step: pip install open-diagram, then claude mcp add with uvx for open-diagram-mcp (exact command in the README), and run python3 examples/<name>.py.

Take for your setup
  • Connect open-diagram-mcp via claude mcp add (uvx) and give diagrams to a subagent, so review-page schemas are built from code, not drawn by hand
  • Add a rule to the review-page skill: architecture diagrams are built with open-diagram and save() must pass without LayoutError before the owner sees it
  • Borrow the pattern of a self-check whose error names the offending objects and suggests a fix, for our own scripts, so an agent can repair in a loop

Astral: how to harden Python projects and GitHub Actions against supply-chain attacks with hashes, lockfiles and cooldowns

Astral (2026-11-23) covers two scenarios: a maintainer's account or CI is compromised and a malicious release ships, or the distribution server itself is hacked. Version pins are not enough; you need hashes. They protect against files added to an old PyPI release (up to 14 days later), force-pushed git tags, and MITM with forged TLS certificates. uv.lock already stores hashes for all files. For Actions: reference the full commit SHA with the version as a comment (`actions/checkout@3d3c42e... # v7.0.1`), convert with pinact, keep it updated with Dependabot/Renovate, and in GitHub settings allow only pinned actions. Publish to PyPI via Trusted Publishing (OIDC, `id-token: write`, `uv publish`) and guard the release workflow with an environment requiring approval. zizmor lints CI for mutable tags and dangerous triggers: `pull_request_target`, `workflow_run`, `issue_comment`. Cooldown: PyPI removes most malware within 24 hours, so don't install releases that are only a few days old.

You likely already know uv.lock and Dependabot; what's new is the cooldown, locking CI tools, and banning sdist builds. Instead of `uvx nox`, use `uv add --group nox nox` and `uv run --only-group nox --isolated nox -s ...`, plus `UV_LOCKED=1` in the workflow `env`. PEP 723 scripts are locked with `uv lock --script foo.py`. First step: add `[tool.uv] exclude-newer = "3d"` to `pyproject.toml` and `cooldown: default-days: 3` to `.github/dependabot.yml`.

Take for your setup
  • Add `[tool.uv] exclude-newer = "3d"` to pyproject.toml and `cooldown: default-days: 3` to dependabot.yml so fresh releases aren't installed for the first days
  • Run pinact over the workflow files, enable "only pinned actions" in GitHub settings, and add zizmor to CI
  • Replace `uvx <tool>` in CI with `uv add --group` + `uv run --only-group ... --isolated` and set `UV_LOCKED=1` in env
  • Enable `no-build = true` in [tool.uv], with `no-binary-package` exceptions, if your dependencies allow it
