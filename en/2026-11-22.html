Thinking Machines releases open-weights Inkling 2 Mini: a 26.4B looped MoE, 20 GB, runs on a laptop

On November 20, 2026 Thinking Machines Lab published Inkling 2 Mini with open weights. It is a 26.4B-parameter MoE (3.4B active) built as a looped transformer: the middle layers run three times per token, so 24 stored layers give 48 layer applications. The model reasons more without writing more tokens. Memory footprint is about 20 GB, trained and served mostly in NVFP4.

Reported numbers (self-reported): SWE-bench Verified 79.2%, SWE-bench Pro v2 Hard 77.9%, Terminal Bench v2.1 71.6%, MCP Atlas 82.7%, BrowseComp 79.0% (with compaction). It leads open-weights models under 100B on DeepSWE v1.1 (48.2%). Weak spots: multi-turn chat and many-constraint instructions (MultiChallenge 50.0%, ComplexConstraints 33.4%, behind Qwen3.8-27B), and factual knowledge is on par with same-size models, so it leans on search and tools. Internal destructive-action rate: 10.2%.

For your setup: the main agent stays on Opus/Sonnet 5.5, but this is a candidate for a cheap local model for bulk subtasks (summaries, extraction, tool calls) next to your MLX models. Pricing and API are not given in the article. First step: on a Mac with 32+ GB RAM, run it via Ollama (support is stated, exact commands are not) or the Unsloth quantized GGUF with llama.cpp, and test it on your own tasks through `claude -p --json-schema`.

Take for your setup
  • Download the quantized GGUF (Unsloth) or the Ollama build and run it on 5-10 real tasks from our scripts via `claude -p --json-schema`, comparing against the current local MLX model.
  • Add Inkling 2 Mini as a candidate in the cross-vendor review skill and as a cheap worker for summarization and extraction, where Gemini/Antigravity or Haiku is used now.
  • Test it against our MCP servers (codebase-memory, Telegram) for tool-heavy work: the article claims MCP Atlas 82.7%, but it is weak on many-constraint instructions, so keep prompts short.

Inkling-2-Mini (26.4B MoE) squeezed to 5.4 GB for Apple Silicon: HumanEval 71% vs 93% for the original

LookAtMyQuant is a set of MLX quantizations of thinkingmachines/Inkling-2-Mini: a 26.4B-parameter MoE with 5.4B active, 128 experts with top-8 routing, and layers 6–17 looped three times. The BF16 text weights take 18.89 GB; the authors made six builds from 3.9 to 12.8 GB. The 5.4 GB build stores 1.65 bits per weight using "SQYFR v2": all experts and 130–144 attention projections are trained jointly on the teacher's rollouts, followed by a final scale polish.\n\nResults versus BF16: GSM8K 87.0% vs 96.5%, HumanEval 71.3% vs 92.7%, vision 4/4. On an Apple M5 Max: prefill 1,807 tok/s, decode 75.3 tok/s, median 124.4 tok/s with a drafter (about 179 MB), active RAM 5.33 GB. Limits: code quality drops noticeably, the eval sets are small (200, 164 and 4 tasks), the README states no license for the weights (MIT covers only the code).\n\nThis isn't about Claude Code but about local MLX models, which you already run. At 71% HumanEval it's weak for coding; it fits cheap jobs like summarizing or extraction. First step: pip install git+https://github.com/ShinMegamiBoson/lookatmyquant.git, then lamq generate shinmegamiboson/Inkling-2-Mini-LookAtMyQuant-5.4GB --drafter shinmegamiboson/Inkling-2-Mini-LookAtMyQuant-drafter -p "..." --stats.

Take for your setup
  • Run the 5.4GB build through lamq with --stats on your Mac and compare tok/s and quality with your current local MLX models.
  • Use it only for cheap background jobs (summarizing, extraction), not for code: HumanEval is 71.3% vs 92.7%.
  • Check the weights' license on Hugging Face before using it: the README doesn't state one.

OpenComputer: Apache 2.0 open-source Devin alternative — @Computer in Slack runs Claude Code/Codex/OpenCode on your own VM and returns a PR

diggerhq released OpenComputer: you mention @Computer in a Slack thread, the agent works on its own computer, the team can watch and steer it, and the result arrives as a pull request. It ships no agent of its own: it runs your Claude Code, Codex or OpenCode (you can bring your ChatGPT/Codex subscription). Architecture: one or more VMs per organization run a gateway called "Calvin", and each session is isolated with rootless Podman. State goes to local disk and is backed up to git after every turn, so a session can resume on another VM. Slack events come in through Cloudflare Workers and Durable Objects; the VM dials out over a websocket, so it needs only outbound network. There is a web UI, CLI and API. Limits: Slack only (Discord and T3 Code planned), self-hosting means your own cloud account (AWS/GCP/Azure, see SELFHOSTING.md), it depends on Cloudflare, and local models are not supported. The authors' benchmarks (PR 3.3x faster than Devin: 56s vs 185s; first push 24s vs 62s) are not independently verified. The cloud offer is a 3-day trial with 600 work minutes.

For you this is a pattern, not a new tool: Claude Code as a server-side worker in a team chat. You already run Claude Code inside a Telegram bot, so the value is in the details: Podman sandboxing and snapshotting session state to git after every turn. First step: read SELFHOSTING.md in github.com/diggerhq/opencomputer to see how a session and its resume are built. You don't need to deploy the whole thing.

Take for your setup
  • OpenComputer backs up session state to git after every turn so a session can resume on another machine. Add that to bot-session.sh?
  • Isolate Telegram bot sessions in rootless Podman, as OpenComputer does, instead of a shared environment. Worth a look?
