Sphinx: a git hook that quizzes you on your agent's diff before push

Sphinx is a free open-source (MIT) git hook. When you or your agent pushes to a protected branch, git pauses and a reviewer model reads the diff (it hasn't seen your chat with the agent) and asks what the change does when things go wrong. The site's example: a webhook handler saves an event ID before calling `charge()`, and the question is what happens on a retry. A wrong answer gets an explanation and a new scenario; a correct one lets the push through. Install: `npm install -g sphinx-understand` (Node 22.19+, macOS, Linux or WSL), then `sphinx install`, which connects git and your agents (Codex, Claude Code, Cursor, OpenCode, Pi) and asks which model reviews: your existing agent, OpenRouter, or any OpenAI-compatible endpoint. `sphinx yolo` turns the questions off and logs every skip. Your answers are never sent to the coding agent, and `.env` files and keys are never opened. The page doesn't describe grading criteria. On HN (246 points) skeptics say the questions can be pasted into an agent, multiple choice invites guessing, and the quiz misses diff-level junk (leftover debug code, weakened assertions, hallucinated imports). Suggestions: gate PRs rather than production pushes, and test whether the reviewer can spot wrong assumptions. Alternatives mentioned: PR descriptions split into why/what/how, and a "quiz me on the PR" skill.

You already have review layers (`/code-review`, vendor-review, quality-reviewer), but they check the code, not your understanding. Sphinx targets exactly that: the hook makes you understand the diff before it ships. First step: run `npm install -g sphinx-understand && sphinx install` in one non-critical repo and pick Claude Code as the reviewer.

Take for your setup
  • Install Sphinx on one repo and see whether its diff questions beat your review skills, which only check the code.
  • Write your own "quiz me on the PR" skill for large agent PRs: questions about failure scenarios (retry, partial failure) on a diff you didn't write.
  • Add a why/what/how block to the PR/commit skill template, as suggested in the discussion: it surfaces hidden LLM decisions.

DeepSeek ships V4.1-Flash-1017: 763B, 1M context, MIT license, Terminal-Bench 4.0 up from 31.2 to 42.3

DeepSeek-V4.1-Flash-1017 is a "minor update" to V4.1-Flash. The weights are open under MIT, 763B parameters (BF16/F32/F8/I8), 1M-token context, recommended max_tokens 256K+, sampling temperature 1.0 and top_p 1.0. DeepSeek claims gains in reasoning, coding, agentic tasks and vision, plus shorter output and faster task execution, so each task costs less. The card's table: Terminal-Bench 4.0 (Claude Code harness) 42.3 vs 31.2 for the previous version; DeepSWE v1.1 77.0 (Opus 5 74.0, GPT-5.6 Sol 73.0); ProgramBench 29.1; NL2Repo 68.2; Automation-Bench 60.5. Opus 5 still leads most rows: Terminal-Bench 51.8, HLE 56.3 vs 42.6, NL2Repo 75.3. The card gives no API price. It runs on vLLM, SGLang (OpenAI-compatible API) and Docker Model Runner, and has 64 community quantizations for llama.cpp/Ollama/LM Studio. There is also deepseek-recipe: Rust libraries with Python bindings that convert Messages, Chat Completions and Responses requests into the model's prompt format and parse tool calls and thinking; no Jinja template is shipped.

On HN (944 points) people praise speed, low cost and "developer-like" code that isn't too clever; one user ported games to Rust for about 3 euros. Complaints: DeepSeek's own API reportedly logs inputs and trains on them (some third-party hosts offer zero-data retention), claims of heavy hallucination, and on local runs Q3_XS loops badly while Q4_K_S is stable. For you this is not an Opus 5.5 replacement but a cheap candidate for an executor or second-opinion role next to Codex, Gemini and opencode. First step: connect the model through OpenRouter or Fireworks in opencode, run one backlog task, and compare time and cost against Sonnet 5.5.

Take for your setup
  • Add DeepSeek V4.1-Flash-1017 to the vendor-review skill as another reviewer through a zero-data-retention provider (Fireworks) — a near-free second opinion?
  • Run the same backlog task on Sonnet 5.5 and on DeepSeek through opencode, measure time, output length and cost, and log the result in observability?
  • Don't send private repos or secrets to DeepSeek's own API: add a rule to the secrets/vendor-review skills to use only zero-data-retention providers?

DeepSeek launches search and fetch APIs at $0.75 per 1,000 successful requests

DeepSeek opened two raw JSON endpoints with Bearer auth: POST https://api.deepseek.com/v1/tools/search (its in-house search engine) and POST .../v1/tools/fetch (a page returned as Markdown). Search takes query up to 128 chars, count 1–50, need_content for full page text, and ori_question to help query understanding. Operators: site:, -site:, "phrase", lang:, after:, before:. Each result carries rerank_score 0–3 (≥1.5 is high quality), a 600–800 char summary, date, and authority 0–4.

Price is $0.75 per 1,000 successful requests for both search and fetch. Billing happens only on HTTP 200 with a non-empty result; empty results, errors and timeouts are free. Limits: search 100 QPS, fetch 25 QPS plus a per-domain cap. Through DeepSeek Harness, Claude Code or Codex, server-side calls are free for now and become paid on 1 Nov 2026 (00:00 Beijing). The page does not document function-calling integration or supported models. HN commenters compare prices per 1,000: Brave $5, Exa ~$4, Serper ~$1, Ceramic $0.25. For quality they rank Exa and Tavily first. The main objection is that DeepSeek's API is not zero data retention, so sensitive queries are risky.

For you this is a cheap fallback search and fetch for your own scripts and headless agents, where built-in WebSearch is costly or unavailable. First step: curl https://api.deepseek.com/v1/tools/search -H "Authorization: Bearer $DEEPSEEK_API_KEY" -H "Content-Type: application/json" -d '{"query":"claude code hooks after:2026","count":5}'. Keep the key via your secrets skill.

Take for your setup
  • Build a skill or MCP wrapper around /v1/tools/search and /v1/tools/fetch, key via the secrets skill, as a cheap fallback search for claude -p scripts.
  • Filter results by rerank_score ≥ 1.5 and authority ≥ 3, and pull full text only via need_content or fetch for selected URLs, to keep context tokens down.
  • Add a CLAUDE.md rule: never send private queries (personal data, names, internal code) to DeepSeek search, since it is not zero data retention.

FastAPI 0.146.0 deprecates the root_path parameter of FastAPI()

FastAPI 0.146.0 (released 18 October) marks the root_path parameter of the FastAPI() constructor as deprecated. The notes list it under Breaking Changes (PR #16520 by @tiangolo). The replacement is to set the root path when you start the server: fastapi run --root-path /api/v1. The notes say nothing else: no reason, no removal date, no migration examples.

This matters if your app sits behind a proxy or API gateway with a prefix such as /api/v1 and your code has FastAPI(root_path="/api/v1"). After upgrading, that code will emit a deprecation warning, and the parameter will probably be removed later (the release gives no date). If your pytest config turns warnings into errors (filterwarnings = error), CI may fail right away. First step: run grep -rn "root_path" across your services, find FastAPI(root_path=...), move the value into the launch command (fastapi run --root-path /api/v1) or into your Dockerfile/manifest, then check that /docs and openapi.json still load with the right prefix. If a service is started directly with uvicorn instead of fastapi run, the notes don't say how to set the prefix there; check the docs.

Take for your setup
  • Grep all FastAPI services for FastAPI(root_path=...) and list what must move into the launch command
  • Replace the parameter in Dockerfile/compose/k8s manifests with fastapi run --root-path /api/v1 and check /docs behind the proxy
  • Check whether the pytest config turns warnings into errors before bumping FastAPI to 0.146.0
