agent-crop: local timing of coding agents and a review loop that writes lessons back into skills

agent-crop (npm `agent-crop-dsh`, MIT, 178 stars, repo created 2026-11-14) is a plugin for DSH, Claude Code and Codex. Hooks write facts to `~/.agentcrop/data/events.jsonl`: tool name and success/failure of each call, end-of-turn time (`stop`) and next-message time (`prompt`). A gap of up to 15 minutes counts as `user_wait`; longer or off-hours gaps are `idle_gap` and excluded. It flags repeats (`tool_churn`, `rework_signal`), and yellow/red timeouts inject a nudge and require the agent to report a `blocked` phase. Conversation text is not stored and nothing is uploaded.

The agent fills in the judgments itself: `phase`, `summary`, `cause`, `next`, and a `category` from a fixed nine-value enum (serial-wait, repeat-pitfall, design-churn, decision-batching, tool-misuse, no-evidence, spec-drift, human-wait, other). Self-reports are not treated as conclusions until checked against the measured times and failure counts. The author's example: a CLI with many subcommands made the agent loop on `help` (tool-misuse); after the agent wrote the missing Skill page, the task dropped from ~10 minutes to 30 seconds (the author admits this is not a full evaluation). Cost is 100–300 characters per turn. Limits: health thresholds are uncalibrated, fewer than 3 sessions gives no conclusion, `type`/`difficulty` are often empty.

For your setup: you already have general observability via ccobs. What is new is the loop of measure, classify the loss, edit a skill or instruction, then verify the effect, plus the nudge tone. First step: install for Claude Code following `docs/INSTALL.md` (it adds MCP tools `crop_health` and `crop_update`) and after a week run `crop health --days 7`.

Take for your setup
  • Adopt the fixed enum of loss causes (tool-misuse, repeat-pitfall, spec-drift, etc.) and add classification of each review to our ccobs/observability skill?
  • Add a rule that the agent must report `blocked` with `cause` and `category` when a time threshold is exceeded, as a Stop/UserPromptSubmit hook with a timer in our hooks?
  • Turn the pattern 'repeated `help`/errors on one CLI → write a skill page' into a weekly step in settings-cleanup: look for tool_churn and close it with a skill?
  • Add the principle 'an agent self-report is not a conclusion until checked against measurements' to loop-design for unattended loops?

02Claude Code releases20.11

Claude Code 2.1.330: loops and schedules run up to 30 days, stricter `rm` approval, worktree and MCP fixes, built-in easel charts

Released 20 November, about 150 changes. Main points: `/loop` and recurring scheduled tasks now run up to 30 days (previously 7) while their session keeps running, and say when they end; tasks created earlier still end at 7 days. More `rm` commands aimed at root, home, a top-level folder or the working folder ask for approval, and are refused where nobody can answer. Skills run with a `model` setting (except `context: fork` skills) keep the session's model for subagents, forks, compaction and `/recap`. Prompt hooks accept aliases such as `haiku` or `sonnet` in `model`. In `deniedMcpServers`, a name entry now hides only the named claude.ai connector; to block everything at that URL, deny the exact URL. Added easel: a built-in mod that draws charts on request and under MCP metrics results (Pro/Max, Team/Enterprise where available, macOS and Linux; turn off in `/config`). Fixed: `ExitWorktree` deleted a worktree another running session was using; an MCP server declared by subagents was shut down when one subagent finished; user settings lost on concurrent saves; `/rewind` restoring an older file version; a subagent's own subagents running on the plan-mode model under `opusplan`/`haiku`; the first prompt after sleep waiting three minutes; WebFetch freezing for minutes; `claude -p` exiting 0 on a full disk (now exit 1 with an error). Also: `claude auth login` for organizations in the Enterprise Admin Console, `/workflows` and `/fork` in VS Code.

For your setup this mostly overlaps with what you already run (worktree per writer, nested leads, `/loop`, `/schedule`, SessionStart hooks), so most of it is bug fixes you may have hit. First step: update and recheck your `/loop` and cron agents, since the 7-day cap may have cut long loops. Also check that models pinned in skills and agents still behave as expected (`model` in a skill no longer switches subagents or compaction), and that your hooks don't trip over the new `rm` approvals.

Take for your setup
  • Recheck long-running `/loop` and `/schedule` tasks: the cap is now 30 days, but tasks created earlier still end at 7 days and need recreating
  • Audit your skills with a `model` field: subagents, forks, compaction and `/recap` now stay on the session model, so fix skills that relied on the old behavior
  • Check hooks and scripts that run `rm` on root, home or the working folder: they now ask for approval or are refused when nobody can answer
  • Prompt hooks accept `model: haiku` or `sonnet` aliases: simplify the hook configs
