renderlint: линтер отрендеренного UI с 40 правилами и Stop-хуком для Claude Code

renderlint (npm-пакет @ngocanhnckh/renderlint, MIT, Node 18.17+) открывает приложение в headless Chromium и ищет визуальные дефекты, которые не видят TypeScript и ESLint. Всего 40 правил: text-overflow, text-clipped, element-overlap, contrast (считается по реальным пикселям, WCAG 2 AA), emoji-иконки, placeholder-text (undefined, NaN, [object Object], lorem ipsum), broken-image, native-dialog (alert/confirm), tap-target, focus-indicator, console-error, dead-link и другие. Рендер идёт на телефоне, планшете и десктопе, плюс тёмная тема, плюс sweep по 13 ширинам от 320 до 1920 px. Потом страницу перепрогоняют с длинным текстом, длинными словами и большими числами. То, что ломается только под нагрузкой, идёт как warning fragile-layout. В отчёте указаны элемент, файл и строка (React, Vue, Svelte, Astro в dev-сборке), пронумерованный скриншот и подсказка по исправлению. Запуск `npx renderlint` возвращает код 1 при ошибках. Страница занимает 4-10 секунд; для скорости есть `--no-sweep`. Ограничения: canvas не проверяется, меню и диалоги только через `states` или Playwright, страницы за логином требуют блока `auth`.

Для твоего сетапа важнее всего интеграция с агентами. `init` ставит Stop-хук (`npx renderlint hook`), который не даёт Claude закончить ход, пока в изменённых им файлах есть UI-ошибки (после 4 попыток отпускает). Он же пишет правила в CLAUDE.md и AGENTS.md и ставит три скилла: renderlint-setup, renderlint-fix, renderlint-e2e. Есть и плагин для Vite, и обёртка для Playwright. Это замкнутая проверка результата в духе твоих хуков и quality-gates, но для вёрстки. Первый шаг: в тестовом фронтенд-проекте выполнить `npx -y @ngocanhnckh/renderlint init`, затем `npx renderlint explain contrast`.

Что взять себе
  • Добавить в наш скилл frontend Stop-хук `npx renderlint hook` для проектов с веб-UI, чтобы агент не завершал ход при ошибках вёрстки в изменённых файлах?
  • Подключить `npx renderlint --format github` или `--min-coverage` в quality-gates как UI-проверку рядом с lint и типами?
  • Взять приём стресс-прогона (длинный текст, длинные слова, большие числа, sweep 13 ширин) как пункт чек-листа в скилле frontend и в тестах интерфейсов?
  • Проверить на одном проекте, как `init` пишет правила в CLAUDE.md и ставит скиллы renderlint-fix и renderlint-e2e, и перенять удачные формулировки?

code-review-skill: код-ревью четырьмя пробами с JSON-доказательствами и merge-gate по JSON

kyy-logs/code-review-skill (v0.1.1, MIT, создан 2026-10-29, 305 звёзд) - скилл для Claude Code и Codex. Читает дифф, окружающий код, тесты и правила проекта; ничего не собирает, не запускает и не правит. Четыре пробы, каждая в свежем контексте и со своим JSON: behavior-review (поведение против контракта), test-coverage, repo-guard (правила репозитория; по умолчанию .java/.ts/.tsx/.vue) - эти три обязательные - и необязательная impact-analysis (кто вызывает, смена контрактов, радиус поражения). Модель везде одна, автор честно называет это разделением обязанностей, а не независимым ревью.

Каждая находка несёт location, summary, evidence, severity и status (open/reconciled/wontfix/false-positive). High требует сигнатуру метода и нарушенный контракт либо конкретный путь выполнения; недоказанные догадки режутся до medium. collect-metrics валидирует JSON и считает метрики; отчёт code-review.md в части фактов рендерится из JSON и перепроверяется. Блокируют слияние упавшая обязательная проба и открытые high. Покрытие строк ниже line_target (85) блокирует, ветвей - только совет. Результаты скромные: на 11 Java-кейсах найдено 5 из 7 целей, 0 подтверждённых ложных срабатываний; сравнения с одиночным ревью нет.

У тебя уже есть /code-review, vendor-review и quality-gates, так что нового тут только схема «JSON как источник истины для гейта» и правило доказательств. Первый шаг: npx -y skills add kyy-logs/code-review-skill --agent claude-code --skill code-review --yes в тестовом проекте, затем «Review these changes with code-review».

Что взять себе
  • Взять правило доказательств: high-находка в ревью-скиллах только с сигнатурой и нарушенным контрактом или путём выполнения, иначе максимум medium - добавить в vendor-review и quality-reviewer?
  • Гейт из JSON: пусть ревьюеры пишут находки в JSON со status, а `claude -p --json-schema` или скрипт считает блокировку (открытые high) и рендерит факты отчёта - сделать так в feature-build?
  • Поставить скилл в тестовый проект и сравнить его находки на одном диффе с нашим /code-review и vendor-review - у автора такого сравнения нет.

Codex CLI 0.167.0: командный центр агентов, переключение бэкендов и ревью патчей прямо в запросе одобрения

Вышел Codex CLI rust-v0.167.0 (6 ноября). Главное: `codex agents --no-daemon` открывает командный центр агентов. Он и выбор сессии помечают непрочитанные результаты (#58238, #58239, #58263, #58264). Задачи в центре сортируются по давности внутри групп статусов. Из терминального выбора сессий можно переключаться между подключёнными бэкендами, черновики сохраняются (#58280, #58457). В запросе одобрения можно развернуть детали патча (#58281). Локальные картинки показываются превью при наборе, пути к просмотренным изображениям кликабельны. В меню «Sign in another way» есть API-ключ и облачные провайдеры. Флаг `gcp_setup_wizard` включает настройку Vertex AI через Application Default Credentials или файл ключа. Системный прокси macOS/Windows включается в `/experimental`.

Из внутренностей: Guardian-ревью теперь проверяет записанные вызовы exec напрямую, а PreToolUse-хуки срабатывают до проверки политики прямого ревью (#58368). Родительские связи субагентов сохраняются до создания хранилища потомка, а в выборе субагентов приоритет у ожидающих одобрения (#58129, #58720). Авто-сжатие контекста учитывает вывод неудачных ответов (#58404). Для тебя это в основном второе мнение: у тебя Codex уже стоит как кросс-вендорное ревью, а свой оркестратор есть в Claude Code. Командный центр — другой подход к тому же, где один экран показывает всех агентов и непрочитанное. Первый шаг: обновить Codex и запустить `codex agents --no-daemon`, посмотреть, удобнее ли это, чем фоновые агенты у тебя.

Что взять себе
  • Обновить Codex и запустить `codex agents --no-daemon`, сравнить обзор параллельных агентов с нашими фоновыми агентами и SendMessage
  • Взять идею «непрочитанных результатов»: в хуке Stop или SessionStart помечать, какие фоновые агенты закончили, а результат ещё не прочитан
  • Для use-codex и vendor-review: если Codex гоняется через Vertex AI, включить `gcp_setup_wizard` и проверить, подходит ли это как отдельный бэкенд

Poki: локальный MCP-сервер, чтобы Claude Code управлял настоящим iPhone без джейлбрейка

Poki (JosssphZhou/poki, AGPL-3.0, создан 5 ноября 2026, 314 звёзд, релиз v0.1.1) даёт агентам управлять реальным iPhone. Внутри два компонента: локальный MCP-сервер и отдельный терминальный Poki Agent, который можно запускать и через iMessage или Telegram. Джейлбрейк и дополнительное железо не нужны: Mac связывается с телефоном через idevice-инструменты (для физических устройств, нужна USB-пара) или через адаптер симулятора. Список инструментов вынесен в docs/tools.md, в README виден только пример list_devices. Poki запоминает прошлые задачи и выполняет повторные быстрее.

Требования: macOS 15+, Xcode, Node.js 24+, ffmpeg; готовый пакет только для Apple Silicon. Ограничения: на физических телефонах проверен только китайский интерфейс, только портретная ориентация. Содержимое экрана уходит в настроенную модель, а просьбу отправить сообщение или оплатить Poki выполнит.

Для тебя это способ дать Claude Code руки на мобильном: проверять iOS-приложения, гонять сценарии на симуляторе, подключив так же, как Chrome MCP. Начни с симулятора, не с личного телефона: git clone, ./bin/setup, npm start, затем claude mcp add (точная команда в README), вызови list_devices.

Что взять себе
  • Подключить Poki как MCP рядом с Chrome MCP, но только на симуляторе, и проверить, что list_devices его видит
  • Если дойдёт до физического телефона: завести отдельный тестовый iPhone/аккаунт и PreToolUse-хук, требующий подтверждения на отправку сообщений и платежи, раз Poki делает их без вопросов
  • Сделать скилл по образцу browser-use для iOS: основная сессия не зовёт инструменты Poki сама, а отдаёт задачу сабагенту, чтобы скриншоты не раздували контекст
