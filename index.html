uncut: минимальный headless-агент на Go, который никогда не обрезает файлы и вывод команд

uncut (Balanov/uncut, MIT, v0.1.1) — один статический бинарник около 7 МБ, 837 строк на Go. Без TUI, телеметрии, плагинов, фоновых агентов, автоповторов и компакции контекста. Четыре инструмента: read_file (файл целиком, UTF-8), write_file, replace (ровно одно вхождение, ноль или несколько — ошибка), run_command (код выхода и полный stdout+stderr). Вся история уходит в модель на каждом вызове. Если ответ оборван лимитом вывода, агент выходит с кодом 3, а не выдаёт обрезок за результат; бинарные файлы и невалидный UTF-8 отклоняются, а не портятся подменой байтов. Коды выхода: 0 успех, 1 ошибка, 2 неверные флаги, 3 обрыв по длине, 4 достигнут --max-steps (по умолчанию 32). Работает с любым OpenAI-совместимым Chat Completions (OpenRouter, Ollama; проверено на qwen3:8b), без стриминга и картинок. Не песочница: команды идут с правами вашего пользователя. Флаги: --json (NDJSON-события), --session файл.jsonl (append-only, возобновление), --cwd, --no-agents, --request-timeout. Цифры бенчмарков в README нет, они в BENCHMARKS.md, которого я не видел; bench/proof.py проверяет только транспорт, не качество модели.

Для вас это не замена Claude Code, а референс детерминированного headless-слоя для локальных моделей (MLX/Ollama) и пайплайнов вроде git diff | uncut "Review this diff". Полезны идеи: жёсткие коды выхода на обрезанный ответ и лимит шагов. Первый шаг: скачать uncut-darwin-arm64 из релиза v0.1.1, сверить checksums.txt, затем UNCUT_BASE_URL=http://localhost:11434/v1 UNCUT_MODEL=qwen3:8b uncut "Explain this repository".

Что взять себе
  • Взять из uncut правило «обрезанный ответ = ошибка»: в наших скриптах с claude -p --json-schema проверять stop_reason и падать с отдельным кодом, а не принимать частичный результат — добавить в скилл loop-design?
  • Добавить в скилл loop-design лимит шагов с отдельным кодом выхода (как --max-steps → exit 4) для cron- и fix-until-green-агентов?
  • Прогнать uncut на локальной модели через Ollama/OpenAI-совместимый сервер MLX как лёгкий агент для пайплайнов (git diff | uncut ...) и сравнить с opencode?
  • Сделать для наших headless-скриптов проверку вроде bench/proof.py: детерминированный фейковый провайдер, который проверяет большие файлы, обрыв и возобновление сессии без API-ключа?

ai-design-check: 87 правил дизайна и чекер без зависимостей для интерфейсов от ИИ-агентов

Репозиторий enmerasoftware/ai-design-check (MIT, 178 звёзд, создан 28 октября 2026) — набор из 87 правил, по которым интерфейс «выглядит сгенерированным», плюс чекер на чистом Node 20+ без зависимостей и без API-ключа. Покрывает веб (.tsx, .jsx, .vue, .svelte, .html, Blade, CSS, i18n JSON), SwiftUI и Jetpack Compose. 50 правил проверяются автоматически, 37 требуют ревью человеком или агентом. Правила на английском и турецком: доступность, типографика, тексты, компоненты, лейаут, анимации, локализация. Для мобильных: отступы вне сетки 4 pt, радиусы вне шкалы, фиксированный текст без Dynamic Type, тап-зоны меньше 44 pt / 48 dp. Классовые правила читают только строки class/className/cn()/clsx()/cva(), поэтому комментарии не срабатывают. Игнор без причины после `--` не засчитывается. Результаты из README: дашборд 266 находок → 0, iOS-приложение 23 → 0. Есть команды inventory, narrow (проверка на 320 px, нужен Chrome), story (видео до/после, Chrome и ffmpeg), system, --write-baseline.

У тебя уже есть хуки, скиллы и скилл frontend, так что нового тут — готовое содержимое: набор правил и детерминированный чекер. Хук в README: PostToolUse на `Edit|Write|MultiEdit`, команда `npx -y @enmera/ai-design-check hook`; чистые файлы молчат, находки идут в stderr с кодом 2, и агент сразу правит. Скилл `ai-design-fix` по описанию не удаляет контент ради снижения счёта. Первый шаг: `npx @enmera/ai-design-check` в проекте с UI, затем `npx @enmera/ai-design-check --write-baseline`, чтобы видеть только новые находки.

Что взять себе
  • Добавить в .claude/settings.json хук на Edit|Write|MultiEdit с `npx -y @enmera/ai-design-check hook` (exit 2 с находками в stderr) для UI-проектов — как ещё один гейт в quality-gates?
  • Подключить RULES.md (node_modules/@enmera/ai-design-check/RULES.md) или список `rules` в скилл frontend как проверочный список для сгенерированного UI?
  • Перенять приём из `ai-design-fix`: агент отчитывается числом находок до/после и не удаляет контент ради снижения счёта — добавить это условие в наши скиллы по правке UI?
  • Прогнать `narrow page.html --width 320` на странице бота/лендинга, чтобы проверить длинные тексты на узком экране?

Скилл stack-diagram: рисует архитектурную схему стека с официальными логотипами по описанию в одну фразу

caru-ini/stack-diagram — скилл для агентов (Claude Code, Codex, Cursor и др.), созданный 1 ноября 2026, уже 737 звёзд, лицензия MIT. Описываешь стек одним-двумя предложениями (например, Next.js и Hono на Vercel с Neon, Clerk, Stripe и GitHub Actions), агент сам скачивает логотипы, прокладывает линии связей в обход подписей, рендерит схему и проверяет результат перед выдачей.

Логотипы берутся по очереди из svgl, devicon, gilbarbara/logos или из репозитория самого бренда; иконки AWS — из официального пакета AWS. Они скачиваются при сборке, не вшиты в репозиторий, скрипты их не перекрашивают и не перерисовывают. Форматы: самодостаточный HTML со встроенными шрифтами и логотипами (по умолчанию), PNG, React-компонент без зависимостей и Claude Artifact; есть светлая и тёмная темы. Нужны Python 3.9+ и сеть; для PNG — Playwright с Chromium. Агент может предложить выложить схему в публичную галерею stacks.caru.moe, но только после двойного подтверждения, промпт при этом не отправляется.

Для твоего сетапа: у тебя уже есть Artifacts и Remotion, а этот скилл закрывает узкую задачу — быстрые схемы архитектуры для README, review-page или описаний тикетов без ручной вёрстки. Первый шаг: `npx skills add caru-ini/stack-diagram`, затем попросить схему своего бота (Telegram + Claude Code + MCP) и посмотреть на HTML.

Что взять себе
  • Поставить `npx skills add caru-ini/stack-diagram` и сгенерировать схему бота (Telegram + Claude Code + MCP-серверы) для manager/ или README.
  • Подключить скилл к review-page: вставлять в страницу согласования плана схему архитектуры в виде самодостаточного HTML.
  • Перенять приём «рендерить и проверять результат перед выдачей» (проверка наложений подписей и линий) в наши скиллы для визуальных артефактов.

OmniDiff: быстрый структурный diff-инструмент на Rust для git, с JSON-выводом

OmniDiff (Rust, AGPL-3.0, v0.3.0, есть платная коммерческая лицензия) — это difftool, который понимает содержимое файлов. Код в 25 языках разбирается через tree-sitter и сравнивается по деревьям (APTED, при вырожденном дереве откат на Myers). Поэтому перенесённая функция показывается как перенос, а не как удаление плюс вставка. Бинарные форматы тоже сравниваются по смыслу: картинки по пикселям, архивы по файлам, шрифты по глифам, PDF по страницам. Скорость на 2302 фикстурах кода: p50 4,2 мс, p99 177 мс. Устойчивость: 99,95% из ~442 тыс. пар «до/после» из ~7500 репозиториев. Сбои — на огромных сгенерированных файлах (в обсуждении автор назвал переполнение стека tree-sitter). По собственным цифрам автора, difftastic идеален на 64% диффов, OmniDiff на 90%. Точность при этом заявленных целей пока не достигла: нулевое расхождение в 60% случаев (--full) и 69,6% (--minimal). Мёрж-конфликты (трёхстороннее слияние) не решены. Внешние PR не принимаются.

Для вашей связки интересен режим без TTY: --headless включается сам, когда stdout не терминал, есть --mode json (JSON Schema лежит в репозитории) и --exit-code. Агенты и хуки могли бы получать структурный diff вместо построчного шума. Проект сам написан с Claude Code, в репозитории есть AGENTS.md. Первый шаг: brew install ivankovic/omnidiff/omnidiff, затем omnidiff git configure или GIT_EXTERNAL_DIFF=omnidiff git diff (вывод будет текстом, без TUI).

Что взять себе
  • Попробовать GIT_EXTERNAL_DIFF=omnidiff git diff в большом рефакторинге с переносом кода и сравнить с обычным git diff по размеру и читаемости для ревьюера-сабагента.
  • Проверить omnidiff --mode json на реальном diff и решить, стоит ли подмешивать его в скиллы code-review и vendor-review, чтобы ревьюеры видели переносы функций, а не пары удаление/вставка.
  • Прогнать omnidiff на изменённых картинках, PDF и архивах (Remotion-кадры, ассеты) как побайтную проверку результата вместо сравнения на глаз.
