01Hacker News16.10

Команда Claude Code описала свой процесс ревью: многоагентный ревьюер с голосованием, REVIEW.md, риск-тиры и инциденты как eval

Anthropic (Addy Osmani и др., пост от 15 октября 2026) пишет, что Claude создаёт около 90% кода Claude Code. Поток изменений в монорепо вырос с ~2500 в день (май) до 30 000+ (сентябрь). Цель команды: минимум человеческого времени на ревью без роста реверта и инцидентов. Доля ревертов с июня по сентябрь упала более чем на 40%, а число мерженных PR выросло больше чем вдвое. Слой ревью устроен так: параллельные агенты ищут баги, отдельная группа голосует по каждой находке, публикуются только находки с достаточным согласием. Стиль и «уборка» отбрасываются. Комментарии помечаются Important, Nit или Pre-existing. Отдельный security-проход, и открытые находки блокируют мерж. Уровень одобрения людьми зависит от риска самого изменения, а не от автора: ноль, один или два человека. Одобрение агента не считается человеческим, одобрение привязано к конкретному коммиту. Репо-правила лежат в коротком CLAUDE.md и в REVIEW.md от владельцев кода: что считать провалом, лимит на nit, пути для пропуска, доказательство в виде файла и строки, сводка начинается со счёта. Каждый инцидент или ревёрт превращается в eval-кейс, на нём прогоняют ревьюера при смене промпта, инструментов или модели. Один PR прошёл 50+ раундов ревью за ночь, поэтому добавили лимит в 3 раунда, повторный просмотр только нового diff и запрет повторов. В HN-обсуждении сомневаются в цифрах и в SOC2, называют пост маркетингом и пишут про Goodhart.

Скрипты ревью в духе /code-review, ultrareview и cross-vendor у вас уже есть. Нового здесь три вещи: REVIEW.md, eval из инцидентов и защита от бесконечных циклов агент-автор против агент-ревьюер. Первый шаг: добавьте в один проект REVIEW.md с пунктами из поста (что считать провалом, лимит nit, пути для пропуска, требование file:line) и подайте его на вход своему ревью-скиллу.

Что взять себе
  • Добавить REVIEW.md в проекты и научить ревью-скилл его читать: что считать провалом, лимит nit, пути для пропуска, обязательные file:line, сводка начинается со счёта.
  • Завести папку eval-кейсов из своих ревёртов и багов и прогонять на ней ревью-скилл при смене промпта или модели: оставлять правку, только если счёт вырос.
  • Добавить в loop-design и ревью-пайплайн лимит в 3 раунда, повторную проверку только нового diff и запрет повторных находок, чтобы агент-автор и агент-ревьюер не зациклились.
  • Ввести в ревью-скилле метки Important, Nit, Pre-existing и голосование отдельных субагентов по каждой находке, отбрасывая находки без согласия.

02GitHub17.10

earshot: локальные «уши» для кодинг-агентов — MCP-сервер, который слушает, измеряет и синтезирует звук на CPU

earshot (Leonxlnx, MIT, создан 15.10.2026) — CLI, Python API и MCP-сервер, чтобы агент мог «слышать» аудио без GPU. Умеет: описывать звук (метки AudioSet, замеры), оценивать, насколько звук подходит текстовому описанию (CLAP), ранжировать файлы и искать лучшие моменты в длинной записи; отличать живую запись от синтезированной кодом; `measure` — громкость, true peak, спектр, темп/тональность без моделей; `timeline` — посекундная расшифровка фильма, `sheet` — аннотированная картинка, `critique` — оценка ролика по семи референсным фильмам. Плюс `forge` (синтез звука по рецептам с критиком и эволюционным отбором) и `fit` (рецепт, который воспроизводит запись).

Цифры из README: «сильное» совпадение при поиске по библиотеке — верный тип звука в 98%, точный вариант в 61%; real-vs-synth ROC-AUC 0.92; найдено ~93% эффектов в 60-секундном миксе. Слепые тесты маленькие: forge-звук выбирали 8 из 15 раз (≈случай). Не судит вкус, эмоции, речь, лицензии; в плотных миксах лишь намёки; критик forge может быть «доволен» без улучшения.

Для тебя: есть Remotion-пайплайн, montage, ElevenLabs и speak, а агент ревьюит звук вслепую. earshot даёт проверяемые метрики. Первый шаг: README (Python 3.10+, ffmpeg, CPU-torch, `pip install -e ".[mcp,llm,dev]"`), `earshot doctor --load` (первый запуск тянет ~1.4 ГБ моделей), затем `claude mcp add earshot` с python из venv и модулем mcp; MCP держит модели в памяти, без 20–40 с загрузки на вызов.

Что взять себе
  • Подключить earshot как MCP и добавить в скилл montage шаг: после рендера прогнать `measure` (громкость, true peak) и `timeline` перед отдачей ролика?
  • Дать visual-meaning-reviewer аудио-проверку: `critique`/`sheet` по готовому видео из Remotion против референсов?
  • Взять два готовых скилла из `skills/` репозитория (`earshot`, `real-sound`) как образец и адаптировать под наш пайплайн озвучки и саундтрека?
  • Учесть оговорку автора: метрикам доверять для громкости, тайминга и одиночных звуков, а вкус и естественность оставлять на ручное прослушивание — записать в правило скилла.

03GitHub17.10

Открытая реализация серверного контроля версий для агентов по описанию Anthropic: репозиторий gitai (graft)

feder-cr/git-ai (gitai, MIT, версия 0.1.0, создан 15 октября, 9 коммитов, 1.1k звёзд) — независимая реализация серверной схемы контроля версий из статьи Anthropic «Redesigning source control». Внутренняя система Anthropic Scion закрыта, проект с Anthropic не связан. Клиенты (агенты, CI, sparse-воркспейсы) ходят по gRPC на сервер, возможно через демон graft-cache. Сервер ведёт лог изменений в SQLite/PostgreSQL, объекты лежат в file/S3/GCS/Azure, локальные git-репозитории — просто пересобираемый кэш. Сервер сам модели не вызывает.

Что умеет: sparse-выгрузка только нужных путей, blame, история и поиск по коду на сервере, приземление изменений без merge queue (ребейз на tip и compare-and-swap с батчингом), разрешение конфликтов подключаемым резолвером (любой LLM, детерминированный инструмент или никакого), тесты после landing с бисекцией и автооткатом виновника, токены на агента, allowlist RPC, политики веток. Лимиты: интерфейсы могут меняться до 1.0, известные пробелы в LIMITATIONS.md (например, GC паков), нужны Go 1.26, Meson, Ninja, сборка собственного Git, основан на форке Gitaly.

Для тебя это скорее справочный материал: твои worktree на писателя решают ту же проблему параллельных агентов проще, а gitai нужен при десятках агентов на одном монорепо. Первый шаг: git clone https://github.com/feder-cr/git-ai.git && cd git-ai && make build && examples/graft/quickstart.sh — поднимет сервер, кэш, двух агентов и один land во временной папке.

Что взять себе
  • Автооткат после landing: бисекция и revert виновного коммита — добавить такой шаг в наши fix-until-green циклы (loop-design) или в Stop-хук после мержа веток писателей?
  • Лог каждого обновления ссылки с указанием агента и операции — завести такой журнал (commit-trailer или файл) для наших worktree-писателей, чтобы видеть, какой субагент что приземлил?
  • Токен и allowlist на агента — прикинуть, нужна ли аналогичная узкая политика прав для субагентов в наших agent-файлах?

04ty releases16.10

ty 0.0.89: опциональный вывод типов возвращаемого значения для функций без аннотаций

ty — type checker от Astral для Python. В релизе 0.0.89 (16.10.2026) появился вывод возвращаемого типа для функций и методов без аннотации (#29253). По умолчанию он выключен, включается настройкой analysis.return-type-inference = "always". В pyproject.toml: [tool.ty.analysis] return-type-inference = "always"; в ty.toml: [analysis] return-type-inference = "always". Авторы просят сообщать о проблемах в issue astral-sh/ty#4739.

Кроме того: обновлён vendored typeshed (#29402); исправлена паника при отрицании динамических type alias (#29427); длины tuple-литералов расширяются, если другие элементы коллекции содержат вложенные tuple (#29147); ty теперь сообщает о неверных аргументах Generic и Protocol с вложенными variadic type variables (#29146); ускорено сужение типов для generic class-pattern (#29240).

Для твоего стека это полезно, если в FastAPI/Celery-коде много хелперов, сервисных функций и тестов без аннотаций: ty начнёт видеть их результат и ловить ошибки на вызовах, не требуя правок кода. Это ранняя функция, поэтому ложные срабатывания возможны. Первый шаг: добавить в pyproject.toml секцию [tool.ty.analysis] с return-type-inference = "always", прогнать ty check на одном сервисе и сравнить число диагностик до и после.

Что взять себе
  • Включить return-type-inference = "always" в [tool.ty.analysis] на одном сервисе и сравнить число диагностик до/после - сделать это?
  • Если найдутся ложные срабатывания, завести отчёт в astral-sh/ty#4739 с минимальным примером - добавить это в чек-лист обновления ty?
  • Закрепить версию ty 0.0.89 в dev-зависимостях и обновить typeshed-зависимые проверки вместе с ней - сделать?
