Репозиторий с CLAUDE.md и тремя промптами: план, критика плана в свежем контексте, аудит git diff

Vaibhav выложил личный набор инструкций для кодинг-агентов (172 звезды, один коммит, MIT): `CLAUDE.md` с 10 принципами и три промпта в `prompts/`. Часы работы (4500+) автор называет прикидкой, не телеметрией. Ядро: Stage 1 `planning.md` — план с критериями приёмки и способом проверки каждого, затем жёсткая остановка до одобрения. Stage 2 `critical-plan-review.md` — в свежем контексте или сабагенте «придирчивый principal engineer» ищет гонки, отсутствие таймаутов, идемпотентность, оверинжиниринг, с «YAGNI-тормозом», отделяющим реальные сбои от гипотетических. Stage 3 `production-readiness-review.md` — свежий контекст смотрит сырое git-состояние (`git status`, `git diff`, `git diff --cached`, неотслеживаемые файлы): баги, null, утечки секретов, забытые артефакты. Маршрутизация: spike (одна проба и два предложения вывода), bounded (1–3 файла, автономно), architectural (весь пайплайн). Согласование с человеком нужно для миграций схемы, публичных API, новых зависимостей и деструктивных команд. Автор честно пишет, что эти гейты лишь инструкции, а не защита; настоящее ограничение дают permissions инструмента. Остальное — ссылки на superpowers, Ponytail и i-have-adhd.

Для тебя это в основном знакомое: feature-build, subagents, vendor-review, superpowers, i-have-adhd, grilling уже есть, а Workflow делает такой пайплайн сильнее. Нового мало: лесенка Ponytail (YAGNI → существующий код → stdlib → платформа → установленные зависимости → минимум кода) и «YAGNI-тормоз» в ревью плана. Первый шаг: прочитать `prompts/critical-plan-review.md` и `production-readiness-review.md` и сравнить с промптами ревьюеров у себя (quality-reviewer, business-reviewer).

Что взять себе
  • Добавить в code-style или CLAUDE.md лесенку Ponytail: YAGNI → существующий код → stdlib → платформенные API → уже установленные зависимости → минимум кода, плюс правило «чинить причину у вызывающего, не оборачивать симптом»?
  • Добавить «YAGNI-тормоз» в промпт ревьюера плана (review-page / feature-build stage 3): отделять реальные режимы отказа от маловероятных гипотез?
  • Заставить финальный ревьюер смотреть сырое состояние (`git status`, `git diff`, `git diff --cached`, неотслеживаемые файлы), а не пересказ implementer'а — проверить, так ли это в quality-reviewer?

FastAPI 0.163.0: у Depends появился параметр max_concurrency для лимита параллельных вызовов зависимости

Релиз FastAPI 0.163.0 вышел 14 ноября 2026. В нём одна заявленная фича: «dependency concurrency limits» — параметр Depends(max_concurrency=...), PR #16746 от @tiangolo. Судя по названию, он ограничивает число одновременных вызовов зависимости. Сам PR влит в master 14 ноября, помечен feature, описан в разделе документации Advanced Dependencies; в описании сказано, что изменение сделано с помощью ИИ и проверено вручную. Тесты на конкурентность есть.

Чего на страницах релиза и PR нет: что именно происходит при превышении лимита (ожидание в очереди или ошибка), лимит на зависимость или глобальный, работает ли для sync-зависимостей. Не выдумываю — это надо читать в доке. Также в релизе упомянут официальный skill для кодинг-агентов, который подсказывает фичи под установленную версию: ставится командой uvx library-skills.

Для твоего стека это потенциально удобный способ защитить узкие места (пул SQLAlchemy/PostgreSQL, внешний API, Redis) без самописных asyncio.Semaphore. Первый шаг: обновиться до 0.163.0, прочитать страницу /advanced/advanced-dependencies/ и проверить поведение при превышении лимита тестом на pytest до применения в проде.

Что взять себе
  • Прочитать /advanced/advanced-dependencies/ и выяснить, что делает max_concurrency при превышении лимита, прежде чем заменять им свои Semaphore
  • Написать pytest-тест на зависимость с max_concurrency, которая оборачивает вызов внешнего API или пул БД, и проверить поведение под параллельной нагрузкой
  • Поставить uvx library-skills в проект, чтобы агент подсказывал фичи под установленную версию FastAPI
