lend: агент на удалённой VM запускает команды на ноутбуке после Touch ID, секреты не покидают ноутбук

lend (blog.antonio.cx, Hacker News, 100 очков, 57 комментариев) встаёт перед SSH-агентом: на VM пробрасывается его сокет вместо настоящего. Запрос (команда или SSH-подпись) идёт на ноутбук в `lend agent`, проверяется по локальной политике (по умолчанию deny), затем подтверждается, обычно Touch ID (`biometric:inline`). Одобренная команда выполняется локально, stdout, stderr и код возврата возвращаются агенту. Правило называет исполняемый файл и может ограничивать подкоманды через `args_prefix`. `secret_reader` (например `op read`) подставляет секрет в env (`GH_TOKEN`) только в одобренную команду, VM значения не видит. SSH-ключи фильтруются по отпечатку, `max_signatures` ограничивает число подписей за сессию. Есть lease: одобрение на время или число использований для точно той же команды. Команды: `lend ssh --config policy.json -- host`, `lend mcp` (инструмент `run_local_command` с обязательной причиной), `lend exec --reason`, `lend doctor`, `lend pause --all`, `lend history`, `lend approve` (маршрутизирует запросы разрешений, например `PermissionRequest` hook Claude Code, на ноутбук). Ограничения: нет песочницы, одобрение shell, `env` или `op` даёт широкий доступ; stdin в запросе не виден; нет PTY; биометрия только macOS; проект ранний. В комментариях критикуют: диалог даёт мало контекста, агент может выпустить новые токены, секреты утекают в транскрипты. Альтернативы: отдельный аккаунт агента, короткоживущие токены, прокси с подменой плейсхолдеров.

Для тебя: близкое у тебя уже есть в скилле secrets (Keychain/Vault по алиасу без вывода) и PreToolUse-хуках, но схемы «агент на удалённой машине, секреты и подпись остаются дома, подтверждение на устройстве» нет. Актуально, если гоняешь агентов на RunPod или VM. Первый шаг: `brew install antoniomika/tap/lend`, затем `lend doctor` и `lend ssh --config policy.json -- host` с политикой на один `gh`-подкомандный префикс.

Что взять себе
  • Для агентов на RunPod/VM поставить lend и прогнать `lend ssh --config policy.json -- host` с политикой на один префикс `args_prefix`, секрет через `secret_reader` из твоего Keychain.
  • Подключить `lend approve` к `PermissionRequest` hook Claude Code, чтобы запросы разрешений от удалённых сессий приходили на ноутбук с Touch ID.
  • Добавить в скилл secrets правило из статьи: не одобрять shell, `env`, `op` как команды, только узкие префиксы, и лимит `max_signatures` для SSH-ключей.

Скилл для Claude Code: пошаговая разгонка скорости локального LLM-сервера с замерами и стабильностью

sybil-solutions/inference-optimisation-skill (MIT, создан 16 ноября 2026, 408 звёзд) — скилл, который ведёт агента по оптимизации локального сервера: декод, спекулятивный декодинг, prefill, размер KV, старт и TTFT. Процедура из шести шагов: посчитать теоретический потолок (байты на токен / пропускная способность, FLOPs, лимит KV), менять одно за раз, мерить против чередующихся контрольных запусков, логировать все результаты, включая неудачи, проверить поиск в длинном контексте (needle), собрать чистый зафиксированный билд. Изменение принимается, только если лучше обоих соседних контролей и ничего не просело больше чем на 3%. Перед словом «лучший» нужен needle-тест и параллельный soak на полном KV.

Внутри: SKILL.md (процедура, правила остановки), references/ (подгружаются по требованию), scripts/ на стандартной библиотеке: bench.py для любого OpenAI-совместимого сервера, ceiling.py, queue.sh (A/B с чередованием), mem.sh. Движки: vLLM, SGLang, llama.cpp, ExLlama. Примеры: Intel Arc B390 43.6→53 tok/s, старт 113→43 с; Arc Pro B70 91.2 tok/s на vLLM против 25.0 на llama.cpp Q4_K_M; RTX 3090 96–141 tok/s; 4×H200 229 tok/s. Шум одного замера ±5–10%; результаты привязаны к железе, Apple MLX в результатах нет.

Для тебя: прямой пользы для MLX мало, но это готовый образец цикла «потолок → один рычаг → контроль → лог» и полезен для RunPod-запусков llama.cpp. Первый шаг: git clone https://github.com/sybil-solutions/inference-optimisation-skill, затем cp -r inference-optimisation-skill/skills/inference-optimisation ~/.claude/skills/ и прогнать bench.py на своём локальном сервере.

Что взять себе
  • Правило приёмки «лучше обоих соседних контролей и не хуже чем на 3% по остальному» добавить в loop-design для циклов с замерами
  • Взять bench.py (любой OpenAI-совместимый сервер) для замеров локальных моделей на MLX и llama.cpp на RunPod вместо ручных прогонов
  • В use-runpod добавить needle-тест длинного контекста и soak на полном KV перед тем, как считать конфиг рабочим

OpenCode выпустил Browse: MCP-сервер и расширение, которое даёт агенту ваш настоящий Chromium-браузер

OpenCode Browse — это MCP-сервер плюс расширение для Chromium-браузеров (Chrome, Edge, Brave, Arc, Helium, Vivaldi, Opera). Агент работает в вашем реальном профиле: с открытыми вкладками, логинами и расширениями, без API-ключей. Его вкладки открываются в фоне, в свёрнутых группах. Умеет читать страницы, кликать, печатать, делать скриншоты, записывать вкладки и сетевой трафик. Для логина, 2FA и оплаты агент возвращает вкладку вам и продолжает после кнопки Continue. Можно «одолжить» агенту уже открытую вкладку и ограничить его списком сайтов. Работает с Claude Code, Codex, Cursor, Zed и OpenCode. Цен и лимитов на странице нет.

В обсуждении на HN (224 очка, 119 комментариев) отмечают: соединение расширения часто отваливается, Firefox и Safari не поддерживаются, CDP-браузер могут определить как бота, а залогиненный профиль открывает путь для prompt injection со страниц, поэтому советуют отдельный профиль. Больше споров о самом OpenCode V2 (нет запросов разрешений, ломающиеся конфиги), к Browse это не относится. Для вас это аналог claude-in-chrome, который у вас уже есть, но не привязанный к Claude. Новое здесь: ограничение по сайтам и запись сети и вкладок. Первый шаг: `npm install -g @opencode/browse && browse install`, затем подключить к Claude Code как MCP и сравнить с claude-in-chrome на одной задаче с логином.

Что взять себе
  • Поставить `npm install -g @opencode/browse && browse install` и сравнить с claude-in-chrome на задаче с логином (например, avito-скилл)
  • Взять идею ограничения агента списком сайтов: добавить в browser-use скилл или хук правило, на какие домены агенту можно заходить
  • Завести отдельный Chrome-профиль для агентов, чтобы prompt injection со страниц не добрался до основных аккаунтов
