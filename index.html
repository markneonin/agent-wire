Nari Labs выложила Qwen3.8-27B в 3 битах (10 GB), который на их бенчмарках держится на уровне BF16

NariQ - квантизация Qwen3.8-27B (vision-language) в 3.0 / 2.5 / 2.0 бита на вес: 10.12 / 8.44 / 6.75 GB против 53.8 GB в BF16. Метод - trellis-coded PTQ на базе QTIP, калибровка на реальных трассах кодинг-агентов; vision tower остаётся в BF16, MTP-модуля пока нет. По собственным замерам авторов (Claude Code как harness): DeepSWE 41.0 против 39.8 у BF16, Terminal-Bench 2.1 63.8 против 62.6, AIME 98.3 против 97.7. 2.5 bpw чуть слабее на Terminal-Bench (60.2), 2 bpw заметно хуже (DeepSWE 28.6). Лицензия Apache-2.0.

Ограничения серьёзные: нужен форк nari-llama.cpp, Ollama/LM Studio/stock llama.cpp не грузят; быстро только на NVIDIA (RTX PRO 6000: ~89 tok/s при 4K и ~71 при 64K), на M3 Pro всего ~3.8 tok/s. На 24 GB влезает ~135K контекста. В обсуждении HN: сравнение с Unsloth снято с графиков и на другом harness, часть выигрыша может быть от harness, а не от модели. Для тебя это скорее справка: твои MLX-модели на Маке на таком не поедут, но для RunPod/Linux с NVIDIA это способ гонять 27B-агента на одной 24 GB карте. Первый шаг: на GPU-поде `curl -fsSLO https://github.com/nari-labs/nari-llama.cpp/releases/download/b12431-nariv0/run.sh && bash run.sh 3.0`, затем llama-server с `--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`.

Что взять себе
  • Проверить через runpod-скилл, что NariQ 3.0bpw на 24 GB карте (L4/A10, ~135K контекста) тянет Claude Code как локальный бэкенд для дешёвых фоновых задач, и сравнить с Sonnet на 3-5 своих задачах.
  • Авторы калибровали квант на реальных трассах кодинг-агентов и мерили на DeepSWE и Terminal-Bench 2.1 - взять эти два бенчмарка как образец для оценки локальных моделей в нашем скилле vendor-review.
  • Добавить в use-runpod заметку: форк nari-llama.cpp, `run.sh 3.0`, флаги сэмплинга `--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0`, `-c 131072` для 24 GB.

agent-sim запускает iOS-симулятор на обычном Linux x86-64, и агент тестирует приложение без Mac

agent-sim (Developing-Gamer, 270 звёзд, создан 21.11.2026, Apache-2.0, автор честно пишет, что проект ранний и с шероховатостями) гоняет симулятор iOS от Apple на Linux без Mac и GPU. Под капотом x86Sim (запускает arm64-рантайм симулятора на x86-64), Darling как слой ядра macOS, dynarmic для трансляции ARM и CPU-Vulkan от Mesa с metal2vulkan для Metal. Агент ставит .ipa, читает экран как текст (`snapshot`, есть `--json`), нажимает `tap` по ref элемента, тексту или координатам, плюс `type`, `scroll`, `swipe`, `screenshot`, `logs`, `record`. Каждое действие возвращает новое состояние экрана. Есть пул телефонов (`pool up/take/release`) и трансляция в браузер (`serve --listen`, H.264 по WebSocket).

Цифры из README: загрузка 12–30 с, касание около 14 мс, скролл около 55 fps на Zen 5. Три телефона занимают 6,8 ГБ с KSM против 8,7 ГБ без него. Нужны Ubuntu 24.04, 8+ CPU, 16 ГБ RAM, 60 ГБ диска; setup около 30 минут и качает 8 ГБ рантайма от Apple. Ограничение: сборки должны быть нешифрованными (не из App Store: нужен Ad Hoc, Development, Enterprise или simulator build). Полный список проблем в KNOWN_ISSUES.md, которого на странице нет.

Для тебя: это готовый MCP-сервер, так что Claude Code получит глаза и руки для iOS-приложений на RunPod или любом Linux-боксе, без Mac. Подходит для проверки мобильных фич в цикле fix-until-green. Первый шаг: поставить через `install.sh` из репозитория на Ubuntu 24.04, выполнить `agent-sim setup`, `agent-sim up`, `agent-sim snapshot`, затем подключить `agent-sim mcp` как MCP-сервер.

Что взять себе
  • Поднять agent-sim на RunPod-поде с Ubuntu 24.04 (8+ CPU, 16 ГБ, 60 ГБ) и подключить `agent-sim mcp` к Claude Code как ещё один MCP-сервер рядом с Chrome
  • Взять из репозитория `SKILL.md` как основу своего скилла для iOS-тестов: `snapshot` → `tap` по ref → снова `snapshot`
  • Использовать `pool take/release` для параллельных субагентов, по одному телефону на агента в worktree
  • Проверить заранее, что у приложения есть simulator build или Ad Hoc .ipa, так как App Store сборки не запустятся

AWS выложил codekb: семантический поиск и граф вызовов по многим репозиториям через MCP

awslabs/codekb (создан 2026-11-12, 169 звёзд) — сервис «понимания кода» сразу по многим репозиториям, для людей и агентов. Один контейнер отдаёт веб-UI, REST API и MCP-сервер. Всё работает в вашем AWS-аккаунте: Bedrock (LLM, Guardrail, эмбеддинги Titan V2), S3 Vectors, S3, KMS для Git-токенов.

Пайплайн: добавляете «space» (Git URL или zip) → Tree-sitter разбирает символы и строит граф вызовов → LLM описывает каждую функцию (Guardrail маскирует секреты и PII), Titan делает эмбеддинги → семантический поиск по смыслу, затем обход callers/callees. Обновление инкрементальное: перепарсятся только изменённые файлы, затронутые вызывающие функции переописываются; при сбое остаётся прошлая версия. «Hyperspaces» группируют связанные репозитории; есть чат-агент Agent Hopper с режимом Impact Analysis. MCP-клиенты: Kiro и Claude Code. Лимиты: снимок одной ветки/тега на одном коммите, без истории; до 10 000 файлов, файлы >10 МБ пропускаются, клон до 5 минут, 32 фоновых задачи (CODEKB_PIPELINE_POOL_SIZE). Бенчмарков в README нет.

Для вас это пересекается с codebase-memory MCP (граф кода), новое здесь — межрепозиторный поиск по смыслу и привязка к Bedrock/AWS, так что без AWS-аккаунта смысла мало. Первый шаг: прочитать docs/local.md в репозитории (одиночный локальный запуск, нужен доступ к Claude на Bedrock и Titan Text Embeddings V2) и подключить его MCP к Claude Code.

Что взять себе
  • Если есть AWS: поднять codekb локально по docs/local.md и подключить MCP к Claude Code рядом с codebase-memory — сравнить на задаче через несколько репозиториев.
  • Взять приём «LLM описывает каждую функцию бизнес-языком, эмбеддинг описаний, потом обход графа вызовов» — добавить в скилл code-investigation шаг поиска по смыслу перед grep.
  • Взять Impact Analysis (кто затронут изменением по callers) как шаг в feature-build перед правкой общих функций — добавить?

safe-anything: сканер уязвимостей на Rust, который проверяет и конфиги AI-агентов (hooks, skills, MCP)

safe-anything (erkamyaman, MIT, 100% Rust, репозиторий создан 22.11.2026) — CLI-сканер без конфига и аккаунта. Ищет SQL/command-инъекции, XSS, eval, path traversal, SSRF, небезопасную десериализацию, слабую криптографию (9 языков + SQL), утёкшие секреты (в выводе маскируются), проблемы Docker, GitHub Actions, Kubernetes, Terraform, nginx, Android/iOS, а зависимости из lock-файлов сверяет с OSV.dev. Всего 75 правил с CWE/OWASP. На Juice Shop: 67 находок в 1195 файлах за ~0,03 с на M4; на express: 0 из 216 файлов. Самое шумное правило — code.xss-inner-html.

Для нас интересен блок AI-конфигов: он разбирает настройки Claude Code, Codex, Cursor, Gemini, OpenCode, MCP, hooks и skills. Ловит bypassPermissions, заранее разрешённый Bash, незапиненные npx/uvx/docker MCP-серверы, токены MCP открытым текстом, `curl | sh` в hooks, skills, читающие ~/.ssh, и невидимый Unicode в инструкциях. Ограничения: это поиск паттернов без трассировки данных, чистый скан не значит безопасный код. Единственный сетевой вызов — OSV.dev (имена и версии пакетов), отключается `--offline`. У нас уже есть quality-gates и vendor-review, но проверки именно агентского конфига нет, а у нас много своих skills и hooks. Первый шаг: `npx safe-anything .` в корне репозитория с .claude, затем `safe-anything --list-rules`, чтобы увидеть правила для агентов.

Что взять себе
  • Прогнать `npx safe-anything .` по репозиторию с .claude (hooks, skills, settings) и разобрать находки по агентским правилам
  • Добавить `safe-anything --offline --fail-on high` как проверку в скилл quality-gates или pre-commit: код выхода 1 при high/critical
  • Подключить `safe-anything mcp` как MCP-сервер (tools `scan`, `list_rules`) и проверять им сторонние skills и плагины перед установкой

open-diagram: Python-библиотека архитектурных схем, которая сама падает с LayoutError при кривой раскладке

open-diagram (MIT, создан 2026-11-18, 372 звезды, 37 коммитов) — Python-библиотека для плотных архитектурных диаграмм, рассчитанная на агентов (Claude, Codex, Cursor) и людей. Схема описывается коротким скриптом: Diagram, Panel, Tile, d.right_of(...) для размещения, d.link(a, b, kind=, label=) для связей. d.save("name") пишет SVG и PNG, печатает сводку и бросает LayoutError, если нашёл проблемы: блоки слишком близко, линия пересекает панель. В сообщении названы конкретные блоки и подсказан фикс: via_x/via_y для маршрута линии, сдвинуть блок или cross_ok=True. Автоматически раскладку библиотека не чинит, только сообщает.

Ширина подписей считается по метрикам и кернингу шрифта (Inter в комплекте), текст рисуется контурами, поэтому SVG одинаково открывается в браузере, PowerPoint, Keynote и Figma. Подписи вынесены в списки в начале скрипта. Есть импорт JSON и Mermaid, CLI, GitHub Action, иконки облаков и шаблоны; PNG требует Chrome, Chromium или Edge (переменная CHROME).

Для тебя это готовый цикл «агент рисует, проверка падает, агент правит»: ошибка с именами блоков заменяет разглядывание картинки. Полезно для схем в spec/review-page и README. Первый шаг: pip install open-diagram, затем claude mcp add с uvx для open-diagram-mcp (точная команда в README) и прогнать python3 examples/<name>.py.

Что взять себе
  • Подключить open-diagram-mcp через claude mcp add (uvx) и дать диаграммы субагенту, чтобы схемы в review-page строились кодом, а не рисовались вручную
  • Добавить в скилл review-page правило: схема архитектуры собирается через open-diagram, и save() должен проходить без LayoutError до показа владельцу
  • Взять приём «самопроверка с именованными блоками в ошибке» для наших скриптов: падать с текстом, где указан объект и подсказан фикс, чтобы агент сам чинил в цикле

Astral: как защитить Python-проект и GitHub Actions от атак на цепочку поставок — хеши, lock-файлы, cooldown

Astral (23.11.2026) собрала практики против двух сценариев: у мейнтейнера взломали аккаунт или CI и выпустили вредоносный релиз, либо взломан сам сервер раздачи. Версий мало, нужны хеши: они защищают от файлов, добавленных в старый релиз PyPI (до 14 дней), от force-push тегов и от MITM с поддельными TLS-сертификатами. uv.lock уже хранит хеши всех файлов. Для Actions: ссылаться на полный commit SHA с версией в комментарии (`actions/checkout@3d3c42e... # v7.0.1`), конвертировать через pinact, обновлять Dependabot/Renovate, в настройках GitHub можно разрешить только pinned-экшены. Публикацию в PyPI делать через Trusted Publishing (OIDC, `id-token: write`, `uv publish`), релизный workflow закрыть environment с approval. zizmor линтит CI: mutable-теги, опасные триггеры `pull_request_target`, `workflow_run`, `issue_comment`. Cooldown: PyPI снимает большинство малварных пакетов за 24 часа, поэтому не ставим релизы моложе нескольких дней.

Про uv.lock и Dependabot вы, скорее всего, знаете; новое здесь — cooldown, закрепление инструментов в CI и запрет сборки из sdist. Вместо `uvx nox` лучше `uv add --group nox nox` и `uv run --only-group nox --isolated nox -s ...`, плюс `UV_LOCKED=1` в `env` workflow. Скрипты с PEP 723 лочатся через `uv lock --script foo.py`. Первый шаг: в `pyproject.toml` добавить `[tool.uv] exclude-newer = "3d"`, а в `.github/dependabot.yml` — `cooldown: default-days: 3`.

Что взять себе
  • Добавить в pyproject.toml `[tool.uv] exclude-newer = "3d"` и cooldown `default-days: 3` в dependabot.yml — не ставить свежие релизы первые дни
  • Прогнать pinact по workflow-файлам и включить в GitHub «только pinned actions», а zizmor добавить в CI
  • Заменить `uvx <tool>` в CI на `uv add --group` + `uv run --only-group ... --isolated` и поставить `UV_LOCKED=1` в env
  • Включить `no-build = true` в [tool.uv], исключения через `no-binary-package`, если зависимости позволяют
