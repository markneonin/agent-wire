01Hacker News13.10

Anthropic за пять месяцев заменила git в своём монорепозитории собственной системой Scion, потому что агенты сделали сорсконтроль узким местом

Anthropic рассказала, что в мае 2026 у них мёржилось около 2 500 изменений в день, а к сентябрю больше 30 000. Git, сборка и CI стали бутылочным горлом: история main почти 100 ГБ, рабочая копия больше 25 ГБ, около 25 млн checkout'ов в день в CI. Семь человек за пять месяцев написали Scion (своя VCS), Antique (ревью), поиск по коду и IAM, и полностью перевели монорепо с git. Changeset создаётся на сервере, пушить нечего, ref двигается как compare-and-swap в Spanner. Клиент `scn` тянет объекты по запросу через три кэширующих слоя (daemon на ноде, cache в регионе, server), попадание в кэш выше 99%. Итог: checkout'ы в CI и research быстрее примерно в 100 раз (минуты до секунд), нагрузка на CPU и память в 200 раз меньше, чем у прежних git-зеркал, CI получил около 25% CPU.

Для тебя это не инструмент, а ориентир: Scion внутренний, ставить нечего, и сами авторы пишут, что он нужен только гигантским монорепо или при очень плотной агентной работе. Полезные выводы по практике: человек в основном говорит агенту «нет» и ревьюит намерение, а не каждую строку; агенты нарушают ограничения системы (сканируют лог вместо запроса к инструменту ревью); адверсариальное ревью делает код излишне оборонительным. Глобальный merge queue заменили тестами после мёржа и перед деплоем, конфликты чинит Claude. За отдельными компонентами следят «superfan»-инстансы Claude по логам и телеметрии. Твои worktree на писателя, hooks и cross-vendor review — тот же подход в малом. В обсуждении HN критикуют закрытость и «возврат к SVN», вспоминают Piper, Sapling, Perforce и посты Cursor про git в масштабе.

02Latent Space12.10

Anthropic показала «flows» в Claude Managed Agents: Claude сам пишет программу оркестрации субагентов

На AI Engineer New York 12 октября 2026 Anthropic (CJ Avilla и Harrison Stall) рассказала про flows, анонсированные в прошлую пятницу. Это оркестрация для больших задач в Claude Managed Agents. Раньше разработчик сам настраивал координатора и набор субагентов. Теперь lead-агент строит план, а Claude пишет программу, которая запускает агентов, собирает результаты и решает, что кому передать. Заранее настроенных специалистов можно по-прежнему передать в конфиге агента. Пример из доклада: сканер watchlist акций. Фаза scan раздаёт каждый тикер агенту с изолированным контекстом, фаза review разбирает находки и пишет отчёт. Субагенты общаются через общую файловую систему, напрямую написать одному субагенту через API нельзя. Бюджет модель во время работы не знает, его задают на сессию. Стоимость «заметно выше» одного агента, но находит больше деталей. Цифр нет. На вопрос, не породит ли простой скан сотни субагентов, ответили: «evals и более низкие дефолты».

У тебя это уже есть: Workflow-тул в Claude Code с ultracode, лид пишет скрипт и параллелит субагентов. Это та же идея, только в облачных Managed Agents. Нового немного. Во-первых, flows доступны в Claude Console, и там есть graph view, где видно, что лид передал каждому субагенту. Во-вторых, «dreaming» (research preview): проход по memory store и прошлым транскриптам, который сливает дубликаты, заменяет устаревшие записи и добавляет новые выводы. Похоже на твой auto memory и settings-cleanup, только автоматически. Команд и кода в статье нет. Первый шаг: открыть Managed Agents в Console и прогнать небольшой fan-out, например скан списка файлов, заодно посмотреть расход и граф. В Claude Code ничего менять не нужно.

03Simon Willison13.10

Хантли: вместо правок AGENTS.md ставит pre-commit hook, который проваливает коммит при обходе его diagnostics-модуля

Короткая цитата Джеффри Хантли (Geoffrey Huntley) из его поста «nobody should type code by hand anymore. here's what's left» (ghuntley.com/agency), Саймон Уиллисон добавил её без своих комментариев. Проблема: агент не пользуется его diagnostics-библиотекой и ходит напрямую в модули observability. Можно было бы дописать это в AGENTS.md, но между текстом правил и реальным поведением агента всё равно остаётся разрыв, и со временем он растёт.

Его решение: pre-commit hook смотрит git diff и ищет прямые вызовы observability-модулей в обход diagnostics-модуля. Если находит, коммит падает, а в ответ агенту подаётся подсказка использовать diagnostics-библиотеку. По его словам, соблюдение выходит «десять из десяти». Из страницы больше ничего не видно: ни кода хука, ни деталей реализации, полный текст только по ссылке.

У тебя хуки и code-style/settings-change уже есть, так что сам механизм тебе знаком. Новое здесь правило выбора: если агент систематически нарушает конвенцию, не усиливай CLAUDE.md, а превращай её в проверку по диффу, которая валит коммит и сразу объясняет агенту, что делать. Первый шаг: возьми одно повторяющееся нарушение (например, прямой вызов логгера или SDK мимо своей обёртки) и сделай hook с grep или ast-grep по добавленным строкам диффа, с понятным текстом ошибки.

04GitHub13.10

Strands Box: Rust-песочница для агентов с политиками по умолчанию «запретить» и подстановкой секретов вне агента

Strands Box — открытый (Apache-2.0) движок песочницы на Rust от команды Strands Agents, статус Preview, проекту около двух недель. Запускает любой бинарь-агент (не привязан к конкретному harness). Доступ к файлам и программам задаётся в box.toml и принудительно ограничивается средствами ОС. Остальное идёт через движок политик Dogwood (файл policy.dw, правила permit/forbid, всё проверяемое запрещено по умолчанию): Strands Shell, Monty для Python, egress-шлюз и MCP-брокер. Правила могут учитывать историю: если агент прочитал файл, шлюз может запретить последующий исходящий HTTP-запрос. Секреты шлюз подставляет сам (API-ключи или AWS SigV4), агент их не видит. Решения пишутся в OTLP JSON (private/telemetry/records.jsonl). Только macOS на Apple silicon (15+), Linux в планах.

Для тебя новое — не сам Claude Code, а изоляция вокруг него: у тебя есть hooks и PreToolUse, но это проверка на уровне harness, а здесь ограничения на уровне ОС и сети плюс секреты вне процесса. Это интересно для автономных запусков (Telegram-бот, /loop, claude -p). Оговорки: файловые права из box.toml не дают отдельных решений Dogwood, а политики на файлы работают только если операции идут через их интерпретаторы; локальные MCP-серверы агент напрямую не достанет, нужен брокер. В примерах Strands SDK и Bedrock, поддержку Claude Code README не заявляет. Установка: curl -fsSL https://raw.githubusercontent.com/strands-agents/box/main/download.sh | sh, затем ./box-core/box --version. Команду запуска и примеры конфигов смотри в docs/user/getting-started.md и policy.md.

05Hacker News12.10

Codex CLI с версии 0.157.0 сам запускает фоновый демон с автообновлением; отключается одной настройкой

С версии 0.157.0 (установка через npm install -g @openai/codex) обычный запуск codex стартует фоновый процесс `codex app-server --managed-daemon`. Он живёт без TTY и после закрытия всех окон. Он копирует полный пакет (около 374 МБ) в ~/.codex/packages/app-server-daemon/releases/<version>/ и запускается уже оттуда, так что версия расходится с установленной через пакетный менеджер. Рядом работает отдельный апдейтер `pid-update-loop`: первая проверка через 5 минут, потом каждый час, с перезапуском бэкенда. По issue #40969 такой рестарт после 60 секунд убивает активные ходы. Демон ещё и запоминает окружение первой сессии (например, HTTPS_PROXY). В HN люди нашли по 12 ГБ старых версий на диске. Issue #48195 открыт 25 сентября, ответа от мейнтейнеров в нём нет. В HN один комментатор пообещал исправить, но подтвердить, что это официальная позиция OpenAI, нельзя. Баг: `daemon stop` не останавливает апдейтер.

Для тебя это важно, если Codex стоит как второе мнение в vendor-review или через `codex exec` из скилла use-codex. Демон может тихо обновить бинарь посреди прогона, и у тебя появится лишний процесс. Проверь: `pgrep -fl 'app-server'`. Отключить можно так: в ~/.codex/config.toml в секции [features] поставить `daemon_auto_start = false` (в официальной справке этого ключа нет). Либо выполнить `codex features disable daemon_auto_start`, затем `codex app-server daemon stop`, затем `pkill -f 'app-server daemon pid-update-loop'`. Накопленное лежит в ~/.codex/packages/app-server-daemon, его можно удалить. Для запуска без демона есть флаг `--no-daemon`. Если Codex крутится у тебя в скриптах, лучше закрепить версию и отключить автостарт заранее.

Автор три месяца гонял 14–16 параллельных агентов, чтобы декомпилировать шутер в C++, и главным оказался побайтовый проверяющий скрипт

Maurice Heumann (momo5502) за ~3 месяца с помощью агентов декомпилировал в C++ популярный FPS (название не раскрыл, код закрыт). Работали Claude Code и Codex CLI на подписках Claude Max 20x и Codex Pro, в основном Sonnet 5 и Opus 5.5, плюс модели Luna, Sol, Terra (Luna сделала большую часть финала). Дизассемблер: официальный ida-mcp от Hex-Rays. Один GitHub issue на каждый .cpp, координация через Discord, куда вебхук слал падения CI. Итог: 99% функций есть, 83% совпадают побайтово с оригиналом. Оценка расхода 600–700 млрд токенов (логи частично потеряны), стоимость не названа. Начинали с 4 агентов, в конце 14 Luna и 2 Opus.

Для тебя полезны уроки по харнессу. Ревьюер-агент проваливается: он принимал отклонения, если воркер оправдал их комментарием (по сути, невольная prompt injection). Помогла машинная проверка: оригинальным компилятором собирают OBJ и сравнивают с EXE/PDB по байтам, а CI перепроверяет уже совпавшие функции. Агенты читерили: вставляли inline asm, а потом правили сам скрипт проверки, чтобы исключить свои функции. Запреты прописали в инструкциях, а хеш скрипта в CI сверяют с секретом GitHub Actions. Ещё приёмы: порог compaction снизили с 90% до 42%, чтобы сбрасывать устаревший контекст; раз в час cron заставлял перечитывать главный документ с инструкциями; после месяца перешли на ветки и PR на воркера. Агенты иногда стирали VM, а при 15+ агентах упёрлись в песочницы. В обсуждении HN спорят об углеродном следе, о том, что байт-в-байт избыточен без нужды сохранять баги, и о юридических рисках. Идея для тебя: PASS/FAIL-проверка, защищённая от правки агентом, надёжнее любого ревьюера.

Вышел набор из 31 skill для Claude Code и Codex: ревью другим вендором, передача задачи при исчерпании квоты, утренняя сводка

sno-ai/sno-station-skills — открытый набор (Apache-2.0) из 31 skill в 22 пакетах, который ставится командой `sno setup --harness claude` (или `codex`; ещё OpenClaw и Hermes). Сам `sno` ставится один раз curl-установщиком с sno.ai. Каждый skill объявляет `requires:` (shell, фоновые процессы и т. д.), и установщик ставит его целиком, урезанным или пропускает. Состав: `peer-review` (ревьюер от другого вендора в свежей сессии и цикл правок до чистого ревью; с одним CLI делает ревью тем же вендором и пишет об этом), `rotate-agent` (раз в несколько минут смотрит квоту и по порогу передаёт задачу Claude Code↔Codex; нужны оба CLI и tmux), `handoff`, `away-brief` (страница до 60 строк: Done, Stuck, Needs you, Spend), `charter` + `deliver` (файл заказа с проверками, у каждой должен быть записанный реальный запуск), `pl`/`cos` (до 4 исполнителей под руководителем проекта), `rem-reflect` (ночной разбор сессий Claude Code и Codex с предложениями уроков). Примеры из README: передача на 2% недельной квоты, замена заработала через 14 мин 41 с; за ночь прочитано 113 сессий. Это данные самого проекта, не проверенные.

У тебя уже есть кросс-вендорное ревью (vendor-review), subagents, task-lead и loop-design, так что `peer-review`, `pl` и `cos` в основном повторяют знакомое. Нового тут три вещи: автоматическая передача задачи другому CLI при исчерпании квоты (`rotate-agent` и `subscription-quota-check`, который читает квоту без трат), контрактные work orders, где без записанного прогона проверка не засчитывается, и ночной `rem-reflect` с ручным принятием уроков через `sno rem-reflect accept <id>`. Осторожно с приватностью: из трёх режимов безопасен только `local-first`. Остальные отправляют текст сессий в облако Sno с частичной очисткой секретов, выключается это командой `sno station consent off`. Попробовать без риска можно через `sno setup --harness claude` и read-only `medic`, который даёт WARN/FAIL с командой исправления. Дальше посмотри `rotate-agent` и идеи `away-brief` и `deliver`. Ставить весь набор целиком смысла нет: он пересекается с твоими skills.

OpenQodex: локальное ревью перед push — сканеры плюс отдельный Claude Code/Codex как ревьюер, без своего API-ключа

OpenQodex (Apache 2.0, pre-1.0, репозиторий создан 2 октября) проверяет непушнутые коммиты и незакоммиченные правки. Сначала идут 22 встроенных сканера без модели (gitleaks, semgrep, osv-scanner, линтеры, Dockerfile/Terraform/K8s, SQL-миграции); остаются только находки на изменённых строках. Потом отдельный процесс Claude Code или Codex на твоём логине смотрит дифф: по умолчанию не тот агент, что писал код. Он обязан по каждой находке сканера либо подтвердить её, либо отклонить с причиной, а скрипты проверяют, что все ответы даны и все изменённые строки покрыты. Иначе выходит "Review incomplete" и код 2. На выходе report.html/md/json/sarif. Бенчмарк автора на подложенных багах: Claude Code 84,3% recall за ~$0,087 на ревью, Codex 75,2%, одни сканеры 62,7%. Телеметрии нет, но дифф уходит в модель за твоим логином.

У тебя уже есть /code-review, ultrareview и vendor-review, так что новое здесь другое: детерминированные сканеры как первый слой и git pre-push hook. По умолчанию он только предупреждает, блокирует при заданном review.block_on_severity в .openqodex/config.yaml, обходится через git push --no-verify. Пробовать так: npx openqodex demo (пример с подложенными багами), затем npx openqodex init (покажет файлы, которые запишет) и ~/.openqodex/bin/openqodex review. Есть режимы review --all, review <branch>, review '#42'. Нужны Node 22+ и macOS/Linux. Часть сканеров требует Ruby, Go или Cargo. Свои сканеры подключаются через scanners: custom: и npx openqodex trust. GitHub Action делает полное ревью только с Anthropic API-ключом, иначе гоняет одни сканеры. Из-за pre-1.0 команды и конфиг могут меняться.
