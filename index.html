01Hacker News17.11

Команда Claude Code описала, как проверяет код, который на 90% пишет сам Claude

Эдди Османи (claude.dev, 16 ноября 2026) разбирает, как команда Claude Code проверяет работу агентов: около 90% их кода пишет и ревьюит Claude. Идея: без петель проверки можно вести 1–2 агентов, с ними — десятки и сотни. Отдельный грейдер по рубрике дал до +10 пунктов успеха на генерации структурированных файлов.

Конкретика. Три типа тестов: E2E (агенту дают «руки и глаза» через скилл `verify` в `.claude/skills/`, CDP, симуляторы), property-тесты (fast-check, Hypothesis, proptest: round-trip, инварианты, идемпотентность, эквивалентность) и дифференциальные (старая система как оракул, список одобренных отличий). Чек-лист из 39 пунктов с триггерами по диффу: запускаются 3–10 подходящих. REVIEW.md читается с базовой ветки, а не из PR, чтобы изменение не правило свой чекер. После трёх неудачных раундов Claude зовёт человека. Коммит-гейт работает в режимах off/observe/enforce; после двух блокировок третий коммит пропускается. Правила из промахов: паттерн в ≥2 PR, три агента пытаются его опровергнуть; либо replay: три баг-искателя, находят ≥2 — баг обнаружим. Флаки-тесты нельзя ретраить или глушить sleep. В HN критикуют цену: дешёвые детерминированные проверки (линтеры, Playwright) надо ставить первыми.

Для твоего сетапа: скиллы, хуки, ревью и /loop у тебя уже есть, новое — дисциплина вокруг них. Первый шаг: добавить в Stop-хук запись способа проверки в коммит и запустить гейт в режиме observe, который только логирует, что заблокировал бы.

Что взять себе
  • Коммит-гейт в режиме observe: хук логирует коммиты без /code-review или /verify, а enforce включать после проверки ложных срабатываний. Сделать?
  • Читать правила ревью (REVIEW.md, гейты) с базовой ветки, а не из изменений, чтобы PR не правил свой чекер, в нашем cross-vendor review и quality-gates.
  • Правило в CLAUDE.md: флаки-тесты не ретраить и не глушить sleep; не найден корень — удалить тест и записать причину. Плюс лимит: три провала проверки — стоп и зовём человека.
  • Скилл `verify` на проект, который поднимает приложение и гоняет сценарий, плюс property-тесты (Hypothesis) для парсеров и миграций. Завести для одного проекта?

02GitHub18.11

rust-anything: постепенный перенос приложения на Rust с проверкой по записанному поведению оригинала

rust-anything (GitHub, создан 2026-11-16) — CLI и MCP-сервер, который ведёт агента через переписывание кода на Rust по одному куску. Работает с CLI, HTTP-серверами и библиотеками на TypeScript/JS, Python, C, Go, Ruby, Java (PHP и C# в preview). Шаги: `profile` находит горячий код на реальной нагрузке, `analyze` даёт список единиц, порядок и риски, `bridge` генерирует Rust-крейт с обёрткой, чтобы вызывающий код не менялся, `record` прогоняет оригинал на сгенерированных граничных случаях и сохраняет выводы. Rust пишет сам агент или человек в `port.rs`; `diff` проигрывает все записи против порта, `bench` меряет скорость, `gate` требует fmt, clippy, тесты, аудит unsafe и покрытие error-путей. Для целых приложений: `app record`/`app replay`, Rust-«парадная дверь» пересылает непортированные команды оригиналу, `app lift` убирает оригинал в конце. Заявлено до 20x на горячих путях, 38 251 случай без расхождений; пример: поиск x18n по 50 000 ключей — 20x, slugify на Python — 17x, Go — 4x, Java — 3x. Но порт по-функционально часто медленнее JIT: 29 функций x18n вышли медленнее TS, нужен батчинг.

Ограничения: «прошёл» значит совпал с записанными случаями; regex-движки различаются, формат float должен совпасть точно, время, память, конкурентность и побочные эффекты не сравниваются. Код не переписывается автоматически. Для тебя это готовый образец «агентной миграции с оракулом»: запись поведения оригинала + replay как критерий готовности, то, что хорошо ложится на твои loop-design и quality-gates. Первый шаг: `cargo install rust-anything && rust-anything setup` (регистрирует MCP и скилл в Claude Code, Codex, Gemini CLI), затем `rust-anything profile` на небольшом скрипте.

Что взять себе
  • Паттерн «записать поведение оригинала, потом replay как критерий готовности» добавить в loop-design/quality-gates для любых рефакторингов и миграций, не только Rust
  • Взять идею «парадной двери»: новый код стоит перед старым и пересылает непортированное, `app lift` убирает старое в конце — оформить как скилл для постепенных переписываний
  • Поставить `rust-anything setup` и проверить на одном горячем скрипте из ботов (`profile` → `analyze`), с батчингом, а не по-функционально

03Simon Willison17.11

Simon Willison и Prime Radiant выпустили три внешние песочницы для кода, который запускают агенты

Simon Willison вместе с Prime Radiant описал паттерн «external sandbox»: агент работает снаружи, а весь код, который он исполняет, уходит в отдельную песочницу по localhost API. Цель — безопаснее пробовать локальные модели, чтобы ошибка или prompt injection не навредили машине. Три реализации с одним и тем же API: external-sandbox-v86 (Node.js, Alpine Linux в WebAssembly через v86), external-sandbox-container (Python, Alpine в Apple Containers) и external-sandbox-quicksand (Python, библиотека Microsoft Quicksand с QEMU и Alpine). Все лежат в github.com/prime-radiant-inc. Pi, Claude Code или Codex настраивают так, чтобы вызовы исполнения кода шли в песочницу.

Есть опциональный HTTP/HTTPS allow-list прокси, который ограничивает, на какие хосты может ходить код агента. Есть подмена учётных данных: авторизованные API-вызовы работают, а секрет агенту не отдаётся. Есть веб-интерфейс, где политику прокси меняют на ходу: разрешённые адреса, JSON-редактор политики, лог недавней активности. Цифр производительности и готовых команд установки на странице нет, детали в блоге Prime Radiant.

Для тебя это актуально, потому что ты гоняешь локальные модели на MLX и запускаешь агентов через Telegram-бота. Первый шаг: склонировать external-sandbox-container (у тебя macOS) и посмотреть README, как направить туда исполнение команд из Claude Code.

Что взять себе
  • Склонировать external-sandbox-container и проверить, можно ли направить в него Bash-вызовы Claude Code для сессии Telegram-бота
  • Взять идею allow-list прокси: разрешать агенту ходить только на нужные хосты, а правила менять в рантайме
  • Взять подмену учётных данных: чтобы секреты из skill secrets не попадали в контекст агента, а подставлялись снаружи песочницы

Навык antialgorithm заставляет Claude назвать свой первый, самый средний вариант и уйти от него

mankidev/antialgorithm — навык для Claude Code для творческих задач: названия, тексты, сюжеты, идеи игр, постеры, UI. Идея: модель сначала называет свой первый, самый усреднённый вариант, потом отходит от него по причине, взятой из проекта. Создан 2026-11-14, 286 звёзд, 9 коммитов, MIT.

Внутри три скрипта. seed.py бросает случайную стартовую точку, если запрос скудный: для визуала метод, цвета, раскладка, шрифт; для текста голос и регистр; для идей глагол, ограничение, масштаб, давление (системный random, одинаковые промпты стартуют из разных мест). rough.py «ручной» вид для SVG: дрожание линий и букв, сбитые интервалы; только для печати, краски, штампа, туши. check.py рендерит SVG в полном и иконочном размере и ловит текст за краем, под фигурой, низкий контраст, мелкий кегль. Нужны Python 3, а для check.py ещё numpy, Pillow и rsvg-convert или cairosvg. Бенчмарков нет; в демо нижний ряд постеров выбран из примерно дюжины прогонов, то есть не типичный результат. Подробности техники лежат в SKILL.md, его страница не показала.

Для тебя это полезно в frontend-скилле и генерации картинок: там модель тоже выдаёт усреднённое. Идея seed.py (случайная затравка вместо одинаковой первой мысли) легко переносится в твои скиллы. Первый шаг: git clone https://github.com/mankidev/antialgorithm ~/.claude/skills/antialgorithm и прогнать один и тот же запрос на постер SVG 400x600 с навыком и без.

Что взять себе
  • Добавить в скилл frontend случайную затравку в духе seed.py (метод, палитра, раскладка, шрифт), чтобы лендинги не сходились к одному виду?
  • Подключить check.py (рендер SVG в полном и иконочном размере, контраст, выход текста за край) как автопроверку для SVG-артефактов и постеров?
  • В image-create и human-writing требовать сначала назвать «первый средний вариант» и отойти от него по причине из проекта?

Microsoft выпустила MAI Code 2 и Code 2 Flash: кодовые модели, в Copilot по 50% цены

Microsoft AI представила две собственные кодовые модели. MAI Code 2 — для повседневных enterprise-задач: отладка, многофайловая реализация, работа по всему репозиторию, UI. MAI Code 2 Flash — для массовой работы: объяснения кода, точечные правки, рутинные фиксы. Плюс MAI Work Flash для Microsoft 365 и Fabric IQ.

Цифры от самой Microsoft (среднее по DeepSWE 1.1, Terminal Bench 2.1, SWE-Atlas, FrontierCode v1.1, макс. reasoning effort, GitHub Copilot CLI без сабагентов): Code 2 — 98% качества GPT 6.1 Sol за 40% цены и 96% Claude Opus 5.5 за 5% цены. Flash сравним с GPT-6 Luna и Claude Haiku 5.5 за 65% и 20% их цены. Абсолютных цен нет, контекст не указан. Доступны в GitHub Copilot (сейчас промо-цена 50%), Flash — в закрытом превью Foundry; OpenRouter, Vercel, Hermes, Open Code, Kilo обещаны позже. Веса закрыты. Microsoft сама пишет, что модели не тюнились под сложные и очень длинные агентные задачи.

В обсуждении HN скептики: сравнение с max-effort версиями, не контролируемые харнессы, по одной таблице модель уступает Qwen и DeepSeek. Один пользователь в Copilot сказал, что отличий от Opus не заметил на сборке Python и Azure Bicep. Другая команда ушла из Copilot из-за лимитов кредитов.

Для тебя: ничего срочного, Opus 5.5 остаётся основным. Это кандидат на дешёвого исполнителя или второй мнение для vendor-review, когда появится в opencode или OpenRouter. Первый шаг: когда придёт в Open Code, прогнать одну свою рутинную задачу и сравнить с Sonnet 5.5 по цене и результату.

Что взять себе
  • Добавить MAI Code 2 в скилл vendor-review как ещё одного ревьюера, когда появится в opencode/OpenRouter.
  • Прогнать A/B на одной рутинной задаче: Code 2 Flash против Haiku 5.5 по цене и качеству, прежде чем менять модель в агентных файлах low/medium.

06uv releases17.11

uv 0.13.9: меньше lock-файл, фикс `uv lock --locked`, защита от подмены имени пакета в индексе

Вышел uv 0.13.9 (2026-11-17). Производительность: lock-файл стал меньше и читается быстрее, потому что повторяющиеся условия в environment markers вынесены в общие (#23184). Исправления: `uv lock --locked` больше не отклоняет lock-файл, где одинаковые platform markers записаны в разной форме (#23185); значения маркеров с апострофами теперь экранируются правильно (#23185); uv отвергает wheel, который индекс выдаёт под другим именем пакета (#23261); при сбое определения musl-интерпретатора сообщается, какой именно не вернул версию (#23213). Preview-функции: поддержка PEP 832 redirect-файлов `.venv` для project-окружений (#21822) и `http2-keep-alive`, который закрывает зависшие HTTP/2-соединения с активными запросами (#23236). Минимальная версия Rust для сборки uv теперь 1.98 (#23263).

Для твоих FastAPI/Celery-проектов это в основном обычное обновление инструмента: `uv lock --locked` в CI реже будет падать из-за ложных расхождений в маркерах, а diff lock-файла после пересборки может заметно измениться (меньше повторов), это ожидаемо. Проверка имени пакета у wheel — небольшая защита цепочки поставок при работе с приватным индексом. Первый шаг: `uv self update`, затем `uv lock` в одном проекте и посмотреть diff; для зависающих загрузок с HTTP/2 можно попробовать preview-флаг `http2-keep-alive`.

Что взять себе
  • Обновить uv (`uv self update`) и прогнать `uv lock --locked` в CI одного сервиса: проверить, что ложные падения из-за маркеров ушли
  • Закоммитить пересобранный lock-файл отдельным коммитом, чтобы diff от факторизации маркеров не смешивался с изменениями зависимостей
  • Если сборки в CI иногда зависают на загрузке пакетов, включить preview `http2-keep-alive` на одном пайплайне
