Atuin 18.24 добавил Threads: синхронизация и поиск сессий Claude Code, Codex и других агентов между машинами

Atuin (инструмент истории шелла) в версии 18.24+ получил Threads: он записывает, индексирует и синхронизирует сессии кодинг-агентов так же, как раньше историю команд. Поддерживаются Claude Code, Codex, Pi, Omp и OpenCode. Сессию можно найти, продолжить на другой машине или форкнуть в другого агента с сохранением контекста. Запись включается явно (opt-in). Синк идёт поверх append-only лога Atuin, с end-to-end шифрованием: можно использовать их сервер, свой или вообще только локально. Есть MCP-сервер, через который агент сам ищет прошлые сессии: находит заброшенные попытки и причину отказа от них, прошлое расследование инцидента. Командные шаринги сессий автор ещё делает. Из обсуждения на HN (79 комментариев): синкается «почти всё», включая возможные секреты; отключить синк только для Threads пока просят; Claude Code web-сессии не поддержаны; Claude удаляет локальные сессии через 30 дней, Threads их сохраняет.

Для тебя это не оркестрация, а память между сессиями и машинами: у тебя есть codebase-memory и task-context, но нет поиска по прошлым транскриптам и переноса сессии на другую машину. Риск: транскрипты содержат токены, а у тебя бот и ключи в Keychain, так что сначала проверь режим «только локально». Первый шаг: `curl --proto '=https' --tlsv1.2 -LsSf https://setup.atuin.sh | sh`, затем `atuin resume`, и `atuin mcp install claude`.

Что взять себе
  • Поставить Atuin и подключить MCP командой `atuin mcp install claude`, чтобы агент искал прошлые сессии (почему отказались от решения) вместо ручного task-context.
  • Включить Threads только в локальном режиме и проверить, что секреты из транскриптов не уходят на сервер; при синке между машинами поднять свой сервер.
  • Добавить в скилл task-framing или process шаг «сначала поискать в прошлых сессиях через atuin MCP» перед расследованием бага, который уже разбирали.

AWS выпустила официальный локальный эмулятор AWS API на Rust (aws/aws-emulator)

aws/aws-emulator — локальный эмулятор AWS API без аккаунта и вызовов в AWS, для разработки и CI (не для продакшена и не для security-тестов). Нет GUI: поднимается endpoint, на него указывают AWS CLI или SDK через переменные окружения. Один crate на сервис в services/, роутер слушает HTTPS на 127.0.0.1:9297 с самоподписанным сертификатом. Есть embedded-режим для Rust-тестов: изолированный экземпляр на каждый тест, без endpoint и сертификатов. Лицензия CC0-1.0 (vendor/ — Apache 2.0). PR репозиторий не принимает, только issues. Телеметрия включена по умолчанию: отключается `aws-emulator --telemetry off` или `EMULATOR_TELEMETRY=off`.

Ограничения: список сервисов в README не приведён, оценки точности по сервисам лежат на страницах релизов. По расчётам из HN: DynamoDB ~69%, Lambda ~53%, EC2 ~40%, Athena ~22%. IAM, bucket- и KMS-политики и cross-account эмулируются ненадёжно: запрос, который AWS отклонит, локально может пройти. Сброс состояния только перезапуском процесса. Скептики в HN заметили ~29 000 коммитов меньше чем за месяц; сотрудник Amazon заявил, что проект будут поддерживать.

Для тебя: агентам удобно гонять интеграционные тесты против облака без ключей и счетов. Есть skill `aws-emulator` для агента (нужен AWS CLI 2.35.0+). Первый шаг: `aws agent-toolkit add-skill --skill-name aws-emulator --region us-east-1`, на Linux — пакет и запуск `aws-emulator`, на macOS — Docker.

Что взять себе
  • Поставить skill `aws-emulator` командой `aws agent-toolkit add-skill` и проверить, умеет ли агент сам поднять эмулятор в проекте с AWS SDK
  • Добавить в CLAUDE.md проектов с AWS правило: интеграционные тесты идут против локального эмулятора, а IAM- и policy-проверки не доверять эмулятору (он их эмулирует ненадёжно)
  • Включить `EMULATOR_TELEMETRY=off` в окружение сессий и в хук SessionStart, если эмулятор будет использоваться

lot-map: плагин Claude Code с живой картой действий агента рядом с чатом

lot-map (alexeyw/lot-map, MIT, создан 2026-11-09, 462 звезды) - плагин Claude Code, который рисует в панели рядом с чатом карту из 10 станций: You, Model, Memory, Files, Shell, Network, Browser, Agents, Skills, Hooks. Каждый вызов инструмента, шаг модели, хук и скилл посылает импульс от центра к своей станции. Есть маршрут последних станций (ноги держатся 40 с, затем гаснут 20 с), параллельные вызовы с счётчиком ×3, красная точка при ошибках, фоновые задачи горят до завершения, точки сабагентов вокруг Agents, кольцо контекста (янтарное с 70%, красное с 90%), лента из 16 последних строк. Работает на хуках, без сети, без чтения файлов и без вызова модели; между сессиями хранит только последнюю модель по папке. Метки содержат только имена: последние две части пути, хост URL, описание команды.

Ограничения: проверен на Claude Code 2.1.321 и macOS, нужно минимум 144 колонки (иначе команда /lot-map), shell-команды подписаны по имени (python -c = Shell), маркетплейс следует за веткой main, так что перед обновлением читать diff. Для тебя это дешёвая наглядность при Workflow, вложенных лидах и фоновых агентах: видно, что реально горит, где зависло, когда контекст подходит к 70%. Из похожего у тебя есть observability (ccobs), но это не живая панель. Первый шаг: claude plugin install lot-map --marketplace alexeyw/lot-map, затем новая сессия; язык: echo '{"language":"ru"}' | claude plugin configure lot-map@lot-map --values-stdin.

Что взять себе
  • Поставить lot-map и запустить одну Workflow-сессию с сабагентами, чтобы посмотреть, видно ли параллельные ветки (×N) и зависшие фоновые задачи.
  • Взять идею порогов контекста 70% янтарный и 90% красный: добавить такое предупреждение в наш Stop или UserPromptSubmit хук?
  • Перед обновлением плагина читать diff, раз маркетплейс следует за main: закрепить версию или добавить это правило в settings-change?

Плагин work-mode для Claude Code: режимы сессии auto, out, wrap и гейты на хуках

Плагин (MIT, 177 звёзд, создан 8 ноября 2026) ставит режим сессии командой /work-mode; режимы комбинируются (/work-mode auto wrap). auto: модель сама делает обратимое (правки файлов, локальные коммиты, тесты), а необратимое (отправка сообщений, установки, секреты, удаления, платежи, права, прод) складывает в список и показывает один раз в конце; действия с подтверждением идут подряд в самом конце. out: пакетную работу, которую можно проверить выборочно, отдаёт фоновому субагенту или внешнему CLI (codex exec, gemini, claude -p), а в основном треде идёт проверка. Здесь же «read gate»: после 20 000 символов сырого вывода за ход следующие Read, Grep, cat/jq и WebFetch отклоняются, пока модель не делегирует или не объявит причину чтения inline (пишется в ~/.claude/state/tempo-inline/). wrap: сходимость, никаких новых веток, только новые решения с пометкой и рекомендацией. Режим повторяется напоминанием каждый 8-й промпт. Второй плагин, work-mode-gates, меняет «спросить» на «отказать с подсказкой» под auto: запрет новых SUMMARY/REPORT/NOTES*.md, безопасный git commit, Stop-хук, блокирующий непомеченные решения и вопросы «можно ли мне…» в конце.

У тебя уже есть субагенты, Workflow, /loop и хуки, так что новое здесь — идея режима сессии, который переключает поведение хуков, и read gate. Он вынуждает основной контекст не читать большие объёмы, а отдавать их делегатам. Первый шаг: /plugin install work-mode --marketplace danyuchn/claude-work-mode, затем /work-mode out на длинной сессии с логами. Требуется Claude Code 2.1.314+.

Что взять себе
  • Добавить в наш PreToolUse-хук read gate: после ~20 000 символов сырого чтения за ход отказывать Read/Grep/WebFetch, пока не вызван субагент или не объявлена причина
  • Сделать файл режима сессии (как ~/.claude/state/tempo/<session_id>), который читают наши хуки: под auto «ask» превращается в «deny с подсказкой, что делать дальше»
  • Добавить Stop-хук, блокирующий финальные вопросы «сделать ли мне…?» и непомеченные решения, чтобы в конце был один список решений с рекомендациями
  • Ввести в Telegram-бот-сессии режим «список необратимого в конце»: исходящие и платежи копятся и показываются одним блоком

Бенчмарк Postgres 18: случайный UUIDv4 в первичном ключе роняет вставки до ~0,65 от UUIDv7, когда индекс не влезает в память

Николай Самохвалов (PostgresAI) прогнал pgbench на Postgres 18.6 (16 клиентов, одна вставка на транзакцию, таблицы 50–100 млн строк). Пока индекс PK помещается в память (меньше 512 МиБ), разницы почти нет: UUIDv4 держит 0,95–1,10 от UUIDv7. Когда индекс больше shared_buffers, UUIDv4 даёт 0,62–0,69 от упорядоченного ключа (13,9k/s против 21,7k/s у UUIDv7 и 23,5k/s у int8), пишет в 1,5–1,9 раза больше WAL (1324 B на вставку против 744 B из-за full-page images) и раздувает индекс: 3996 МиБ против 3012 у UUIDv7 при заполнении листьев 68% против 90%. Причина: упорядоченный ключ всегда пишет в самый правый лист, а случайный бьёт по любому, и рабочим набором становится весь индекс. Точечный поиск по id одинаков, но order by id desc limit 100 занимает 32 мс против 1 мс. UUIDv7 и int8 вставляют почти одинаково.

Ловушки uuidv7(): id раскрывает время создания; случайных бит 62 против 122, так что это не токен; при генерации на клиентах с расхождением часов индекс заполнен на 69%, поэтому генерируйте на сервере; на Postgres 17 uuid_extract_timestamp() для v7 возвращает NULL. Для SQLAlchemy/FastAPI, если PK сейчас uuid4: смена дефолта не требует перезаписи таблицы, но старые значения остаются v4, а середина индекса будет заполнена примерно наполовину (оценка автора, не измерение). Первый шаг: SET lock_timeout = '500ms'; ALTER TABLE events ALTER COLUMN id SET DEFAULT uuidv7(); — после проверки на копии таблицы.

Что взять себе
  • Найти в моделях SQLAlchemy/SQLModel PK с default=uuid4 и сверить размер каждого индекса с shared_buffers и RAM: ниже порога разницы нет, выше начинаются потери
  • Запустить на проде запрос к pg_stat_io (client backend, writes/evictions) и pg_stat_bgwriter.maxwritten_clean: рост означает, что бэкенды сами вытесняют страницы
  • Для новых таблиц ставить server_default=uuidv7() (генерация на сервере, не в Python) или bigint identity; на копии таблицы сравнить I/O на нагрузке, потом делать ALTER ... SET DEFAULT
  • Заменить order by id desc на order by created_at там, где id — UUIDv4, и проверить, не ищут ли так «последние» строки
