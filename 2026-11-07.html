Дешёвая модель Jev отдаёт сомнительные случаи Opus и даёт его точность в 4 раза дешевле

Hightouch проверял LLM-судей для identity resolution: нужно найти «пере-склейки», когда в одну личность попали записи разных людей. Бенчмарк: 1000 личностей из синтетического городка (pseudopeople), половина склейки. Opus 5.5: 99,0% точности, $3,86 за 1000, 2,2 с на личность. Дешёвые «решающие» модели отдают оценку уверенности 0–1: Luna 97,3% за $0,10, Jev 95,7% за $0,05, быстрее в 10+ раз. На сложном наборе (опечатки в дате рождения, близнецы, Jr/Sr) Opus 95,1%, Jev и Luna около 89%.

Гибрид: Jev оценивает всё, а если уверенность в полосе 30–90% (около 22% случаев), решение передаётся Opus. Простой набор: 98,8% за $0,88 против $3,86. Сложный: 95,3% за $2,94 против 95,1% за $5,39 у одного Opus. Luna с Opus дала лишь 91,6%: она переуверена, ошибается при 90–100% уверенности, поэтому ошибки не видны. Jev ошибается около 50%, то есть откалиброван. Ограничения: синтетические данные, одна задача, сложный набор придумали сами авторы. В комментариях HN критикуют калибровку без ECE и спорные метки. Один пишет, что с хорошим Haiku эскалация почти ничего не дала.

Для твоего сетапа: у тебя уже есть сабагенты на разных моделях и `claude -p --json-schema`, так что новое только в паттерне «дешёвая модель + порог уверенности → эскалация». Первый шаг: в одном скрипте с `claude -p --json-schema` попросить Haiku вернуть поле confidence 0–1, а ниже порога (например, 0,9) переспрашивать Opus, и сравнить цену с «всё на Opus» на 50–100 размеченных примерах. В HN упомянули настройку `/advisor`, где слабая модель сама зовёт сильную; в источнике её нет, это стоит проверить отдельно.

Что взять себе
  • Добавить в наши скрипты на `claude -p --json-schema` поле confidence 0–1 и эскалацию к Opus только в полосе неуверенности, вместо прогона всего через Opus.
  • Перед включением замерить калибровку дешёвой модели: смотреть, где она ошибается при уверенности 90–100%. Если там много ошибок, как у Luna, эскалация не сработает.
  • Подобрать порог эскалации на размеченной выборке, строя кривую «доля отправленного в Opus – точность – цена», как в статье (полоса 30–90% → 22% случаев).

devvm: отдельная Lima-VM на каждую папку проекта для Claude Code, Codex и opencode

devvm (MIT, репозиторий создан 6 ноября 2026, 252 звезды) даёт каждой папке проекта свою изолированную VM на базе Lima. Запускаешь `devvm` в папке: он по файлам проекта определяет тулчейны (например, package.json даёт node), показывает, что получит VM, и после подтверждения открывает шелл по тому же пути, что на хосте. Внутри запускаешь `claude`. Первый запуск собирает базовый образ несколько минут, дальше VM стартуют за секунды как копии образа, тулчейны общие и только для чтения. Встроенные слои: docker, nix, desktop; свои создаются через `devvm layer new`.

Изоляция: VM монтирует только папку проекта, сеть по умолчанию в режиме allowlist (доступны только разрешённые хосты), токены GitHub и Claude Code остаются на хосте. С флагом `--clone` VM работает в собственном клоне репозитория, не трогая рабочее дерево и .git; результат забираешь на хосте через `git fetch devvm` и смотришь `git log -p main..devvm/main`. Авторы сами оговаривают, что полной защиты песочница не даёт. Нужны macOS 13+ или Linux, Lima 2.2+; проверено на Apple silicon и Linux, Intel Mac не тестировался.

Для твоей схемы (Claude Code в терминале и в Telegram-боте, git worktree на писателя) это способ запускать агента с широкими правами без риска для хоста и секретов: вместо worktree получаешь целую VM с клоном. Агентские настройки, скиллы и MCP переносятся через `devvm agent import`, вход через `devvm agent login claude`. Первый шаг: `brew trust --formula devvmhq/tap/devvm && brew install devvmhq/tap/devvm`, затем `devvm doctor` и `devvm --clone` в тестовом проекте.

Что взять себе
  • Гонять писателей-сабагентов и бота в Telegram внутри `devvm --clone` вместо git worktree: забирать результат через `git fetch devvm` и ревьюить `git log -p main..devvm/main` — попробовать на одном проекте?
  • Пустить автономные циклы (/loop, /schedule, fix-until-green) в VM с allowlist-сетью, чтобы агент без человека не имел доступа к токенам и лишним хостам — добавить это правило в скилл loop-design?
  • Перенести окружение в VM через `devvm agent import` и проверить, что скиллы, хуки и MCP (codebase-memory, Telegram) там работают — сделать такой тест?
  • Записать в CLAUDE.md правило: опасные эксперименты и сторонний код запускать только в devvm-VM, а секреты оставлять на хосте (скилл secrets)
