Meta выложила веса Muse Spark Open: 816B параметров, контекст 1M, лицензия с ограничениями

15 октября 2026 Meta опубликовала веса Muse Spark Open: нативно мультимодальная модель на 816B параметров (42B активных) с контекстом 1M токенов, заточенная под код и агентные задачи с длинным горизонтом. Лицензия Muse Model License с ограниченными коммерческими условиями; по обсуждению на HN главное ограничение — нельзя продавать модель как сервис при выручке компании выше $20 млн. Веса на Hugging Face, SageMaker, Google Cloud Model Garden и Microsoft Foundry; через API — Baseten, Fireworks, Groq, Modal, Nebius, OpenRouter, Together. Поддержка SGLang, vLLM, TensorRT-LLM, Transformers, MLX, llama.cpp, Unsloth. Числовых бенчмарков на странице нет, полный отчёт обещан позже. Демо Meta: Muse Code правит и собирает iOS-приложение Ice Cubes целиком на устройстве.

Локально это тяжело: Meta запускала на двух Mac Studio M5 Ultra по 512 ГБ (≈$20–30k по оценке комментаторов). На HN качество оценивают неоднозначно: по Artificial Analysis модель уступает GLM 5.3 Flash и Qwen 3.8 Flash Next, для кода чаще советуют GLM 5.3 Flash и DeepSeek V4.1 Flash. Для твоего сетапа это не замена Opus 5.5, а возможный дешёвый второй мнением или исполнитель через OpenRouter. Первый шаг: добавить в vendor-review модель Muse Spark Open через OpenRouter и сравнить её ревью с Codex и Gemini на одном диффе.

Что взять себе
  • Добавить Muse Spark Open (через OpenRouter) в скилл vendor-review как ещё одного рецензента и сравнить с Codex/Gemini на одном диффе.
  • Проверить, что модель реально тянет tool calls в твоих скриптах: на HN жалуются на сломанные вызовы инструментов у сторонних провайдеров с агрессивной квантизацией, так что тестировать на нескольких провайдерах.

Вышел open_scion: открытая реализация Scion — сервера контроля версий для массовой работы coding-агентов

open_scion (MIT, v0.1.0, ~1000 звёзд за день, 6 коммитов) — независимая реализация публично описанной Anthropic системы Scion, которая сама внутренняя. Идея: классический Git рассчитан на человека (клон, часы работы, один push), а агенты делают тысячи коротких задач по паре файлов в одни и те же ветки. Поэтому работа уходит на сервер. Это форк Gitaly (GitLab), под ним обычные Git-репозитории. Что внутри: sparse-клон только нужных путей (`graft clone`, `graft sparse`); blame, история и поиск считаются на сервере и кэшируются по коммиту; вместо merge queue `UserLand` делает rebase и compare-and-swap, параллельные посадки батчатся; конфликты уходит решать выбранный резолвер (LLM, детерминированный инструмент или никто); `graft-verify` тестирует tip, бисектит и откатывает виноватый коммит; у каждого агента свой токен, allowlist RPC и политики веток; журнал changeset’ов можно слушать вживую. Сервер сам модель не вызывает. Хранилище: SQLite/PostgreSQL + S3/GCS/Azure. Ограничения: интерфейсы до 1.0 поменяются, нет GC паков, нужны Go 1.26, Meson, Ninja.

Для вашей схемы (worktree на писателя, параллельные агенты) это не замена, а взгляд на то, что ломается при масштабе: слияния и проверка после посадки. Сервер вам нужен вряд ли, пока агентов единицы, но паттерны переносимы. Первый шаг: `git clone https://github.com/feder-cr/open_scion && cd open_scion && make build && examples/graft/quickstart.sh` — демо с сервером, двумя агентами и посадкой.

Что взять себе
  • Post-land проверка как у `graft-verify`: после мержа веток от параллельных писателей гонять тесты на tip, при падении бисектить и откатывать виноватый коммит — оформить как скилл или Stop-хук для нашего пайплайна feature-build?
  • Семантические правила ревью: для изменений только в комментариях/доках требовать меньше ревью, чем для логики — добавить такое правило в наши reviewer-агенты (quality-reviewer, business-reviewer)?
  • Права на агента: у каждого свой набор разрешённых действий и веток (аналог RPC allowlist и branch policies) — прописать в PreToolUse-хуке, какие ветки и команды git доступны каждому кастомному агенту?
